---

## 一句话介绍

给 APK 做加固的 GitHub Actions 项目：你给它一个 APK 和几个勾选，它在云端把 APK
解包 → 加固（签名校验 / 核心逻辑转 C / 字符串加密 / 防对比混淆）→ 回编 → 吐回
一个未签名 APK，你拿回去自己重签即可。

---

## 全景图（数据怎么流）

```
你的 APK
   │
   ▼
.github/workflows/protect-modules.yml   ← 唯一入口：网页上勾选 + 填 APK 链接
   │
   ▼
scripts/pipelines/protect.sh            ← 唯一总控：固定顺序执行，勾几个跑几个
   │
   ├─ STEP1  提证书指纹 ────────────────► sigcheck/hash/make-sig-hash.sh
   ├─ STEP2  核心方法转 C（dcc）────────► tools/dcc/ 里的 dcc.py
   ├─ STEP3  把 C 代码组装成 NDK 工程
   ├─ STEP4  编译出 libnc.so
   │
   ├─ STEP5  解包 APK 成 smali，然后按顺序做三件事：
   │     ① repack/mark-native.py        把转 C 的方法改成 native 壳
   │     ② string-enc/encrypt-strings.py 字符串加密
   │     ③ anti-diff/anti-diff.py       防对比混淆（最后做，盖全包噪声）
   │
   └─ STEP6  回编 APK（lib/lib-repack.sh）→ zipalign → 产出 unsigned.apk
             │
             └─ libnc.so 里装着：签名校验 + 环境检测（App 运行时自检，不对就闪退）
```

**执行顺序是写死的**：`sigcheck → dex2c → stringenc → anti-diff → packer(未接入)`。
你勾选的顺序和数量只决定"哪些步骤跑"，不决定先后。

## 谁跟谁有关系（关联表）

这是最容易迷路的地方，全部关联就这几条：

### protect.sh 调用了谁（总控的"手臂"）

| protect.sh 的步骤 | 调用 | 干什么 |
|---|---|---|
| source | `lib/common.sh` `lib-repack.sh` `lib-ndk.sh` | 三个公共库全部吃进总控 |
| STEP1 | `sigcheck/hash/make-sig-hash.sh` | → 内部再调 `extract-cert-fp.py` |
| STEP2 | `tools/dcc/dcc.py` | filter 由 `filter/` 下两个脚本提前生成 |
| STEP3 | `sigcheck/log/make-sig-log.py` | 扫 `sig_check.c`/`env_check.c` 的注释生成头文件 |
| STEP5 | `repack/mark-native.py` **或** `inject/inject-loadlib.py` | 二选一：勾了 dex2c 用前者，只勾 sigcheck 用后者 |
| STEP5 | `string-enc/encrypt-strings.py` | 规则文件直接透传 |
| STEP5 | `anti-diff/anti-diff.py` | 无参数依赖 |
| 回编后 | `repack/patch-dex-version.py`（藏在 lib-repack.sh 里调） | 修 dex 版本头 |

### Python 脚本之间的隐藏依赖（容易漏改的地方！）

| 脚本 | 暗中引用 | 引用什么 |
|---|---|---|
| `encrypt-strings.py` | `filter/rules-to-filter.py` | 借用它的规则解析函数 |
| `encrypt-strings.py` | `inject/inject-loadlib.py` | 借用它的多 dex 目录正则 |
| `anti-diff.py` | `inject/inject-loadlib.py` | 同一正则（报错七的教训：正则只准有一份） |

> **改 `inject-loadlib.py` 里那个目录正则时，三个脚本同时受影响。**
> 这是历史上真实炸过的地方（报错七）。

### lib-repack.sh 内部的固定动作

解包时自动带 `--no-debug-info`（dex 瘦身约 1.8MB）、自动 save dex 版本头；
回编时自动 restore 版本头、调 `patch-dex-version.py`。这些你不用记，
但**别往解包/回编命令里手动加参数**，公共库已经统一了。

### dcc 解压逻辑有 4 份——这是设计，不是重复代码，别去"清理"

解压 `tools/dcc.zip` 的逻辑确实存在 4 份：`lib/common.sh`（bash，主流水线用）、
`inject-loadlib.py` 和 `make-filter-from-apk.py`（python，各自单独运行时的自救兜底）、
`protect-modules.yml`（云端 checkout 后先解压）。历史结论（报错六时期）：
bash 和 python 是两种运行时，python 无法直接复用 bash 函数，硬合并要引入
跨语言子进程调用/状态文件，报错六已证明"跨语言依赖执行顺序"会炸。
各份都幂等（目录在就跳过）且解压后校验 `dcc.py` 存在，唯一真源 `dcc.zip`
只有一份，谁先需要谁解压。**改动时四份的目标解压路径必须保持一致**
（都是 `<仓库根>/tools/dcc/`），改任何一份先 grep 其余三份。
