## 0. 一句话定位

对 dex/smali 做**零方法新增、膨胀受预算约束**的局部等价变换，
让 jadx 阅读成本显著上升，同时**运行时性能几乎不变**。

与现有模块的关系：
- `string-enc` 已覆盖"字符串加密"（正交模块，不重做）
- `anti-diff` 已覆盖"花指令/块重排/防 diff 定位"（正交模块，不重做）
- 本模块补齐剩下三块：**数字混淆、指令替换、标识符混淆**（NP 管理器
  "控制流混淆 8.0"勾选项中性能安全的子集）

## 1. 背景与需求原文（不可压缩项）

> 用户需求原文（2026-xx）："我的需求是一个轻量化的混淆，就是说性能要好，
> 性能一定一定一定一定要好，我的整个项目模块每个性能都其实都还挺好。"

用户提供的对照样本：`docs/dex代码混淆/`（classes.dex 原版 /
classes_flow.dex 为 NP 管理器"控制流混淆 8.0"全开产物，
勾选了字符串加密+方法隐藏+Dex优化+花指令+数字混淆+指令替换）。

## 2. 为什么不做重型 CFF（实测数据，一票否决项）

对样本跑 `python3 scripts/ai-tools/dex-info.py summary` 的权威数据：

| 指标 | 原版 | NP flow 版 | 膨胀倍数 |
|---|---|---|---|
| insns units 总量 | 549 | 6735 | **12.3x** |
| 含码方法数 | 6 | 91 | 15.2x |
| 类数 | 1 | 6 | 6x |
| 核心方法(onCreate$lambda$0) | 451 | 1122 | 2.5x |

重型 CFF 的每一层都是运行时开销：
- 拆块 → 块间跳转变成 `invoke-static`（ART 方法分派 = 最贵指令之一，
  且**内联失效**，JIT 无法跨越调用边界优化）
- 跨类状态机（样本中 5 个辅助类各持 `static int`）→ 每次状态迁移 =
  `sput`(本类) + `invoke` + `sget`(彼类)，还引入 5 次额外类加载/验证
- jadx 反编译这类结构确实困难 —— **但代价是全方法、全路径、每次执行都付**，
  与"性能一定要好"直接冲突。

**结论：方法拆块/跨类状态机/分发循环一律不做。** 本模块只做
"线性代码内的局部变换"——执行时代价 = 变换点数 × 常数条指令，
与循环次数无关（循环体内禁用非零代价变换，见 §5）。

## 3. 目标与红线

### 3.1 目标

| 维度 | 指标 |
|---|---|
| 语义保真 | 对拍测试 100% 一致；真机冷启动 100 次不崩 |
| 运行时性能 | 方法内指令数增幅 ≤15%（预算制，见 §5.4）；方法数/类数增幅 = 0 |
| 混淆效果 | 常量不可直读（jadx 不折叠）、运算式不可心算直译、私有符号不可读 |
| 幂等 | 同一输入重跑，产物逐字节一致 |
| 确定性 | `--seed` 固定时输出一致（可回归） |
| 可集成 | 与 dcc/stringenc/anti-diff 任意组合，回编/安装/运行正常 |

### 3.2 红线（违反 = 设计错误）

1. ❌ 不新增类、不新增方法、不新增字段（方法分派/JIT/类加载零新增）
2. ❌ 循环体内不做常量拆解、运算替换、不透明谓词（循环 = 每迭代都付代价）
3. ❌ 不改方法签名、不改访问标志、不改类继承关系
4. ❌ 不触碰 Manifest 引用的组件类/被反射的名字/`R$xxx` 内部类
   （硬排除名单见 §7）
5. ❌ 不改字符串内容（string-enc 管辖）
6. ❌ 寄存器总数增幅每方法 ≤2（仅不透明谓词需要临时寄存器；宽对完整性
   约束沿用报错三十二教训：**wide 值两寄存器不可拆**）
7. ❌ 凡 .locals 提升，只允许在 **`4 + 参数槽总数 - 1 ≤ 15`** 时进行
   （这是**允许提升的条件**；`> 15` 即越界、拒绝提升——报错三十四：
   提升 .locals 会让参数物理号整体平移，多参数槽方法
   （wide J/D 占 2 槽、非 static 含 this）一旦越界，4-bit 指令槽直接
   回编炸 `Invalid register: v16`）；参数槽计数逻辑从 anti-diff
   `_count_param_slots`/`_max_param_index` 抽公共到 `scripts/lib/`
   （两处共享同一实现，严禁各抄一份——报错七：单一真相）
8. ❌ 凡把寄存器/常量从一个指令形态搬进另一形态，必须校验目标形态的
   编码宽度（报错三十三/二十一：4-bit 槽上限 v15、const/4 上限 v15、
   const/16 可到 v255、/range 需连续升序）；宽对作整体单元永不拆

## 4. 变换清单（全部为线性局部变换）

### 变换 D：标识符混淆（零膨胀，性能代价 = 0）

- **字符集门控（探针决定，见 §6 阶段 0）**：
  - 首选：不可见 Unicode（U+06DB 系阿拉伯区分音符号，参照 NP 样本）——
    **仅在阶段 0 探针全部通过后启用**；任一探针失败即降级
  - 降级：ASCII 可见随机后缀（如 `a~z` 6 位随机串），牺牲"不可见"效果
    换全链路兼容；两条路线由 `--charset unicode|ascii` 显式选择，
    构建日志必须打印实际生效的字符集（防静默降级无人知晓）
- 对象：类内 `private` 方法名、非反射使用的字段名 → 上述字符集
- 不改 public/protected/**internal**（见 §7.1 Kotlin 可见性陷阱）、
  不改组件类名（§7）
- 运行时代价：0（只有 dex 字符串表略大，冷启动无感）
- jadx 效果：满屏不可见符号（unicode 路线）或长随机后缀（ascii 路线），
  方法名无法记忆/搜索
- 风险：反射/序列化/JNI RegisterNatives —— 靠硬排除名单 + 仅改 private
  把风险压到最低；`$r8$lambda$`/`$i$a$`/`access$`/`Companion` 等 R8/Kotlin
  编译器合成名**不改**（样例中 lambda 名是 Compose 编译器产物，改了影响
  调试符号回溯；完整边界清单见 §7.2）
- **改名必须同步改三类位置**：① `.method`/`.field` 声明行本身；
  ② 方法体内全部 `invoke-*`/`sget-*`/`iput-*`/`iget-*` 等对该名字的
  引用；③ **`access$NNN` 桥方法体内的调用点也要跟着改**（§7.2 规定
  桥名本身不改，但桥是普通方法体，体内对被改名 private 成员的引用
  属于②的范畴——漏改 = 回编炸或运行期 NoSuchMethod）。
  冒烟测试必须有"改名后引用计数守恒"断言

### 变换 B：常量拆解（数字混淆，+2~3 条/处，预算制）

- **寄存器安全（先于效果论证，红线 7/8 落地）**：
  - 中间值寄存器**只允许两种来源**：① 复用方法内**值已知**的寄存器
    （保守判定：该寄存器在插入点之前有确定的写入且其值到插入点处
    仍可静态追踪——文本层可达判定，判不准就不算已知）；② 走
    `.locals` 提升路线，必须满足红线 7 的提升条件
    `4 + 槽总数 - 1 ≤ 15`（复用 `scripts/lib/` 公共参数槽计数），
    不满足的方法**放弃 B 的需新寄存器形态**
  - **⚠️ v3 删除了 v2 的"零新寄存器保底形态"**（v2 评审 🔴3）：v2 曾
    设计"`const/16 v0, 0xC8` + `add-int/2addr v0, v1_orig`，v1_orig 取
    插入点处已死的寄存器"——**数学上不成立**："死寄存器"是数据流术语
    "此后无读"，**不是"此时值已知"**：死寄存器的当前值是未定义垃圾，
    拿它做运算 = `v0 += 垃圾`，结果不是原常量（报错三十二"读未初始化
    寄存器"的同型错误）。拆 700 成 500+200 必须有第二个**已知为 200**
    的操作数，这只能来自新寄存器或值确定的现有寄存器，不存在真正
    "零新寄存器"的拆解形态。**不要为覆盖率硬造错误的形态**：变换 B
    的路线只有三条——复用值已确定的寄存器（罕见）、过门槛的
    .locals 提升、放弃该处。找不到安全路线就整处放弃（宁缺勿滥，
    同报错三十四"签名解析失败也跳过"策略）
  - 每方法 .locals 提升至多 1 次、且只对通过硬门槛的方法（宁缺勿滥，
    同报错三十四"签名解析失败也跳过"策略）
- `const/16 v0, 0x1F4` → 链式依赖形态（关键：jadx 的常量折叠只处理
  同语句纯常量，**跨语句变量链不折叠**）：
  ```smali
  const/16 v0, 0x1F4          ; 原: const/16 v0, 0x2BC (700)
  const/16 v1, 0xC8           ; 新增: 中间值 200(v1 为已死寄存器或已提升的局部)
  add-int/2addr v0, v1        ; v0 = 500+200 = 700，但 jadx 显示两个"变量"相加
  ```
  深链形态（3 段）让读的人必须手动求值
- **const 指令变体选择按值重选**（报错二十七 `_fits()` 同型约束）：
  500 装不进 `const/4` 就必须换 `const/16`，拆出来的中间值同理逐个
  校验编码宽度；`const/4` 目标寄存器受 4-bit 上限 v15 约束（报错三十三）
- 乘法形态用于大常量：`x = A` → `v0 = A>>k; shl v0, k; or 低位`
- 代价：每处 +2~3 条一次性指令；配额制（§5.4）保证预算不破
- jadx 效果：所有魔法数字变成需要人工求值的表达式链

### 变换 A：运算替换（+1~2 条/处，预算制）

- **逐形态寄存器读/写方向论证（红线 8 落地，凡论证缺失的形态禁止实现）**：
  - `add-int v0,v1,v2 ⇄ sub-int v0,v1,neg(v2)`：`neg-int` 是**原地写**
    （`neg-int v2, v2` 会破坏 v2 原值），v2 在插入点之后若仍被读即语义
    变化。安全实现二选一：① 仅当 v2 在该指令之后**再无读引用**（同
    变换 B 的死寄存器判定）才允许原地 neg；② 需要额外寄存器的
    `move v3, v2` + `neg-int v3, v3` 形态按变换 B 的寄存器来源规则
    办理（已死寄存器或过门槛的 .locals 提升），找不到就放弃该处
  - `const vX, 0` 后接 `xor-int/2addr` 恒等对：**0 常量由本模块自己插入**
    （const/4 vX, 0），插入的 vX 同样受变换 B 的寄存器来源规则约束；
    严禁假设"方法内已有寄存器恰好为 0"
  - lit8/lit16 边界值互换：**同一指令、仅换立即数编码**（如
    `add-int/lit8` ⇄ `add-int/lit16` 同语义变体——同为 int、同为 22s
    格式，仅立即数可容纳范围不同），不搬寄存器、不换寄存器数——避开
    跨形态寄存器宽度问题（报错三十三/二十一的教训只适用于"搬寄存器"，
    本形态不搬）。若某候选形态必须搬寄存器，一律按红线 8 校验目标形态
    编码宽度。
    **变体池准入硬约束（v3 修订，v2 评审 🔴2）：池内只放"类型一致 +
    位宽可容纳"的指令变体。v2 曾举 `const/16` → `const-wide/16` 作
    "等值重编码"例——**错误已删**：前者产 int、后者产 long，类型不同
    语义不等价，下游 `int-to-long`/算术会因源类型改变而结果不同，或被
    verifier 寄存器类型推断直接拒绝。任何"换 opcode"候选必须先证明
    产出类型与原指令一致，证明不了就不进池
- 代价：每处 +1~2 条，一次性；配额制
- jadx 效果：运算语义不变但表达形态被随机化，模式识别失效

### 变换 C：不透明谓词（+2~3 条/处，预算制，**阶段 3：待调研，无设计**）

> ⚠️ 状态声明：本节只有**调研方向**，没有可执行设计。在候选形态经 jadx
> 实测验证"确实不被折叠"之前，**禁止把本阶段排入实施计划**（折叠了就
> 等于白付性能）。寄存器来源规则同变换 B（已死寄存器或过门槛的
> .locals 提升）。`rem-int/lit8` 是 22b 格式，操作数寄存器受 8-bit 编址
> 约束（上限 v255），lit8 立即数受有符号 8 位约束——设计期须逐形态
> 校验（红线 8）。

- 候选调研方向（每个都必须先 jadx 实测，且记录测试时用的 jadx 版本——
  抽象解释能力随版本演进，今天不折叠的形态明天可能被消化，见 §9.2）：
  1. 操作数来自方法参数派生（参数值运行期才确定，静态必然不可折叠；
     代价是参数被"读"一次，需确认不触发 verifier 对未初始化的误判）
  2. 跨语句链：两条以上指令接力制造恒真值（jadx 折叠器跨语句不工作，
     与变换 B 同一原理，但需实测验证 jadx 数据流分析边界）
  3. 未初始化语义边界形态（风险最高，可能触发 VerifyError，最后调研）
- 代价：每分支 +2~3 条；仅用于非循环方法的低频分支

## 5. 模块设计

### 5.1 位置与 CLI 契约（沿用仓库惯例）

```
scripts/light-obf/
├── light-obf.py          # CLI: <smali目录> <规则文件> [--seed N] [--flags b,a,c,d] [--clean]
└── tests/
    └── test-smoke.sh     # 合成 smali 冒烟 + 幂等 + 预算断言
```

- 输入是 **smali 目录**（baksmali 产物），与 string-enc/anti-diff 同路线：
  apktool 解包 → 文本变换 → 回编。不做 dex 直改（沿用 §8.8 已知边界）
- 规则文件格式与 `rules-to-filter.py` 输入一致（点号通配符），方法筛选
  复用同一套"点号→斜杠"逻辑
- `--seed` 确定性；类标记沿用 string-enc 的组件标记思路（变换过的类留
  标记行，重跑跳过）
- **`--clean` 语义（v3 修订，v2 评审 🟠4，采纳方案 (b)——B/A 本质
  不可逆，必须向用户说明白）**：
  - clean **只能**撤销变换 D（标识符改名）：D 的可逆性靠 `--map`
    （原名↔新名映射反查）；clean 清除"标记行 + 未进 dex 的注入物"
  - 变换 B/A **不做恢复**——指令已写进 smali 文本/dex，clean 后
    依然在；smali 文本里没有原名可查、没有"拆链前的常量"可逆推，
    B/A 回滚的唯一路径是**重新解包原始 apk**
  - **clean 后重跑保护（fail-fast）**：clean 只清标记，若对含 B/A
    形态但已无标记的 smali 重跑，会被当"未处理类"二次变换（B 的
    常量链再拆一层、A 的形态再反转一次）→ 幂等破坏、逐轮膨胀。
    因此 CLI 必须 fail-fast：对"无本模块标记但检出 B/A 特征形态"
    的类**拒绝处理并报错**，提示"请从 fresh unpack 重新开始"，
    绝不静默二次变换。此行为写进 CLI --help 与冒烟测试断言
  - 禁止在 --help 或日志里暗示 clean 是"完整回滚"——它只回滚 D

### 5.2 执行顺序

流水线中放在 **dcc 之后、stringenc 之前**（被 dcc 抽走的方法已是
native 壳，自然不被本模块处理；stringenc 的桩字段引用依赖名字稳定，
故标识符变换须在其之前完成——集成时必须验证此顺序）。

**消费者清单（变换 D 开启 unicode 路线时必须同批核验；报错二十一
"模块产物形态一变，消费者必须同批更新"教训的落地）**：

| 消费者 | 受影响点 | 核验要求 |
|---|---|---|
| `encrypt-strings.py` `_FIELD_RE`(L497) | `[A-Za-z_$][\w$]*` 匹配不到 Unicode 字段名 → 字段明文初值残留 | **探针 P2 直接验证**（§6 阶段 0）；unicode 路线启用则同批放宽为 `\w`+Unicode 类 |
| `encrypt-strings.py` `_FIELD_STRING_LITERAL_RE`(L777) | 同上正则族，构建期"去初值漏改"断言随之漏判 | 同上，与 `_FIELD_RE` 同一 commit 更新（两处共享同型正则） |
| `anti-diff.py` `_method_name`(L1140) | `[A-Za-z0-9_.$<>]+` 提取不到 Unicode 方法名 → 标签重命名漏处理（静默，仅覆盖率损失） | 同批更新或在 §5.5 记录"已知覆盖缺口" |

**不受影响（已核实，勿盲目"顺手修复"）**：`_FIELD_REF_RE`/`_PAYLOAD_RE`
绑定的是 StrDec 桩自身 ASCII 字段名（`StrDec;->F\d+:`），变换 D 不碰
桩字段；`_INVOKE_RE` 的方法名段是 `[^\s(]+`，可匹配 Unicode；
`mark-native.py` 与 dcc 在 light-obf **之前**运行，顺序上免疫——但若
未来有人把 light-obf 提到 dcc 之前，dcc 的 `compiled_methods.txt`
正则 `^(L[^;]+;)([^(]+)(\(.*\)\S+)$` 仍兼容（`L[^;]+;` 不限 ASCII），
风险在 smali 编译器而非正则。

### 5.3 循环检测（红线 2 的落地）

smali 文本层保守判定：方法内存在**反向 goto**（目标标签行号 < goto 行号）
→ 判定含循环 → 该方法**只做变换 D**（零膨胀），跳过 B/A/C。

**两个方向的代价论证（缺一不可，v1 只论证了误判方向）**：
- 误判有循环（把无循环当有循环）：只损失该方法的 B/A/C 覆盖，
  混淆效果打折，**性能无损** —— 可接受
- **漏判有循环（把有循环当无循环）：性能灾难**。循环体内的 +2~3 条
  变换指令按迭代次数放大，与"性能一定要好"直接冲突 —— 不可接受。
  已知漏判形态：do-while 编译产物可能只有前向 goto；try-catch 内
  循环的回边可能不走 goto；if 条件回跳可能被文本层当普通分支

因此检测必须**宁误判勿漏判**：除反向 goto 外，把以下也判为"含循环"
（全部纳入 §6 冒烟断言）：① `if-*` 目标标签行号 ≤ 自身行号（条件回边）；
② 方法内任何 `goto/32`、`packed-switch`/`sparse-switch` 目标指向
更早位置；③ **try-catch 方法一律视为可能含循环**（保守全跳过 B/A/C，
与 anti-diff 对 try-catch 的保守策略同型）。仍无法静态覆盖的残余
形态（如经过 switch 的循环）由阶段 2 验收兜底：**对拍用例必须含
已知循环方法**，发现循环方法被做了 B/A/C 即 fail 并把该形态补进
检测规则。

不做精确支配树分析——按上述保守规则，误判只损失覆盖不损失性能，
两害相权取其轻。

### 5.4 预算制（红线 1 的落地）

- 每方法变换配额 = `min(原insns数 × 15%, 24)` 条新增指令上限
- ≤10 units 的小方法只做变换 D（膨胀比例在小方法上放大最快）
- **11~16 units 的方法只做 A 的 lit 变体互换**（v3 修订：v2 写的
  "B 的零新寄存器保底形态"已被删除，见 §4 变换 B；该区段 15% 配额
  ≈ 2 条，不够任何需新寄存器/需 .locals 提升的形态
  （每处至少 +2 条还得留余量）；≥17 units 才开放全部形态
- 同一基本块内 B+A+C 合计 ≤3 处（避免局部热点集中膨胀）

### 5.5 与 anti-diff 的关系（顺序 / 名单 / 标记，三件事必须显式定义）

- **执行顺序**：light-obf 在 anti-diff **之前**跑（流水线固定顺序
  dcc → light-obf → stringenc → anti-diff → packer，与 protect.sh
  现行 sigcheck → dex2c → stringenc → anti-diff → packer 对齐插入）。
  理由：anti-diff 的块重排/条件反折会移动方法体行位置，light-obf 的
  变换 B/A 依赖"指令相对顺序 + 死寄存器判定"，在重排后的代码上做
  线性分析不可靠；且 anti-diff 的幂等标记在类头，light-obf 块级
  操作不会挪走它。**集成时必须真机验证此顺序**（报错二十六教训：
  顺序正确性只有端到端能证明）
- **排除名单单一真相**：light-obf 的硬排除名单**直接复用**
  `anti-diff.py` 的 `SKIP_CLASS_PREFIXES`（`_load_module` 方式加载，
  同 anti-diff 复用 inject-loadlib `SMALI_DIR_RE` 的先例——报错七：
  名单只准有一份）。light-obf 不另写副本；light-obf 特有的追加条目
  定义在 `EXTRA_SKIP_PREFIXES` 并集处理（报错七：并集是"追加"不是
  "抄副本"），当前追加内容及理由：
  - **`'com.nc.'`（v3 修订，v2 评审 🔴1）**：stringenc 的解密桩
    `Lcom/nc/strdec/StrDec;`（`GAMMA`/`SEED` 等桩字段）不在
    `SKIP_CLASS_PREFIXES` 内——anti-diff 不需要它（不改字段名），
    但 light-obf 改字段名：若规则写 `**`，桩的 private 字段会被改名
    → 桩解密引用全断 → **全包字符串静默乱码**。stringenc 靠
    `classify()` 单独返回 `'stub'` 兜底（`encrypt-strings.py` L869），
    light-obf 必须有同型兜底：类描述命中 `Lcom/nc/` 前缀即跳过，
    不依赖用户规则
- **标记格式**：light-obf 用独立标记 `# nc-lightobf-applied v1`
  （与 `# nc-antidiff-applied v1` 并存，互不解析对方标记，幂等各自
  独立判定）；light-obf 的变换不做块重排，不会挪动 anti-diff 标记行

  - jadx 人工抽查：常量链确实不被折叠（变换 B 的核心验收）

  - **往返验证**：回编 → 再反编译 → 对比，指令骨架零语义漂移

## 7. 硬排除名单（变换 D 的防御边界)

- Manifest 引用的全部组件类及其内部类（Activity/Service/Receiver/Provider）
- `R`/`R$*`、`BuildConfig`、`databinding/*`
- 名字含 `$r8$`/`$i$a$`/`$$` 的编译器合成符号，及 Kotlin 的
  `access$`/`Companion`/`DefaultImpls` 产物（边界细则见 §7.2）
- 被 `invoke-` 之外的机制引用的符号无法静态识别 → 凡 public/protected/
  internal 一律不改（保守：混淆收益让位于正确性）
- **反射/序列化高危形态**：类内出现 `getDeclaredField`/`getDeclaredMethod`/
  `Class.forName` 且目标字符串可静态解析到本类成员 → 该成员不改
  （保守：宁可漏混淆）；Gson/Jackson/Room/kotlinx.serialization 注解
  标记的类不改（与 stringenc 硬排除名单对齐）
- 含 `native` 方法的类（sigcheck/inject 插桩目标）
- **light-obf 自家桩/基础设施类**（v3 修订，v2 评审 🔴1）：`com.nc.`
  前缀全部类——含 stringenc 解密桩 `com.nc.strdec.StrDec`（其
  `GAMMA`/`SEED` 等 private 字段被改名会导致全包字符串静默乱码）。
  与 `EXTRA_SKIP_PREFIXES`（§5.5）同一真相，实现时两处引用同一常量
- 用户规则显式排除的类

### 7.1 Kotlin 可见性陷阱（变换 D 的对象判定依据；v3 自 §9 底下归位）

dex 层的访问标志与 Kotlin 源码可见性**不是一回事**：Kotlin 的
`protected` 成员编译成 JVM `public`（`protected` 在 JVM 字节码层
不存在于方法标志的组合语义中）。因此变换 D **不能只看 smali 的
`.method public` 就当它是真 public**——正确的保守判定是：
- 只改 smali 层明确 `private` 的成员；
- `public`/`protected` 一律不改（宁可漏改）；
- 命中 `@JvmName`/`@PublishedApi`/`@VisibleForTesting` 注解的成员
  一律不改（跨模块/inline 契约面）。
漏改的代价只是混淆覆盖变小，误改的代价是运行期 NoSuchMethod——
两害相权永远取漏改。

### 7.2 编译器合成符号边界清单（变换 D 不改的完整集合；v3 自 §9 底下归位）

| 形态 | 来源 | 不改理由 |
|---|---|---|
| `$r8$lambda$*` | R8 desugaring | 调试符号回溯、Compose 编译器产物 |
| `$i$a$*` / `$i$f$*` | Kotlin inline 标记 | 与 stringenc `_SKIP_STRING_PREFIXES` 同源策略 |
| `access$NNN` / `access$NNN$p` | Kotlin/Java 内部类互访桥 | 编译器契约，反射框架（Gson 等）会引用；**桥名不改，但桥体内对被改名 private 成员的引用要跟着改**（§4 变换 D 第③类位置） |
| `Companion`/`getInstance` | Kotlin object/companion | 跨模块契约面 |
| `DefaultImpls` | Kotlin 接口默认方法 | 接口契约面 |
| `serialVersionUID`、`writeObject`/`readObject`/`readResolve` | Java 序列化协议 | 序列化按名字反射查找 |

## 9. 已知边界（审查时知悉，不算 bug）

1. 本模块是"阅读成本放大器"，不是密码学屏障；jadx 人工求值恒量链的
   成本是 O(链长)，有心人仍可还原——威胁模型与 stringenc 一致
   （`encrypt-strings.py` 文件头边界声明："防静态可见性，不是密码学
   安全"；v3 注：v2 写的"string-enc §8.6"经全库核实无对应章节，
   系悬空引用，已改指真实源头）
2. 阶段 3 的不透明谓词对**新版 jadx 的抽象解释**效果需要持续验证，
   jadx 升级可能消化掉部分形态——这是所有 smali 层混淆的共同宿命
3. 混淆只改 dex 层；dcc 抽走的 native 方法在 so 里，不受本模块影响
4. 标识符混淆后堆栈可读性下降（与 NP 样本相同的副作用），排障需靠
   保留的 public 符号 + 混淆 mapping（可选输出 `--map` 供开发者留存；
   map 是 clean 撤销变换 D 的反查依据，见 §5.1）
