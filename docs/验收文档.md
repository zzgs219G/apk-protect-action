### 3.1 L1 缓存产物三重验证（A/B 对质）

| 验证项 | 旧加壳包（`简盒_加壳.apk`） | 新包（`简盒_加壳_新字符串加密_sign.apk`） |

**结论：被测 APK 确实包含 L1 缓存**——真机数据有效，下述证伪结论成立。

### 3.2 真机复测结果（报告 §六，7 轮冷启动取中位数）

| 维度 | 正式版 | 旧加壳版 | **L1 缓存版** |
|---|---|---|---|
| 冷启动中位数 | ~195ms | ~427ms | **~427ms（持平）** |
| 启动 6s CPU | ~2.75s | ~3.9s | ~3.7s（小幅改善） |
| TOTAL PSS（8s） | 280.6MB | 339.9MB | ~314MB（-26MB，改善） |
| 热启动 | 失真 | 失真 | 44-59ms（有效值） |
| 崩溃 | — | — | 全程无新增 |

### 3.3 验收判定（诚实记录）

1. **L1 缓存交付合格**：实现、测试、产物三重验证通过；无回归；CPU/PSS 小幅改善；intern 语义恢复。
2. **性能假设证伪**：预期「缓存使冷启动 ~427 → ~270ms」**未发生**。原假设「stringenc 每执行解密 × 重组 ~20 次 ≈ 200ms」不成立——真机冷启动期间大部分使用点仅执行 1~2 次，stringenc 实际成本 ≈ 10-20ms 量级。当初从 v1 事故（debuggable 解释执行下首帧卡死）外推到 release+JIT 场景，放大了约一个数量级。
3. **stringenc 主犯地位撤销**；L1 缓存保留（无回归 + CPU/PSS 小幅改善 + intern 语义 + 重组密集场景仍有价值）。

## 四、新归因假设：packer 的 AOT 损失（下轮验证的主目标）

### 4.1 证据

| # | 事实 | 来源 |
|---|---|---|
| 1 | 正式版内置 baseline profile（`assets/dexopt/baseline.prof` 12,769B + `.profm`） | 验收时 unzip 实查 |
| 2 | 加壳包**原样保留**该 profile（字节级相同，md5 一致）——未被流水线处理 | 同上 + `AOT损失验证记录.md` §四 |
| 3 | profile 按 dex 校验和/方法索引绑定；加壳后 dex 已被替换/改写 → profile 校验失败 → ART 忽略 | baseline profile 机制；**已被日志坐实**（见下） |
| 4 | 系统在装包阶段主动降级编译档位：`ArtService: Adjusting the compiler filter ... from 'speed-profile' to 'verify' because there is no valid profile`；最终 `[status=verify] [reason=install] [executable=false]` | `AOT损失验证记录.md` §3.2 装包全量日志 |
| ~~5~~ | ~~dpt 的 execve 钩子拦截 dex2oat~~ | **已证伪**（全量日志无拦截痕迹，dex2oat 正常执行 code 0）——原判据撤销，见 `AOT损失验证记录.md` §五 |
| 6 | 综合效应：加壳版**全程解释/JIT、无 AOT**——对一个 6.8MB 的 Compose 应用，冷启动 +100~200ms 属典型量级 | AOT 机制 |

### 4.2 验证方案执行状态（原三步）

| # | 操作 | 状态 |
|---|---|---|
| 1 | ~~`cmd package compile --check-prof`~~（Android 12+ 已废弃该 flag） | ✅ 改用 `dumpsys package dexopt` 完成：`[status=verify]`，见 `AOT损失验证记录.md` §二 |
| 2 | 安装期 logcat 抓 dex2oat | ✅ 完成：dex2oat 正常执行未被拦；决定性行来自 `artd`/`ArtService`（须全量抓取，`-s` 过滤会漏），见 `AOT损失验证记录.md` §三 |
| 3 | 二分矩阵（A=仅 packer；B=A+stringenc；C=B+dex2c） | ⏳ 未执行（需 jian_box 逐轮勾选） |

> ⚠️ **关于「强制 AOT」实验的设计缺陷**：`AOT损失验证记录.md` §6.3 建议
> `cmd package compile -m speed -f` 后复测冷启动——该实验**无法验证 AOT 假设**：
> 加壳包的 APK 里唯一的 dex 是壳 dex（~10KB），业务 dex 是运行时从内嵌 zip/
> 内存加载的，**不在 dex2oat 的编译范围内**。`status=speed` 只会编译壳类，
> 冷启动必然无变化——按 §6.3 的判据会误判成「瓶颈在壳运行时」。
> 能「看见」执行方式差异的正确仪器是 **Perfetto/simpleperf**：加壳版冷启动
> trace 里应出现大量 interpreter/JIT 帧（对比正式版的直接执行）。

### 4.3 若坐实的缓解方向（另立项，不在本批次）

| 方向 | 说明 | 代价 |
|---|---|---|
| ① profile 重建 | 打包时对变换后 dex 重算/裁剪 baseline profile（需 profile 重写工具，方法索引映射复杂） | 高 |
| ② 有条件放行 dex2oat | 对「还原后」的 dex 二次 dexopt（需壳与 dexopt 时序配合，且填料期不能编） | 高 |
| ③ 接受 AOT 损失，冷启动关键路径方法走 dex2c | native 方法不受「无 AOT」影响（本就是编译好的 C） | 中；注意仅主类应指向真正的启动热路径 |
| ④ 接受现状 | 427ms 对目标用户可接受 | 0 |
