# 字符串加密架构优化（设计文档）

- **日期**：2026-10-12
- **状态**：L1 已实施并验收（真机：缓存生效、无回归，但**冷启动持平 ~427ms——L1 的性能假设被证伪**，stringenc 非主犯）· **L2 缓行**（其前提"stringenc 占冷启动大头"已消失）· L3 预告（缓行）
- **验收后新归因**：冷启动 +232ms 的头号嫌疑转移至 **packer 的 AOT 损失**（baseline profile 未随 dex 变换重算 → ART 编译档位降级 verify → 全程解释执行），详见《简盒-加壳对比测试报告.md》§六与变更历史报错四十四后批次验收行
- **关联**：`docs/简盒-加壳对比测试报告.md`（性能实测）、~~`scripts/string-enc/`~~（**模块已于 2026-10-13 随验收结论下线删除**,本文档保留为设计与验收档案;git 历史可找回源码)
- **结论先行**：启动慢 ~200ms 是**架构问题**（解密挂在「每次执行」上、无缓存、无 intern），不是**算法问题**（XOR 算术仅占 ~5%，纳秒级）。换算法不解决问题；缓存（L1）拿走 ~90% 收益；clinit 前移（L2）是缓存的终态形态。

## 一、问题定位（实测证据）

### 1.1 测试数据（详见《简盒-加壳对比测试报告.md》）

全模块勾选（sigcheck + dex2c仅主类 + stringenc全量 + antidiff + envcheck + packer），简盒 v2.1.1，Xiaomi/Android 16：

| 指标 | 正式版 | 加壳版 | 差值 |
|---|---|---|---|
| 冷启动中位数 | ~195ms | ~427ms | **+232ms** |
| 启动 6s CPU（jiffies） | 2.72s | 3.86s | **+1.14s** |
| PSS | 280.6MB | 339.9MB | +59MB |

### 1.2 同一方法的三态字节对照（本仓库可复现，见 §8 工具）

```
① 原始 dex（真字节码）：
   70 10 86 61 01 00 62 00 d3 28 71 10 1f 2b 00 00 ...     ← jadx 可读出业务逻辑
② 默认加壳（随机填料）：
   32 4e df 2c a9 cd ff 73 fc 93 a8 d4 d7 c8 9d 6c ...     ← 噪声
③ stringenc（统一 0x0e 填料，另一包）：
   00 0e 00 0e 00 0e 00 0e ...                              ← 整齐 return-void 串
```

### 1.3 stringenc 全量的规模实测（从全模块产物 `简盒_加壳.apk` 提取）

| 项 | 值 |
|---|---|
| 加密字符串位点 | **5,526**（Base64 形态，密文 0.43MB） |
| dex 字符串总数 | 30,645 → 40,844（密文替换+膨胀） |
| dex 体积 | 7.13MB → 8.08MB（Base64 +33% 膨胀 + antidiff 噪声） |

### 1.4 每次执行的成本构成（读 `StrDec.java` 确认，**无缓存**）

```
每次 const-string 使用点执行 ≈ 1-3μs，构成：
  android.util.Base64.decode + 2 次堆分配 + new String(UTF-8)   ← ~90%（结构成本）
  splitmix64 密钥流算术                                          ← ~5%（S2 已优化到纳秒级）
```

乘数效应：Compose 启动路径 + 重组会**反复执行**同一使用点（估均值 ~20 次），
5,526 位点 × ~20 次 × 1-3μs ≈ **200ms 量级**，与实测 +232ms 吻合。
分配 churn 同时解释 PSS 增量的一部分（年轻代压力）。

> **历史前科**：v1 方案（每条 SHA-256 派生 + intern + 查表）曾让「1.3 万条字符串把
> 冷启动首帧卡死」。S2 只优化了**密钥生产**（纳秒级现算），每执行的固定成本
> （Base64+分配+String 构造）原样保留——本次定位的正是这部分。

## 二、病根

**解密挂在「每次执行」上，而不是「每类一次」。**

原生 `const-string` 的成本模型：字符串 intern 一次，之后每次使用 = 一条
quickened 指令、零分配。S2 的改写把这条指令换成了「函数调用 + 解码链 + 分配」，
且没有任何记忆——同一条字符串每执行一次就完整重做一遍。

因此：**换算法（XOR 花样）不解决问题**——算术只占 ~5%。解法是改结构。

## 三、L1：解密桩缓存（立即可做，收益 ~90%）

### 3.1 改动（仅 `StrDec.java`，~10 行）

```java
private static final java.util.concurrent.ConcurrentHashMap<String, String> CACHE
        = new java.util.concurrent.ConcurrentHashMap<>();

public static String d(String payload) {
    String hit = CACHE.get(payload);          // 命中：~50-100ns，0 分配，无调用链深钻
    if (hit != null) return hit;
    String out = /* 原有 Base64 + XOR + UTF-8 解密 */;
    CACHE.put(payload, out);
    return out;                               // 返回共享实例，顺带恢复 intern 语义
}
```

使用点 smali **一个字节不变**。

### 3.2 设计边界

| 项 | 决策 |
|---|---|
| 线程安全 | `ConcurrentHashMap`（Compose 重组多线程并发调 `d()`） |
| 内存上界 | 5,526 条 ≈ 1-2MB（key+value+entry），远小于现状的分配 churn；可加上限（如 3 万条）防极端 |
| 失败语义 | 不变：解密失败原样返回（失败结果**不进缓存**，避免把毒缓存住） |
| 与 `intern` 的关系 | 缓存命中返回同一实例，恢复原生 const-string 的同一性；若业务存在 `==` 比较字符串的路径（R8 后罕见），此改动**修复**而非破坏 |

### 3.3 预期

冷启动税 ~200ms → **~15-25ms**（5,526 条首次解密一次性成本 + 重复执行查表）。

> **⚠️ 实测修正（2026-10-12 真机验收）**：上述预期**未发生**——缓存生效（产物三重验证 + CPU 小幅改善 + PSS -26MB + intern 恢复）但冷启动持平 ~427ms。原"位点 × 重组 ~20 次"的乘数假设高估约一个数量级：真机冷启动期间大部分使用点仅执行 1~2 次，stringenc 实际成本 ≈ 10-20ms 量级（从 v1 事故的 debuggable 解释执行场景外推到 release+JIT 所致）。**L1 保留**（无回归 + CPU/PSS 改善 + intern 语义 + 重组密集场景仍有价值）；L2 的前提（stringenc 占大头）消失，缓行。

## 四、L2：解密前移到 `<clinit>` + 类级静态表（结构终态）

### 4.1 原理

把解密从「使用点的调用」搬进「类初始化的一次性填表」，使用点退化为普通数组读。

```smali
# ── 改造后的使用点（业务方法里，任意次执行都是这三条）──
sget-object   vX, Lcom/nc/strdec/StrDec;->T:[Ljava/lang/String;
const/16      v1, 0x2a3b                                   # 构建期分配的槽位号
aget-object   vX, vX, v1
# 无调用、无解码、无分配——成本回到原生 const-string 级别

# ── 注入到该类 <clinit> 的解密块（每类只跑一次）──
const/16      v0, 0x2a3b
const-string  v1, "QzgzZmRm..."                           # 密文从使用点挪来（表总量不变）
const-string  v2, "eW91clN0cmluZw==..."
invoke-static {v0, v1, v2}, Lcom/nc/strdec/StrDec;->fill(I, [Ljava/lang/String;)V
```

```java
// StrDec 新增
public static final String[] T = new String[TOTAL_SLOTS];   // 构建期写入槽位总数

public static void fill(int first, String[] payloads) {
    for (int i = 0; i < payloads.length; i++) {
        try { T[first + i] = decryptOne(payloads[i]); }
        catch (Throwable t) { T[first + i] = ""; }   // 逐条兜底：绝不让 clinit 炸掉整个类
    }
}
```

### 4.2 为什么「槽位在使用前一定已填」——语言规范兜底

JVM/ART 语义：**类初始化（`<clinit>`）先于该类任何静态字段读取、实例创建与方法执行**。
所以「本类的表在本类使用点前就绪」由规范保证，不依赖任何时序技巧。
（注意：这要求每类的 clinit 填**本类自己的槽位**；跨类引用不存在。）

### 4.3 成本与体积

| 维度 | L1 | L2 |
|---|---|---|
| 每使用点 | ~50-100ns（调用+查表） | ~10-30ns（sget+const+aget，无调用） |
| 冷启动税 | ~15-25ms | ~5-15ms（仅已加载类的 clinit 一次性解密） |
| 体积 | 不变 | ±几 KB：密文从使用点**挪进** clinit（表总量不变）；使用点指令省 2-3 unit × 5,526 ≈ -15KB；clinit 注入 +几 KB |

### 4.4 实施决策点（做之前必须拍板）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 表位置：类级 `static String[]` 字段（推荐）vs 全局大表 | 类级：索引无需全局协调（构建顺序即槽位序）、未加载类零成本 |
| 2 | 失败兜底 | batch 内**逐条** try/catch，失败填 `""`；clinit 绝不抛（否则 ExceptionInInitializerError = 整类不可用） |
| 3 | 模块顺序 | 沿用现状：R8 之后跑 ✓；**跳过已被 dex2c 清空方法体的类**（其字符串引用已不在） |
| 4 | 硬排除清单 | 沿用（androidx/kotlin/反射依赖库 + 解密桩自身） |
| 5 | 边界类 | 接口/注解/enum 的 clinit 形态特殊——**首版跳过**（其字符串不加密），按「报错 N」节奏逐类补 |
| 6 | 幂等 | 沿用 `# nc-strdec-encrypted` 标记机制；clinit 注入需自己的幂等标记 |
| 7 | 多 dex | 跨 dex 引用 StrDec 合法（主 dex 的桩类）；各 dex 的类各自注入各自 clinit |

### 4.5 风险面

主要风险 = **clinit 注入的类边界**（畸形类、无 clinit 类、enum 常量表）。
仓库已具备 smali 手术能力（`scripts/inject/inject-loadlib.py`、javacheck 方法注入、
变换 D 寄存器改写），但按仓库纪律需逐类真机回填（「报错 N」流程）。

## 五、L3：密文移出 dex 字符串表（预告，缓行）

密文不再以 Base64 字符串放 dex 表，改存**单个二进制 blob**（raw XOR，无 Base64 的
+33% 膨胀）：dex 预计缩 ~0.4-0.5MB，且 `strings` 扫描连「大量 Base64 文本」这一
stringenc 指纹都消失。

**缓行原因（硬骨头）**：clinit 读取 blob 需要 I/O，而 clinit 可能运行在 Context
可用之前。候选解法均不轻量：
- blob 塞进 dex 的 `fill-array-data`（0.43MB 需按 32KB 上限切块，十几个数组拼接，丑）；
- 无 Context 读自身 APK（`/proc` 路径探测，native 已有先例，Java 侧时序风险）。

待 L2 落地稳定后再评估。

## 六、算法要不要换？（三方案分析）

背景：另一侧提出 ①纯异或+字节模式 ②可插拔轻量算法+每站点独立密钥 ③极简固定密钥异或。

**前提事实**：算术仅占每次解密成本的 ~5%（§1.4）。L1/L2 落地后算术被缓存/表格吸收，
三种算法的运行期差异**不可测量**。因此选择标准只剩：实现复杂度、体积、抗逆向。

| | ① 纯异或+字节模式 | ② 可插拔+每站点密钥 | ③ 极简固定密钥 |
|---|---|---|---|
| 性能（配 L1/L2） | ≈ | ≈ | ≈ |
| 体积 | 持平 | **变差**（5,526 份密钥材料入 dex） | 持平，桩最小 |
| 复杂度 | 中（「字节模式」含义待澄清 ⚠️） | **最高**（抽象层+密钥管理+对拍面扩大） | **最低** |
| 抗逆向 | **三者等价**：桩类在 dex 里，jadx 可读出算法与钥匙来源；异或的经典弱点（已知明文 → 密钥暴露）对三者同样成立。文档既定定位是「防静态可见性，非密码学安全」 | | |

**结论**：
- **② 否决**——给「防 strings 扫描」定位的方案加可插拔抽象与站点密钥，是拿体积和复杂度买不存在的安全性。
- **③ 可选**——最简单、桩最小、维护最省；属于「顺路简化」，不是性能需要。
- **① 待澄清**——若「字节模式」指「密文移出字符串表改存字节块」，即本文件 L3，应作为独立提案评估（有额外体积收益）；若仅指 XOR 逐字节循环，则与 ③ 同物。

**无论选哪种算法，L1/L2 的结构改造都是前置条件**——换算法本身不构成性能优化。
