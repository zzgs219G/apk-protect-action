🔴 新问题 1：StrDec 桩自身会被改，名单漏项

v2 §7 硬排除名单列了 Manifest 组件 / R / $r8$ / 反射类 / native 类，但没有解密桩 com.nc.strdec.StrDec。

同时 §5.5 说"名单直接复用 anti-diff.py 的 SKIP_CLASS_PREFIXES"——查了，anti-diff 的名单也没有 com.nc.。而 anti-diff 不需要它（它不改字段名），light-obf 需要。

后果：用户规则写 ** 时，light-obf 会去改 private static final long GAMMA 和 SEED → 桩的解密引用全断 → 全包字符串乱码，而且是静默的（stub 里 SEED 引用还在，但值读不到了）。

修：EXTRA_SKIP_PREFIXES 必须显式包含 'com.nc.'（桩包），且在 §7 名单里写出来，不能只藏在"复用 anti-diff"一句话里。stringenc 那边是靠 classify() 单独返回 'stub' 兜底的——light-obf 也要有同型兜底。

🔴 新问题 2：const/16 ⇄ const-wide/16 不等价

§4 变换 A 举例：

同一指令、仅换立即数编码（如 const/16 改 const-wide/16 类的等值重编码……

const/16 产生 int，const-wide/16 产生 long。类型不同，语义不等价。 下游任何 int-to-long / 算术都会因为源类型变了而结果不同，或者被 verifier 拒（寄存器类型推断）。

对照：add-int/lit8 ⇄ add-int/lit16 是真等价的（都是 int，22s 格式，只是立即数范围不同）——但文档给的例子恰好是最错的那个。

修：删掉 const/16→const-wide/16 这个例子，只保留 lit8/lit16 同语义变体；同时明确"变体池只放类型一致、位宽可容纳的指令"。

🔴 新问题 3：变换 B 的"零新寄存器形态"数学上不成立

§4 变换 B 的保底形态：

const/16 v0, 0xC8 + add-int/2addr v0, v1_orig，其中 v1_orig 是原指令已在用、插入点处值已死的寄存器；找不到就整处放弃

问题：v1_orig 是已死寄存器——意味着它的当前值是未定义的垃圾（死 = 后面不再读，但之前写没写过不知道）。拿它去 add-int/2addr v0, v1_orig，等于 v0 += 垃圾，结果不是原常量。

"已死寄存器"在数据流术语里是"此后无读"，不是"此时值已知"。用它做运算 = 读未定义值 = 语义破坏（这正是报错三十二"读未初始化寄存器"的同型错误）。

要拆 700 成 500+200，必须有第二个已知为 200 的操作数——这就要新寄存器或复用值确定的寄存器。不存在真正"零新寄存器"的拆解形态。

修：删掉这个"保底形态"。变换 B 要么走"复用值已确定的现有寄存器"（罕见），要么走 .locals 提升（受红线 7 约束），要么放弃该处。不要为覆盖率硬造一个错的形态。

🟠 未彻底解决：--clean 与变换 B/A 的幂等冲突

§5.1 说 clean"只清标记行 + 未进 dex 的注入物"。

但变换 B/A 是改了 dex 内容的（指令已经写进 smali 文本）。clean 后：

· 标记没了
· B/A 的指令还在 smali 里
· 重跑时会被当"未处理类"再处理一遍

再处理的后果：变换 B 对已经是"500+200"的常量链再拆一次（变 500+120+80），变换 A 对已经 sub-int v0,v1,neg(v2) 再反转……幂等破坏，且产物会逐轮膨胀。

反过来说，如果 clean 不清理 B/A，那 clean 的语义就是"清一半"——用户以为回滚了，实际上没有。

修：两条路线二选一，文档必须明写：

· (a) clean 只清标记，B/A 变更不回滚 → 那么 clean 后必须禁止重跑（或重跑必须从 fresh unpack 开始），CLI 要 fail-fast 检查"smali 里有 B/A 形态但无标记"；或
· (b) clean 完全不做 B/A 恢复 → 文档直接说明"clean 仅用于撤销 D（可逆的改名，靠 --map 反查），B/A 不可逆，回滚靠重新解包"

推荐 (b)，因为 B/A 本质不可逆。但无论如何，当前文档的表述会让用户以为 clean 是完整回滚，这是危险承诺。

🟡 小问题（不影响架构，但会拖慢排障）

1. §9.4 哨兵路径写成 /storage/emulated/0/n —— 实际是 /storage/emulated/0/xixin_debug。文档自己在 §10 里说"评审写的 xixin_debug 是旧名"，然后自己又写了个错的 /n。笔误。
2. §8.1 / §8.6 挂错了位置 —— 它们出现在 §9 底下，但内容是"变换 D 的对象判定依据 / 合成符号清单"，应该是 §7（硬排除）的子节。文档结构乱。
3. **改名时 access$ 桥体内的引用没显式说明** —— §4 变换 D 说"改两类位置：声明 + 方法体内引用"，OK；但 §8.6 说不改 access$ 名，这里要补一句"access$ 体内的对 private 名的调用点仍要跟着改"（它也是方法体，字面已覆盖，但读者容易误解）。
4. §6 阶段 2 的"寄存器断言"没说怎么实现 —— "模拟 verifier 语义逐条检查写目标"是难点（_check_stub_registers 只对单一方法、单一白名单形态工作）。全方法数据流模拟要么用 androguard 读回，要么自己写保守的"读前必有写"检查。文档应指明用哪条路。
5. 红线 7 的公式容易误读 —— "4 + 参数槽总数 - 1 > 15 硬门槛"是判定越界的条件，即"越界就拒绝"。但写"必须过 xxx 门槛"容易被读成"必须满足 xxx"。建议写"允许提升的条件：4 + 槽总数 - 1 ≤ 15"。
