
二、你需要自己核实的事实

1. 定位"跳过"逻辑

在 encrypt-strings.py 里找到字段处理分支，确认：

· 什么条件下字段被跳过（保留原样，不去初值）？
· 跳过的字段是否参与 hits 计数？

2. 定位"断言"逻辑

找到构建期断言相关代码，确认：

· 断言的扫描范围是什么？（全包？还是"加密面"？）
· "加密面"的判定条件是什么？
· 断言的判定正则具体匹配什么？

3. 核实冲突链

把上面两条逻辑放在一起，验证推断是否成立：

· 被跳过的字段保留了明文初值
· 同类其他字段处理成功 → 类被打标记
· 断言扫描到"有标记的类里有明文 String 字段" → 误报

4. 核实"空串跳过"的必要性

找到跳过逻辑的注释，确认：

· 为什么空串不能加密？
· 为什么跳过时不能简单地去初值？（去初值后 <clinit> 不赋值，运行期读到 null，语义变了）

这一步必须自己读代码确认，不许照抄本计划书的任何推测。

三、修复方向（至少评估两种，自己选）

方向 A：让断言"知道"跳过规则

· 给跳过的字段行加一个可识别标记
· 断言的判定排除这些被标记的行
· 风险：动断言 = 动防线。要确认"真漏改"仍然能被拦

方向 B：跳过的字段也统一处理

· 空串也走"去初值 + <clinit> 回填"
· 回填的是显式构造的空串，不是 null
· 好处：加密面内不再有例外，断言无需改动
· 风险：要验证 <clinit> 回填空串的语义正确性

方向 C：缩小"加密面"判定范围

· 断言只扫"真正被改写的字段"，而不是"文件里有标记就全扫"
· 风险：需要精确追踪"哪些字段被改了"，实现复杂

自己评估并选择。 评估维度：改动量、风险、对报错二十四/二十七防线的影响、是否引入新例外。
