## 报错三十三(2026-09-17):变换 D 寄存器重编号——4-bit 编码上限与 /range 连续性约束(回编期拦截)

### 背景
用户反馈"当前防对比强度不够"(37 方法仅 17 个有差异,MT 式归一化对比可
过滤掉全部噪声)。选定增强路线:变换 D——方法内局部寄存器随机置换,
让每条指令的寄存器号在 dex 层真实变化,规则归一化无法抹平。

### 现象(首次重放,回编期连续暴露三个设计缺口)
1. `Invalid register: v26. Must be between v0 and v15`:35c invoke 等
   4-bit 指令的寄存器槽只 4 位,置换把 v3 → v26 后编码不下;
2. `Invalid register count: -13`:/range 指令要求寄存器连续升序,
   置换把 `{v31 .. v17}` 打乱成降序;
3. 覆盖盲区:37 方法中 20 个是 `.locals 0/1`(R8 产物,几乎无局部
   寄存器),D 与 C 都无法命中——覆盖率天花板 17/37。

### 根因
初始设计只考虑了"寄存器语义等价"(读/写同步替换、wide 对不拆),漏了
**编码层约束**:dalvik 指令有多套寄存器寻址宽度(4-bit/8-bit/16-bit),
置换后寄存器必须仍落在所用指令形态的编码范围内;`/range` 还有连续性
约束。且真实包中 range 区间两两大量重叠(单文件 31 区间 60+ 处重叠),
"区间整体互换"不可行。

### 修复(scripts/anti-diff/anti-diff.py)
1. `_collect_low_reg_set`:非 /16、非 /range 形态指令的寄存器归入
   "低域"(v0..v15);置换分低/高两个独立域,永不跨域(报错三十三);
2. `_collect_range_blocks`:/range 区间成员**全部锁定不动**,只置换
   区间外寄存器(报错三十三之二;宁缺勿滥,与 wide 对重叠的对也锁);
3. `_bump_locals`:`.locals N<4` 提升到 4(smali pN 是虚拟名,汇编时
   自动重映射,参数语义不变),让 C/D 覆盖此前 54% 的盲区方法;
4. `_permute_registers`:wide 对作整体单元、跨 16 位边界的 wide 对
   放弃置换;pN 参数区永不参与;恒等置换跳过。

### 验证
- 回编成功(报错 1/2 消失);androguard 读回 dex 解析 OK,自赋值 move=0;
- 语义等价:37/37 方法在 C/E 归一化后指令骨架子序列对齐零破坏;
- wide 对消费链完整(move-result-wide 的值均被后续指令消费);
- normdiff.py 归一化对比:**37/37 方法有差异**(增强前 17/37),
  覆盖率 46% → 100%;
- 冒烟测试全绿(含幂等)。

### 教训
寄存器重编号的约束空间比"语义等价"大得多:**语义合法 ≠ 编码合法**。
dalvik 的多宽度寻址(4/8/16-bit)与 /range 连续性是汇编器层的硬约束,
必须在设计期枚举;真实包的 range 区间重叠密度决定了"锁定"是唯一稳妥
策略。覆盖率短板常常不在算法,而在目标方法的形态分布(.locals 0/1 占
一半)——先量测形态分布,再决定门槛是否可以"创造条件"(如 _bump_locals)
而不是直接放弃。

## 报错三十四(2026-09-17):变换 C0 `_bump_locals` 参数平移越界——13 参数槽方法提升 .locals 后回编炸 `Invalid register: v16`

### 现象
CI 流水线回编阶段(`docs/build.log`)在 `smali_classes11/com/xixin/box/data/local/
TaskEntity.smali[807,4]` 报:

```
Invalid register: v16. Must be between v0 and v15, inclusive.
brut.androlib.AndrolibException: Could not smali file ...
```

anti-diff 已完成(7139 类 / 231555 处改动),失败发生在回编,是**编码期**错误
而非语义错误。

### 根因
变换 C0(`_bump_locals`,报错三十三引入)把 `.locals N<4` 提升到 4。smali 的
pN 是虚拟参数名,汇编器按 `.locals N` 把参数平移到 `v(N + 槽偏移)`——提升 0→4
即所有参数物理号整体 +4。

`TaskEntity.copy$default` 是 static 方法,参数槽总数 13(12 个参数 + 1 个
`J` wide 占 2 槽):原 `.locals 0` 时 p12=v12 合法;提升后 p12=**v16**,而
`and-int/lit16`(22b)、`if-eqz`(21t)等指令的寄存器槽是 4-bit 编码(上限
v15)→ 汇编器直接拒绝。旧代码只检查 `.registers` 与 N≥4,**完全没有参数
寄存器数上限**这个维度——参数多的方法天然踩雷。

最小复现:抽取 copy$default 方法体(替换类名),用 apktool jar 内 SmaliBuilder
汇编,精确复现 `[59,4] Invalid register: v16`。

### 修复
`scripts/anti-diff/anti-diff.py`:
1. 新增 `_count_param_slots(method_sig)`:逐字符解析 `.method` 签名参数列表,
   数**槽**而不是参数个数——`J`/`D` 占 2 槽,数组 `[X` 按元素 1 槽,非 static
   方法 `this` 占 1 槽;
2. 新增 `_max_param_index(method_lines)`:方法体实际引用的最大 pN 序号,
   作签名解析的双保险兜底;
3. `_bump_locals` 增加硬门槛:`4 + 槽总数 - 1 > 15` 一律不提升;签名解析
   失败(`None`)也跳过。宁缺勿滥,与报错三十三"range 成员全锁"同一策略。

### 验证
- 真实包(简盒 21 dex)端到端:anti-diff 处理 7140 类 → apktool b 回编
  exit 0,产物 20980592 字节(修复前同一目录必炸);
- 定向:copy$default 形态(13 槽)保持 `.locals 0` 不提升,汇编 ok=true;
  7 槽方法正常提升 0→4(覆盖率不回退),汇编 ok=true;
- `tests/test-smoke.sh` 新增断言 4c2(双向钉死:多参数槽不提升 + 少参数槽
  仍提升),修复前红、修复后绿,冒烟全绿含幂等。

### 教训
报错三十三刚钉死"置换"侧的 4-bit 约束,这次在同一条编码约束上从"平移"侧
再次踩坑:**.locals 提升不是免费午餐,参数区整体平移的合法性受
`4 + max_param_phys ≤ 16` 硬顶约束**。凡是对寄存器号做算术的变换,都必须
同时回答:变换后的每个寄存器引用,在它所在指令的**具体编码格式**下还合法吗?
另外:wide 参数(`J`/`D`)占 2 槽,按参数"个数"统计永远是错的,必须按槽。

## 报错三十五(2026-09-17):anti-diff 产物 app 闪退(续)——变换 D 的 wide 寄存器对被拆散 → ART verifier 读未定义寄存器

**现象**(用户提供 `docs/对比测试/简盒闪退包.apk`(21618278 B)与 `简盒-原包.apk`
(29761126 B),实测:MT 对比"忽略编译优化/寄存器数量/调试信息/nop"后可见大量
修改项(变换生效),但 **app 闪退**。用户质疑"上一任 AI 没解决吗"——报错三十二
只修了变换 C 的 `move v,v`,变换 D 的同类缺陷仍在)。

**两包同源确认**(排除包体差异):条目数均 450、dex 均 21 个;
`AndroidManifest.xml` 二进制完全一致;`resources.arsc` 一致;lib/ 3 个 so、
assets/ 20 项内容全一致;dex 版本头两包全为 **038**(排除报错十八式回编降级)。
全 21 dex 寄存器越界检查、分支目标合法性检查(注意 `get_ref_off()` 单位是
code units,须 ×2 换算字节)、try/catch 起点边界检查:两包**均 0** 异常。

**dex 层实证**(androguard 读回,verifier 式"读前未定义寄存器"扫描):
原包 1 处 vs 闪退包 **94 处**(差分 93 处全部指向闪退包独有形态)。

**逐指令对照实锤**(`DownloadManagerViewModel$loadApksFromStorage-IoAF18A$$inlined$sortedByDescending$1.compare`):

```
原包:   move-result-wide v2                              ← 写宽对 (v2,v3)
        invoke-static {v2, v3}, Long;->valueOf(J)        ← 读 (v2,v3) 连续 ✔
闪退包: move-result-wide v1                              ← 只写 (v1,v2)
        invoke-static {v1, v4}, Long;->valueOf(J)        ← 读 (v1,v4) 断裂 ✘
```

`move-result-wide` 的结果只写了 `(v1,v2)`,读端却读 `(v1,v4)`——高半 v4 从未被
写入 → ART verifier 判定读未定义寄存器 → VerifyError 秒闪退。

**根因**(变换 D 的 wide 对保护有三处同源漏洞,`_collect_wide_pairs` 全部漏登记):
1. `_WIDE_INS_RE` 缺 `move-result-wide`——它与 `move-wide` **前缀不同**不被覆盖,
   整条指令被无视,其目标宽对完全裸奔;同样漏了 `cmpg-double`/`cmpl-double`;
2. `_collect_wide_pairs` 只取每条指令的 `regs[0]`,因此 `add-long v4, v0, v2`
   的两个 **src 宽对** `(0,1)`/`(2,3)` 全漏;
3. `invoke` 传入的 wide 参数对(如 `invoke-static {v8, v9}, Math;->pow(DD)D`)
   完全未保护——变换 D 只逐 token 替换寄存器号,不识别 invoke 的槽排列。

漏保护的宽对被 `_permute_registers` 当普通 single 单元独立置换 → 64 位值高低半
被拆到不相邻寄存器。**与报错三十二同型**:smali 汇编器宽容放行(smali 层完全
合法,回编 exit 0)≠ dex 产物合法。原包全量模拟变换 D 实证:wide 对拆散
**19674 处 / 4222 个方法**(另有数千处 invoke 传入的 wide 参数对被拆散)。

**修复**(`scripts/anti-diff/anti-diff.py`,非冻结):
1. `_WIDE_INS_RE` 补 `move-result-wide`/`cmpg-double`/`cmpl-double`;
2. 新增 `_wide_operand_bases(name, regs)`:按指令语义取出**全部** 64 位操作数
   基址(含 dst 与所有 src,区分 `/2addr`、`return-wide`、`cmp-*` 等形态),
   `_collect_wide_pairs` 改用它(不再只取 `regs[0]`);
3. 新增 `_param_slot_list(desc)` + `_collect_invoke_wide_pairs(line)`:解析
   invoke 的参数描述符为**槽列表**(J/D 占 2 槽),按槽顺序定位寄存器列表里的
   wide 对;非 static 跳过 receiver;`/range` 形态由 `_collect_range_blocks`
   整体锁定故跳过;描述符含空格(baksmali 产物 `(Ljava/lang/String; J)`)必须
   跳过;token 匹配须保留 `pN` 占位(丢 pN 会错位产出非连续假对);
4. 稳健性:`max_used` 上界纳入宽对成员(高端寄存器可能从未在文本出现,如
   `const-wide v2` 只写 v2);宽对之间共享寄存器时涉及寄存器全部锁定不置换
   (宁可不置换,绝不可拆散)。

**验证**:
- 权威不变量(用生产 `_collect_wide_pairs` 认定的宽对 + 导出的 mapping 判定):
  原包 **22162 个发生置换的方法上 0 拆散 / 0 受影响**;修复前同口径
  19674 处 / 4222 方法;
- 旧代码黑盒对照:同一 `move-result-wide v2 + invoke {v2,v3}` 最小方法,80 个
  种子中宽对 `(2,3)` 被拆散 **68 次**;修复后 **0 次**;
- 闪退根因方法复核:原包该方法宽对 `(2,3)`/`(3,4)` 重叠,修复版正确锁定跳过
  (`changed=False`),不再产出闪退包的 `move-result-wide v1` + `invoke {v1,v4}`;
- `scripts/anti-diff/tests/test-smoke.sh` 新增断言 8(①收集器覆盖三类旧漏洞
  形态 ②黑盒行对齐断言置换后宽对仍整体移动,78 个种子),修复前红、修复后绿,
  冒烟全绿含幂等与确定性。

**教训**:报错三十二只论证了"垃圾指令池"的读方向安全,漏掉了"寄存器置换"的
**宽对完整性**维度——这是同一类错误的第二次发作(同一条"smali 合法 ≠ dex 可
校验"的教训)。凡是对寄存器号做**算术/置换**的变换,都必须同时回答:被置换的
单元边界在哪里?**wide(64 位)值的两个寄存器是不可拆的整体**,无论它出现在
dst、src 还是 invoke 的寄存器列表里;而 invoke 的槽排列必须靠**被调方法签名**
反推,不能只看寄存器编号。回归验证除回编外必须做 dex 层读回 + 数据流(读前
定义)检查——这也是本次唯一能区分原包(1 处)与闪退包(94 处)的判据。
