# 字符串加密 v2 重构方案(交接文档 · 给下一代 AI)

> **用途**:本文是「本工具字符串加密卡启动」问题的**完整排查总结 + 重构设计 + 执行计划**。
> **本轮任务边界**:出文档。**代码未实施收口**(仓库现处半成品状态,详见 §6),接手者按 §8 执行。
> **一句话**:把解密从「运行期 SHA-256 派生密钥」改为「运行期纯 XOR + 种子现算密钥流(S2)」,做到比第三方更轻。

---

## 1. 背景

### 1.1 现象
- 用本工具加密的 APK(规则 `com.xixin.box.*`,产物 `简盒_signed_08_15_29_sign.apk`)安装后**卡在系统启动页**,无法进入,logcat 无 FATAL。
- 第三方工具(全量规则)加密的同款 APK **正常**。
- 两个 APK 均 `android:debuggable="true"`,minSdk 26 / targetSdk 37。

### 1.2 根因结论(已定案)
**不是加密错,是解密太慢,把启动首帧卡死了。**

排查证据:
| 排查项 | 结果 |
|---|---|
| 13015 条密文逐条解密 | **100% 成功,0 失败** |
| idx 唯一性 | 无重复,无 keystream 复用 |
| 桩 `StrDec` 完整性 | 类存在、加载顺序正确、寄存器修复生效 |
| `<clinit>` 字段回填链 | 34 个回填目标全部存在 |
| 第三方实际加密范围 | **10273 个类**(含 androidx/kotlin),比本工具 874 类多 12 倍,却正常 → 排除"规则/范围" |

真因链条:
1. **v1 单条解密成本高**:`Base64.decode` + 每条按 32 字节分块算 `SHA-256`(每块 5 次 `MessageDigest.update` + 1 次 `digest`)+ `new String` + `intern()` + `ConcurrentHashMap` 缓存查表;
2. **全包量级**:13015 条密文 ≈ **23733 次 digest + 约 11.9 万次 update**;
3. **放大器**:`debuggable=true` → ART 全程**解释执行**,JIT/AOT 不优化,同代码慢 10~50 倍;
4. 启动关键路径(Compose 首帧 + `Application`/`MainActivity`)的解密风暴串行阻塞首帧 → 表现为"停留在系统启动页",不是崩溃;
5. 第三方方案:每类自带 `short[]` 表 + 一个 `$()` 方法,解密 = 纯数组 XOR(纳秒级),故无感。

### 1.3 次要发现(非根因,建议顺手处理)
- 本工具加密了 **24 个枚举类的 name 字段**(如 `SYSTEM`/`LIGHT`/`DARK`),第三方保留明文。实测解密后值正确、`valueOf` 不挂,属"不必加密的结构性字符串"。建议把"`<clinit>` 传给 `Enum.<init>` 的 name 参数"列入跳过名单。

## 2. 目标与验收标准

### 2.1 目标
1. **运行期解密降到纳秒级**(纯算术 XOR,无 SHA-256 / 无 intern / 无缓存查表),消除启动卡顿;
2. **可维护**:算法只改 Java 源码(`StrDec.java`),smali 由编译链自动生成,**人永不手写 smali**;
3. **比第三方更轻**:全包仅 **1 个解密方法**、**0 张表**(只有 1 个 8 字节种子),方法数与体积都最小。

### 2.2 验收标准
| 编号 | 标准 | 验证方式 |
|---|---|---|
| A1 | 对拍:构建期加密 ↔ Java 解密 **逐字节一致** | 离线脚本(空串/ASCII/中文+emoji/最长 5188B) |
| A2 | 幂等:同输入重跑产物 md5 稳定 | 离线重跑对比 |
| A3 | 续跑:复用已有桩时 offset 不重叠、旧密文可解 | 离线构造两次运行 |
| A4 | 结构:产物 dex 无 FIELD 型(0x19)static_value(报错二十四) | 汇编产物 + dex 读回断言 |
| A5 | 回归:规则解析/硬排除/多 dex/组件清理保持 | 现有冒烟 |
| A6 | 端到端:产物能进入主界面、首帧正常 | **需真机安装验证**(执行者需自备设备/交给用户) |

## 3. 算法设计(定稿:S2)

### 3.1 新旧对比
| 维度 | v1(现状) | **v2/S2(目标)** | 第三方 |
|---|---|---|---|
| 密钥来源 | 运行期 `SHA-256(salt‖idx‖block)` | **运行期 splitmix64 现算** | 每类一张 `short[]` |
| 密文形态 | `Base64(idx_be24 ‖ cipher)` | `Base64(offset_be24 ‖ cipher)` | 类内数组 |
| 桩内数据 | `SALT` + `DIGEST` + `CACHE` | **仅 1 个 `long SEED`** | 每类一张表 |
| 运行期解密 | Base64 + N×SHA-256 + intern + 缓存 | **Base64 + 纯 XOR** | XOR |
| 解密方法数 | 1 | **1** | 每类 1 个 `$()` |
| 密钥表/种子 | 16B salt | **8B seed(零表)** | 每类 1 张表 |

> **"比第三方更轻"的落点**:第三方每类塞一张表;本方案连表都不要,只有一个 8 字节种子——
> 第三方省不掉的表,本方案直接不存在。

### 3.2 数据布局
- `seed`:8 字节随机(`secrets.token_bytes(8)`;`--seed-hex` 供复现);
- **密钥流**(splitmix64,双端逐字节一致,见 §3.3):第 `i` 个字节 = `key_byte(seed, i)`;
- 全包按顺序为每条密文分配**不重叠**区段 `[offset, offset+len)`;
- `payload = Base64( offset_be24 ‖ (plain_utf8[k] ⊕ key_byte(seed, offset+k)) )`;
- 桩运行期:`Base64.decode` → 取 offset → `plain[k] = raw[3+k] ^ key_byte(seed, offset+k)` → `new String(plain, "UTF-8")`。

### 3.3 splitmix64 双端精确定义(必须逐字节一致)
**构建期(Python)**:
```python
MASK64 = (1 << 64) - 1
GAMMA  = 0x9E3779B97F4A7C15
M1     = 0xBF58476D1CE4E5B9
M2     = 0x94D049BB133111EB

def _mix(z):
    z = (z ^ (z >> 30)) & MASK64
    z = (z * M1) & MASK64
    z = (z ^ (z >> 27)) & MASK64
    z = (z * M2) & MASK64
    return (z ^ (z >> 31)) & MASK64

def key_byte(seed, i):                       # O(1): 第 i 个字节
    w = _mix((seed + (i >> 3) * GAMMA) & MASK64)
    return (w >> ((i & 7) * 8)) & 0xFF
```
**运行期(Java,桩内)**:
```java
private static final long GAMMA = 0x9E3779B97F4A7C15L;   // 与 Python 同常量

private static long mix64(long z) {          // Java long 溢出 = mod 2^64,天然对齐
    z = (z ^ (z >>> 30)) * 0xBF58476D1CE4E5B9L;
    z = (z ^ (z >>> 27)) * 0x94D049BB133111EBL;
    return z ^ (z >>> 31);
}
private static int keyByte(long seed, long i) {
    long w = mix64(seed + (i >>> 3) * GAMMA);
    return (int) ((w >>> ((i & 7L) * 8)) & 0xFFL);
}
```
**等价性(数学上)**:S2 现算流 == S1「把流前 N 字节预存成表」,完全等价;所以 S2 不损任何正确性。
**已做的离线验证**(本轮,`~/tmp/spm64_check.py`,纯 Python 侧):
```
O(1) 跳跃 == 顺序流: OK
byte_at(seed, 999999) = 0x8b        (取任意位置皆 O(1))
256 桶取值数: 256                    (分布均匀)
表流等价(O(1) 现算 == 预存表): OK
```
> **接手必做**:把上表换成「**Python ↔ Java 双端对拍**」(§8 P3),锁定两处易错点:
> ① Java 用 `>>>`(无符号右移)、`long` 溢出即 mod 2^64;② Python 每步 `& MASK64` 且 `>>` 作用在已掩码的非负数上。

**性能优化余地**(可选,不改变语义):运行期按 64 位块批量展开——每 8 字节算一次 `mix64`,块内用位移取 8 个字节;`offset` 不必 8 对齐,靠 `i>>>3`/`i&7` 天然覆盖。

### 3.4 桩生成流水线(核心变更,对应决策 D2)
```
scripts/string-enc/stub-src/StrDec.java     ← 唯一真相(人可读/可改/可测)
      │ javac -cp android-all.jar
      │ d8  → classes.dex
      │ apktool d → smali
      ▼
scripts/string-enc/stub-src/StrDec.smali    ← 自动产物(人永不手改)
      │ encrypt-strings.py「结构化注入」:写入 SEED 常量 + 字段声明 + <clinit> 回填链
      ▼
注入解包目录 → 重打包
```
**"结构化注入"要求**:`encrypt-strings.py` 以 build-stub.sh 产物为**骨架**,按 smali 结构定位插入点(字段区 / `<clinit>` 的 `return-void` 前),**不再依赖手工模板里的 `%FIELDS%`/`%CLINIT_FILL%` 占位符**。这样"改 Java → 重跑 build-stub.sh"才真正闭环,消除 Java 与 smali 漂移。

### 3.5 必须保留的历史防线(报错二十一/二十二/二十四/二十五教训)
- **报错二十一**:注入用 `invoke-static/range {dst .. dst}`(寄存器宽度 v0–v15 限制),不放宽;
- **报错二十二**:桩内任何**写指令**的目标寄存器**不得落在参数寄存器区间**(构建期断言保留);
- **报错二十四**:字段初值**保持明文字面量**,运行期经 `<clinit>` 回填(禁止 FIELD 型 0x19 static_value,否则 ART 类初始化秒闪退无日志);
- **报错二十五**:占位符**只允许出现在非注释行**;渲染/注入后**残留占位符或类体顶层出现裸指令即 fail-fast**。

## 5. 已发生改动明细(含待修 bug)

### 5.1 `encrypt-strings.py`(v1→v2,方向 S1,需转到 S2)
已落地的 v2 函数:
- `keystream_stream(seed, length)`:SHA-256 级联生成**整条流**(S1 用;S2 下应改为**不预生成**,只留 `key_byte` 式 O(1) 取字节);
- `encrypt_payload_v2(offset, plain, stream)`:生成 `Base64(offset_be24‖cipher)`;
- `process_file(...)`:offset 区段顺序分配(不重叠);
- `write_stub(decompiled_dir, keys_stream, stub_fields)`:读模板→注入 KEYS/字段/回填;
- `max_existing_idx(content)`:续跑时取已用区段末(`offset+len`),避免密钥复用;
- `load_stub_template()` / `_render_stub()` / `_check_stub_registers()`:模板加载 + 三道防线。

**未收口的断点(必须修)**:
- `main()` 里 `write_stub(args.decompiled, salt, all_stub_fields)` 传的是 **16 字节 `salt`**,而 `write_stub` 期望 **密钥流**;S2 下定稿后应统一为「`seed` + `key_byte`」;
- `read_existing_salt()` 复用逻辑:需从桩里读回 `SEED`(而非 `SALT_B64`/`KEYS_B64`);
- 幂等标记 `STUB_GEN_MARK` 已升到 `v2`,但桩模板/产物形态要与之一致。

**S2 落地时的改动方向**:
1. 删除「预生成整条流」的 `keystream_stream`,改为 `key_byte(seed, i)`(§3.3);
2. `encrypt_payload_v2` 内 `cipher[k] = plain[k] ^ key_byte(seed, offset+k)`;
3. 桩不再有 `KEYS`/`KEYS_B64`,只有一个 `SEED`(long);
4. `read_existing_*` 改为读回 `SEED`。

### 5.2 `stub-src/StrDec.java`(需按 S2 重写;内含一个真 bug)
- 现形态为 **S1**(`private static final byte[] KEYS = /*%KEYS_LITERAL%*/null;`),S2 下整段替换为 §3.3 的 `mix64/keyByte` + `d()`;
- **真 bug**:现 `d()` 用 `char[] out` + `(char)(byte^key)` + `new String(char[])` —— `char` 语义是 **Latin-1**,遇到**中文/emoji 等多字节 UTF-8 会乱码**。正确写法:`byte[] out` + `new String(out, "UTF-8")`。**S2 重写时必须一并修掉**;
- `KEYS` 字段若保留 `final`,javac 可能把占位符常量**内联进 `<clinit>` 指令行**(而非字段初值),注入逻辑要按实际形态适配——S2 不再需要字段占位符,天然规避。

### 5.3 `stub-src/StrDec.smali`(手工模板,按 D2 废弃重建)
- 现含手工占位符与「KEYS_B64 → decode」逻辑,**与 build-stub.sh 从 StrDec.java 编译的产物不一致**;
- 按 D2,应由 build-stub.sh 直接产出骨架,`encrypt-strings.py` 结构化注入;此文件届时**重新生成,不再手维**。
