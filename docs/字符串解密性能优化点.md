## 〇、当前实现与成本基线

`d(String)` 解密流程：

```
Base64.decode(payload, NO_WRAP)        ← 系统实现，未自定义
  → 块展开 XOR 主循环                    ← 本文优化对象
  → new String(out, "UTF-8")
```

主循环结构（块展开版）：

```java
byte[] out = new byte[len];
for (int k = 0; k < len; ) {
    long w = mix64(SEED + ((offset + k) >>> 3) * GAMMA);   // 每块一次
    for (int j = (int) ((offset + k) & 7L); j < 8 && k < len; j++, k++) {
        out[k] = (byte) ((raw[k + 3] & 0xFF) ^ (int) ((w >>> (j * 8)) & 0xFFL));
    }
}
```

对比旧版（逐字节 `keyByte(seed, i)`，每字节内部重算 `mix64`）：

| | 旧版（逐字节） | 现版（块展开） |
|---|---|---|
| 每字节方法调用 | 2 次（`keyByte` + `mix64`） | **0 次** |
| 每字节指令数 | 40 条（12 + 15 + 13） | **16 条** |
| 每块额外开销 | — | 13 条 |

**已获得收益**：XOR 段 **3.06×**；若含 Base64 约 **2.4×**（旧 6.9M 条 → 新 2.9M 条）。

> 说明：旧版 56% 的成本是同块密钥被重复重算 8 次的纯浪费，块展开已消除。

## 一、真实指令流（`d()` 主循环，可逐条复查）

命令：

```bash
sed -n '/:cond_1/,/:goto_0/p'  scripts/string-enc/stub-src/StrDec.smali   # 外层块循环
sed -n '/:goto_0/,/goto :goto_0/p' scripts/string-enc/stub-src/StrDec.smali  # 内层字节循环
```

### 外层块循环（每块执行一次，共 13 条）

```smali
:cond_1
if-ge v3, v1, :cond_2                        # 循环条件（每块 1 次）
int-to-long v9, v3                           # ① k → long
add-long/2addr v9, v4                        # ① + offset
ushr-long v11, v9, v6                        # ① >>> 3  得块索引
const-wide v13, -0x61c8864680b583ebL         # ② GAMMA 重载 ← 可优化
mul-long/2addr v11, v13                      # ② * GAMMA
const-wide/high16 v13, 0x5eed000000000000L   # ③ SEED 重载 ← 可优化
add-long/2addr v11, v13                      # ③ + SEED
invoke-static {v11, v12}, …->mix64(J)J       # 密钥流（必需）
move-result-wide v11
const-wide/16 v13, 0x7
and-long/2addr v9, v13                       # ① & 7 得块内起始偏移
long-to-int v9, v9
```

> 说明：`if-ge v3, v1, :cond_2` 在外层循环体顶部——内层退出后跳回 `:cond_1`，故**每块都执行一次**，计入每块路径。

### 内层字节循环（每字节执行一次，共 16 条）

```smali
:goto_0
if-ge v9, v8, :cond_1        # 1. 边界检查 ① j < 8      ← 必需
if-ge v3, v1, :cond_1        # 2. 边界检查 ② k < len    ← 大部分冗余，可优化
add-int/lit8 v10, v3, 0x3    # 3. k + 3
aget-byte v10, v2, v10       # 4. 读 raw[k+3]
and-int/lit16 v10, v10, 0xff # 5. & 0xFF
mul-int/lit8 v13, v9, 0x8    # 6. j * 8
ushr-long v13, v11, v13      # 7. w >>> (j*8)
const-wide/16 v15, 0xff      # 8. 0xFFL 常量重载  ← 可优化
and-long/2addr v13, v15      # 9. & 0xFFL
long-to-int v13, v13         # 10. → int
xor-int/2addr v10, v13       # 11. XOR
int-to-byte v10, v10         # 12. → byte
aput-byte v10, v7, v3        # 13. out[k] = …
add-int/lit8 v9, v9, 0x1     # 14. j++
add-int/lit8 v3, v3, 0x1     # 15. k++
goto :goto_0                 # 16. 回跳
```

## 二、优化点清单

### ✅ 优化 ①：`0xFFL` 常量提出内层循环 —— **已实施并验证（2026-09-12）**

**实施结果**：

| 项 | 值 |
|---|---|
| 改动 | `StrDec.java` 内层循环 **1 行 → 3 行**（含 3 行注释） |
| smali | 227 → **223 行**；内层循环 16 → **15 条** |
| 新 md5 | `a9e8cb2d081fe6edb4a7a15880685c90` |
| 回归 | A1 **288 例全绿** / A2 冒烟全绿 / A3+A4 全绿 |
| 实际收益 | 每字节省 1 条 → 解密操作总量 **−5.67%** |

smali 实际变化（内层循环，`const-wide/16` + `and-long` 消失）：

```diff
- const-wide/16 v15, 0xff        ← 每字节重载 64 位常量（已删除）
- and-long/2addr v13, v15
- long-to-int v13, v13
+ long-to-int v9, v12
+ and-int/lit16 v9, v9, 0xff     ← 立即数形式，不占寄存器
```

**风险与缓解**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 位语义不等价 | 若 `w >>> (j*8)` 的高位未先丢弃，`int` 截断可能改变结果 | 位宽分析：`ushr-long` 后取低 8 位，`long-to-int` 截断保留低 32 位，低 8 位逐位相同 → **等价** |
| 回归覆盖不足 | 若测试未覆盖 `offset%8!=0`，错误可能漏网 | A1 含 `offset = 1/7/9/65535` 非对齐用例，**288 例全绿** |

> ⚠️ **唯一残留风险**：真机 ART 下 `d8` 可能对两种写法产出不同优化（如 JIT 常量提升），实际加速比可能与静态预估不同。本环境无法实测（`dalvikvm` 链接失败）。
>
> **回滚方式**：`git checkout -- scripts/string-enc/stub-src/StrDec.java && bash scripts/string-enc/build-stub.sh`

#### 原始分析（保留供参考）

**问题**：第 8 条 `const-wide/16 v15, 0xff` 每字节都重新加载 64 位常量。解释执行下 `const-wide` 属较贵指令（常量池取指 + 写 2 个寄存器）。

**改法**（只改 `int` 运算写法，不动算法）：

```java
// 现在
out[k] = (byte) ((raw[k + 3] & 0xFF) ^ (int) ((w >>> (j * 8)) & 0xFFL));

// 改成：先截断成 int，再用 int 掩码
int kb = (int) (w >>> (j * 8));
out[k] = (byte) ((raw[k + 3] & 0xFF) ^ (kb & 0xFF));
```

**指令变化**：

```smali
const-wide/16 v15, 0xff    ┐
and-long/2addr v13, v15    ├ 3 条 → 2 条
long-to-int v13, v13       ┘
```
变为
```smali
long-to-int v13, v13       ┐
and-int/lit16 v13, v13, 0xff ┘ 2 条（and-int/lit16 无需常量寄存器）
```

| 项 | 值 |
|---|---|
| 收益 | **1 条 / 字节**（16 → 15） |
| XOR 段加速 | ≈ **1.07×** |
| 整段（含 Base64） | ≈ **1.03×** |
| 风险 | **极低**（纯运算宽度改写，位运算语义等价） |

---

### 🥈 优化 ②：拆分主体/尾部，省掉冗余 `k < len` 检查（收益中等，风险中）

**问题**：内层第 2 条 `if-ge v3, v1, :cond_1`（`k < len`）在**每个字节**都执行，但块展开后**只有最后一个块**可能不足 8 字节。主体段的该检查恒成立，是纯开销。

**改法**：把循环拆成「整块主体」+「尾部收尾」：

```java
int blkEnd = len & ~7;                       // 主体段结束（8 的倍数）
for (int k = 0; k < blkEnd; ) {              // 主体：无需 k < len 检查
    long w = mix64(SEED + ((offset + k) >>> 3) * GAMMA);
    for (int j = (int) ((offset + k) & 7L); j < 8; j++, k++) { … }
}
for (; k < len; ) { …原始带检查逻辑… }        // 尾部：保留检查
```

| 项 | 值 |
|---|---|
| 收益 | ≈ **0.87 条 / 字节**（作用于主体段字节） |
| XOR 段加速 | ≈ **1.06×** |
| 整段 | ≈ **1.02×** |
| 风险 | **中**——引入三段式边界，需保证主体段在 `offset` 非 8 对齐时的取块字节仍正确 |

> ⚠️ **风险警示**：本项目已有先例——块展开时若对齐写错，会**静默解错**部分字符串（`offset % 8 != 0` 时取错密钥字节），且回归测试若覆盖面不足不易发现。拆分循环属同类边界改动，**收益仅 6%，性价比偏低**。

---

### 🥉 优化 ③：`SEED` / `GAMMA` 常量提到块循环外（收益小）

**问题**：外层第 6、8 条每块重载 `GAMMA` 与 `SEED` 两个 `const-wide`（各 2 条指令，共占 4 条）。

**改法**：用 `long` 块基址递增，把乘加换成累加：

```java
long base = SEED + ((offset >>> 3)) * GAMMA;   // 循环外算一次
for (long blk = (offset >>> 3); …; blk++) {
    long w = mix64(base);
    base += GAMMA;                              // 只加不减
    …
}
```

| 项 | 值 |
|---|---|
| 收益 | **2 条 / 块**（每块 13 → 11），摊到每字节 ≈ **0.25 条** |
| XOR 段加速 | ≈ **1.02×** |
| 风险 | 低（但需重算 `offset` 起始块，边界仍要核对） |

> 注：`SEED` 字段值由构建期哨兵注入（`build-stub.sh`，`0x5eed000000000000L`），提出循环外后**仍以字段读取实现**，不受影响。

---

### ❌ 优化 ④：`j * 8` 改移位 —— 无收益

`mul-int/lit8 v13, v9, 0x8` 已是最优形式（d8 不会把它变成 `shl`，因为 `imul` 单周期且已是最短编码）。**不建议改**。

### ❌ 优化 ⑤：`k + 3` 提前算 —— 无收益

`add-int/lit8 v10, v3, 0x3` 即使改用随循环递增的 `rk`，也仍需 1 条 `add-int/lit8` 自增。**净收益 0**。

## 三、汇总

| 优化 | 每字节省 | XOR 段加速 | 整段加速 | 风险 | 建议 |
|---|---|---|---|---|---|
| ① `0xFFL` → `int & 0xFF` | 1 条 | 1.07× | 1.03× | 极低 | ✅ **已实施** |
| ② 拆主体/尾部 | ~0.87 条 | 1.06× | 1.02× | 中 | ⚠️ 不建议 |
| ③ SEED/GAMMA 提循环外 | ~0.25 条 | 1.02× | 1.01× | 低 | 🥉 可选 |
| ④ `j*8` 移位 | 0 | — | — | — | ❌ 不做 |
| ⑤ `k+3` 提前 | 0 | — | — | — | ❌ 不做 |

**算式（可复核；① 已实施，② ③ 未实施）**：

- 现状每字节成本（①前）= 内层 16 条 + 块开销 13/8 = **17.63 条**
- ① 已实施后 = 内层 15 条 + 13/8 = **16.63 条**（**−5.67%**）
- 若再做 ② ③：合计再省 ≈ 1.12 条/字节 → **15.51 条**（相对 ①后 −6.7%）

## 四、结论与建议

1. **优化 ① 已实施**（2026-09-12）：`.field` 常量重载去除，解密操作量 **−5.67%**，全套回归全绿。
2. **剩余空间有限**：再叠加 ② ③ 也只能再省约 6.7%（相对 ① 后），且 ② 风险中（拆分循环边界）。
3. **收益已不可感知**：报错二十六（v1 SHA-256 卡启动页）已由 v2 块展开修复；① 在此基础上再省 ≈**3.3ms**（58ms → 54.7ms），**远低于人眼 100ms 感知阈**。
3. **推荐只做优化 ①**：收益确定、风险极低、改动量小（1 行 Java → 重跑 `build-stub.sh`）。
4. **不建议做优化 ②**：收益 6% 但引入三段式边界，与历史事故（块展开对齐写错静默解错）同类，风险收益不对称。

## 六、对比：第三方算法（`docs/别人的加密算法.md`）

第三方 `$(i, i2, i3)`：静态 `short[]` 表 + 每字符 `xor`。

| 维度 | 我们（`StrDec`） | 第三方 `$(…)` |
|---|---|---|
| 密钥来源 | 8B seed + 现场算 splitmix64 密钥流 | 静态 `short[]` 表（表即密钥） |
| 每字符指令 | ≈8 条（+ 每块摊薄） | ≈8 条（`aget-short`+`xor`+`aput-char`） |
| 运行期指令（12786 条规模） | XOR 段 2.31M 条 | 1.52M 条（**0.66×**） |
| 整段（含 Base64） | 3.58M 条 | 1.52M 条（**0.42×**） |
| 密文体积极限 | 表零字节（零表） | ≈2 字节/字符（本样例 236 short = 472B） |
| 强度 | 表不存在，须逆向算法+seed | **表即密钥**：读表 + `xor` 即可还原 |

**结论**：第三方运行期更快（省掉 Base64 + 密钥流派生），代价是**体积**（表 ≈2× 明文）与**强度下降**（表泄露即明文泄露）。**不建议追随**——当前块展开已把性能拉到同一量级，而零表设计在体积与强度上更优。

## 附：环境限制声明
