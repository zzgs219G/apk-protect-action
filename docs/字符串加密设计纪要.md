# 字符串加密模块设计讨论纪要(2026-10)

> **本文是什么**:用户与 AI 关于"dex 字符串加密"需求的完整讨论结论。
> 当前状态:**方案已定型,尚未动工**。动工前需用户点名冻结模块(见 §6)。
>
> 上下文起因:用户在 so 加固完成后提出想自己写一个"字符串加密脚本",
> 隐藏源码里的业务字符串(服务器地址、`"获取API地址成功"` 这类提示语)。

---

## 1. 用户需求(原话还原,不要曲解)

- 把**自己源码里写的字符串**隐藏掉:服务器地址、业务提示语
- 规则写 `**`(全部类)时,脚本要**自动认出"哪些不是我源码"**,内置保护网
  跳过系统/库/资源类——不是让用户自己小心写排除规则
- 不要把清晰源码变成复杂天书(与 so 加固同一约束)
- 不希望"改了不该改的导致崩溃"

## 2. 讨论中纠正的错误认知(重要,防反复)

| 曾经的疑虑 | 澄清结论 |
|---|---|
| "全量 `**` 加密性能损耗很大吗?" | CPU 侧几乎无感(解密带缓存);**真正代价是 dex 体积 +10%~25%**。兼容性才是全量方案的真坑,但会被内置保护层解决(见 §3) |
| "系统类(Landroid/ 等安卓开头)会被误加密吗?" | **天然碰不到**。系统类不在 APK 里,在手机 framework 里,dex 里只有引用没有实现。真正要挡的是打进 APK 的第三方库、R 资源类、Manifest 组件名 |
| "解密算法该写 Java 还是 C?" | **Java(编成 dex 的那个十几行工具类)+ C(只出密钥)**。分工:dex 里被加密的字符串由 ART 执行的 Java 解密类解;密钥住在加固 so 里,Java 通过一次 JNI 取回后缓存。C 写解密函数没必要也不安全 |
| "Kotlin 行不行?" | 不行:编译产物臃肿、依赖 stdlib、语法糖在反编译后留明显模式记号。业界同类工具全用 Java |
| "一个解密类被 AI 看到,直接写脚本解密怎么办?" | 解密类里**没有密钥**(密钥在 so),AI 看到的是空壳;AI 缺输入,需要人类先定位+啃 so,通用自动化失效 |
| "签名指纹哈希当密钥行不行?"(用户自己发现方案二漏洞) | **不行**。指纹是公开数据(MT 管理器直接看),公开数据派生的密钥等于没加密。这是用户自己抓到的真 bug,方案二废弃 |
| "复用双轮派生的哈希值当密钥行不行?"(用户新思路) | **方向对,原料换一下**:派生结果 `SIG_HASH_STORED` 纠缠公开指纹,不能用;派生体系的**随机原料 `SIG_SALT`** 才能用——它每包随机(`os.urandom(16)`)、与公开数据无关、只存在于加固 so 里 |
| "解密进 so 的 JNI 消耗很大吗?" | 误会。**只有取密钥那一次跨 JNI**(微秒级一次性),之后密钥进 Java 静态缓存,所有字符串解密是纯 Java 异或+缓存,零感 |
| "密钥缓存下来,AI 看不见缓存里有什么,是不是就安全了?" | 缓存是运行时概念,**静态分析里不存在**。安全来自"密钥唯一来源是加固 so",缓存只是性能手段 |

## 3. 定稿方案架构

```
┌─ libnc.so(已加固:无路标词/堆破坏/-Oz 等)─────────────┐
│  SIG_SALT(16 字节随机,构建时生成)                     │
│  k() 函数:返回 SIG_SALT(新增 C 代码,追加式)          │
└──────────────────┬──────────────────────────────────┘
                   │ App 启动后唯一一次 JNI 调用(微秒级)
                   ▼
┌─ dex:解密类(Java,十几行,类名普通化)────────────────┐
│  public static native byte[] k();  ← 声明,实现在 so  │
│  public static String d(String s) {                  │
│      byte[] b = Base64.decode(s);                    │
│      for(...) b[i] ^= key[i % key.length];           │  key = k() 结果
│      return new String(b);        }                  │  缓存进静态字段
└──────────────────┬──────────────────────────────────┘
                   │ smali 里所有加密字符串 → 调 d()
                   ▼
  dex 常量池:全是密文,strings/jadx 零收获
```

**三层铁律(设计不变量)**:

1. **密钥唯一来源是加固 so**(不落 dex、不落脚本、不基于公开数据派生)
2. **每包随机**(SIG_SALT 构建时生成 → AI 对上一包的破解经验对下一包失效)
3. **解密结果与密钥都要缓存**(性能零感的必要条件)

**内置保护层(脚本永远跳过,用户关不掉)**:
第三方库前缀(androidx/google/okhttp3/kotlin/... 常见集)、R$ 资源类、
Manifest 注册组件类、反射特征调用点(`forName` 等)。
用户规则 `**` 只在保护层放行的类里生效——用户写错规则最坏是"加密得少",
不是"加密了不该加密的导致崩溃"。

## 4. 攻防定位(对 AI 时代的诚实评估)

- **防得住**:拖 APK 静态看(strings/jadx/MT 管理器)→ 全是密文;AI 写解密器
  → 没有密钥输入,写出来也是空转;每包 SIG_SALT 不同 → 攻击经验不可复制
- **防不住**:抓包(服务器地址这类信息,联网一次就到手)、动态运行时 dump
  内存。字符串加密从来只防"静态阅读",不防"动态截获"
- **AI 对抗的核心逻辑**:不跟 AI 比解题速度,让 AI **拿不到解题输入**——
  密钥不在静态产物里,解题必需的材料被 so 加固防线挡住

## 6. 红线与约束(动工前必读)

- `sig_check.c` / `env_check.c` / dcc/ / inject-loadlib.py / mark-native.py /
  apktool.jar 是冻结模块;本方案动 so 侧需要用户在对话中点名
- 新模块不 import 仓库其他模块内部函数;公共能力放 `scripts/lib/`
- 解密类编译依赖 javac + d8(workflow 已有 JDK17;d8 由 Android SDK 提供,
  setup-ndk 场景下同样可用,需在 workflow 验证一次)
- 性能验收标准:启动到首帧无可感延迟;解密类不在启动热路径上大量调用

## 8. 补充决策(2026-10 第二轮讨论,用户拍板)

1. **解密算法形态 = 模板池随机化**:预写 3~5 个解密能力完全等价、但写法
   不同的模板(异或/加减法/先编码再运算等),每次构建随机抽一个,
   类名方法名同时随机生成。理由:完全固定 = AI 研究透一个包通吃所有包;
   全生成式 = 生成环节静默出错风险高(仓库历史报错高发类型)。
   模板池两头兼顾:每包算法形态不同,且每个模板可被回归测试钉死。
   **配套:每个模板绑定一种彩蛋主题**,逆向者拆不同包看到不同彩蛋,可收集。
2. **密钥流 = 按位置派生**:每条字符串的密钥流按其在常量池中的序号再派生
   (多几行 Java),关闭"猜中一条足够长的明文即可反推全部 16 字节密钥"的
   静态攻击面(16 字节 repeating-key XOR 的经典弱点)。
3. **彩蛋设计(用户核心兴趣:让逆向者看到点有意思的东西)**:
   - 风格:**嘉豪型(打工人自嘲)**——像一个普通开发者深夜改代码随手留的
     实话:方法名「写这段是凌晨三点」「能跑_别动了」「改了八遍_就这吧」
     「别找了_我也没找到过」。精髓是**自嘲、实在、个人味儿**;
     姿态上是平视("都是打工人"),**不是**站防线跟逆向者斗法
     ("钥匙不在这里_真的"式抖机灵太装逼,已否决——那是把自己摆在
     "防守方炫耀"的位置,而且一秒暴露"此处有蹊跷")。
     成功标准:逆向者看到会心一笑"这哥们跟我一样",不是"被作者耍了"。
     附带好处:嘉豪版名字混在业务代码里毫无违和,伪装性反而更好
   - **双层结构(架构约束)**:中文彩蛋只放**纯 Java 彩蛋类**(解密逻辑层);
     取钥匙的 native 声明必须留在**英文薄壳类**(5 行,普通类名)。理由:
     native 方法靠 JNI 命名规范自动绑定(`Java_包名_类名_方法名`),类名
     含中文会转成 `_0x…` 转义绑定名,极易出错(报错十一/十三同型:命名
     假设错→空壳 so)。双层后 JNI 绑定走稳定英文路径,彩蛋自由发挥
   - 安全边界(诚实声明):彩蛋不增加也不减弱密码学强度,安全核心仍是
     "钥匙在加固 so 里";正常中文字符兼容性最好,不用不可见字符
     (工具链兼容性炸点)

## 9. 一段话总结(给未来的自己)

> 我们要做一个脚本,把 dex 里自己写的业务字符串换成密文,运行时才解开。
> 解密逻辑是个十几行的 Java 小类(不用 Kotlin,太显眼),但密钥不在它里面——
> 密钥是构建时随机生成的 SIG_SALT,住在加固过的 libnc.so 里,Java 启动后
> 取一次就缓存住,性能无感。AI 再聪明,静态拆 APK 看到的只有密文和空壳,
> 密钥必须先啃过 so 防线才能拿到,而且每个包的密钥都不一样,经验没法复制。
> 字符串加密只防静态阅读,不防抓包——它的价值是消灭"拖一眼"级别的信息收集,
> 和签名校验(防篡改)、so 加固(防定位)各守一层,互为犄角。
> 彩蛋:解密类的方法名是中文打工人自嘲(「能跑_别动了」,§8.3 嘉豪型)——
> 不是炫技,是留点个人味儿,让逆向者会心一笑。
