### 4.3 异常堆栈

```
java.lang.IllegalStateException: State must be at least 'CREATED'
  to be moved to 'DESTROYED' in component e23(<uuid>)
  destination=ag0(0x3fd384b5) route=com.xixin.box.navigation.MainHubRoute

fk2.e → e23.h → c33.t → c33.b → c33.k → c33.l → i.invoke
→ t21.invoke → ah4.invokeSuspend → hu.resumeWith → p01.run → rd.t0
```

- 两版堆栈**逐帧一致**，仅 `component e23(...)` 的 UUID 每次不同。
- 正式版带 R8 行号映射（`r8-map-id-...:70`），加壳版显示 `Unknown Source` —— 证明二者为**同一份 dex 代码**。
- 崩溃前应用日志固定末行：`[Splash] ✅ 配置已是最新，无需更新`

### 4.4 根因

- `SplashViewModel.kt:27-36` 时序：`REVEAL_MS(1000) + DRAIN_SECONDS(3) + POST_DRAIN_DELAY_MS(80) ≈ 4s`，与实测崩溃时机吻合。
- `SplashScreen.kt:102-122`：倒计时协程的 **`finally` 块无条件调用 `navigateOnce()`**。协程因 composition dispose 被取消时，`finally` 照样执行。
- `AppNavHost.kt:78`：`navigate(MainHubRoute){ popUpTo(SplashRoute){ inclusive = true } }`

Activity 销毁途中仍执行 `navigate()`，新建的 `NavBackStackEntry` 停在 `INITIALIZED` 就直奔 `DESTROYED`，抛出异常。

> **结论：该崩溃是应用自身的 Jetpack Navigation 竞态缺陷，与是否加壳无关。**

## 五、修复方案（已实施）

涉及文件：

- `jian_box/app/src/main/java/com/xixin/box/page/splash/SplashScreen.kt`
- `jian_box/app/src/main/java/com/xixin/box/navigation/AppNavHost.kt`

| # | 改动 | 说明 |
|---|---|---|
| 1 | `navigateOnce()` 移出 `finally`，仅保留在正常走完的路径上 | 取消时 `animateTo`/`delay` 抛 `CancellationException`，协程直接退出，不再导航 |
| 2 | `hasNavigated` 由 `rememberSaveable` 改为 `remember` | 避免 Activity 重建后标志仍为 `true`，导致永久挡掉导航、卡在启动页 |
| 3 | `AppNavHost.kt` 导航前加生命周期守卫 | `lifecycleOwner.lifecycle.currentState.isAtLeast(Lifecycle.State.CREATED)` 为真才导航 |
| 4 | 清理失效 import | 移除 `rememberSaveable`、`kotlinx.coroutines.isActive` |

**对"点跳过"的影响**：无。`onSkip`（`SplashScreen.kt:255-261`）直接调用 `onAnimationEnd()`，不经过 `navigateOnce()`，三条改动均不触及该链路。

# 第二部分：字符串加密 + StrDec 类 dcc 真机测试（2026-10-14）

- **测试对象（精确定义，勿混淆）**：`简盒_字符串加密类被dcc.apk` ——
  **字符串加密（类名规则 `**` 全量）+ dcc 抽取 StrDec 解密桩类**的包。
  即：dex 层全包字符串常量加密，且**解密桩本身**（`Lcom/nc/strdec/StrDec;`）
  被 dex2c 转译进 `libnc.so`、dex 内方法变 native 壳。
  **不是**「dcc 抽业务类」的常规联合方案（那是一直在用的老路径）。
- **对照组**：原生正式版 `简盒-正式版-v2.1.1_211-20261011-2048-18f9281_sign.apk`，
  **同日同时段先后测量**（见下文「对照组设计」）
- **安装方式**：卸载后全新安装，非覆盖
- **体系注意**：本部分被测包属 **apk-protect-action 体系**（dex 在 APK 根、装包期 AOT 完整），
  与第一部分的 dpt-shell 加壳版（隐藏 dex、无 AOT，冷启动 427ms）**不可混比**。

## 一、结论摘要

| 维度 | 结论 |

| 兼容性 | **全过**：无崩溃、`<clinit>` 字段回填链正常、JNI 反调 L1 缓存正常、界面全部字符串正确解密（截图验证） |
| 冷启动 | **无劣化**：稳态 ~173ms vs 原生同日对照 ~181ms（差异在噪声内） |

## 三、兼容性：dcc 转译 StrDec 的三个风险点落地结果

立项前预判的三个未知坑，本次真机全部落地：

| 风险点 | 预判 | 实测 |
|---|---|---|
| `<clinit>` 与 native 化 | `<clinit>` 不能是 native（dex 校验），dcc 应跳过它 → 桩成「回填 Java + 解密 native」混合形态 | **正常**：字段常量回填链（F 字段）工作，无类初始化失败（报错二十四式秒闪退未出现） |
| L1 缓存反向 JNI | 桩内 `ConcurrentHashMap` 在 native 侧需 JNI 反调 Java 集合，可能有性能/语义问题 | **正常**：缓存命中/miss 两路均正确（界面字符串正确 = 全链对） |
| 随机名/种子恢复与 native 壳兼容 | mark-native 后桩 smali 变 native 壳，续跑恢复正则可能失配 | 本次包构建链路自洽（构建成功 + 产物正确），续跑恢复场景待专门验证 |

## 四、性能归因讨论：「解密在 C 层更快」假说

**机制上成立，本次数据无法区分**。桩的解密分两条路径，C 化影响相反：

| 路径 | Java 桩 | StrDec 类 dcc 后 |
|---|---|---|
| 缓存命中（稳态） | 零分配查表 ~50-100ns | 多 2 次 JNI 往返，**变慢** |
| 缓存未命中（冷启动 1-2 万次全走此路） | 每条分配 byte[]/String，Base64 走 Java 实现 | 栈 buffer、无边界检查、零对象分配，**变快** |

冷启动全走 miss 路径，C 化省掉上万次对象分配 —— 这是「测试包与原生打平
甚至略优」的合理解释之一。但对照组是**原生包（无解密可言）**，
173 vs 181ms 的差距在噪声内，无法归因。要坐实该假说需要第三组对照：
**同流水线、规则同样 `**`、桩不 dcc（纯 Java 桩）**的包。
在那之前，结论止步于：**StrDec 类 dcc 无性能代价，可能有小赚**。

## 五、遗留与下一步

1. **待确认**：本次测试包的桩名是固定名（`com.nc.strdec.StrDec` 手动填进

   「随机名自动填入」（方案 E 核心机制，每包构建期才知道名字，手动填规则
