防对比混淆模块 · 开发计划工程书

本文档写给下一任 AI 和开发者。看完你应该知道：做什么、为什么、分几步、每步怎么验收、什么情况算失败。

---

0. 先解释一个词：MVP

MVP = Minimum Viable Product，最小可行产品。

意思就是：别一上来就做完整版，先用最小的代价做一个"能跑通核心流程"的版本，验证这条路走得通，再往上加功能。

比如你要造车，MVP 不是先造发动机，而是先造一块滑板——能站上去、能滑、能证明"轮子+板子"这个方向对。然后再加把手、加座椅、加发动机。

对我们这个项目：

· 完整版：寄存器置换 + 块重排 + 指令变体 + 表重排，全套
· MVP：只做 3 件零风险的事（标签重命名 + 块顺序重排 + 少量垃圾寄存器），先证明"能防对比、不崩、不慢"

MVP 通过了，再决定要不要做复杂变换。MVP 不通过，说明方向有问题，及早止损。

1. 项目背景（为什么做）

1.1 现状

apk-protect-action 仓库已有的能力：

· dcc（dex2c）：把类的方法体抽进 so，dex 里只留 native 壳
· stringenc：加密 dex 里的字符串常量
· sigcheck / envcheck：native 层签名校验和环境检测

1.2 漏洞

攻击者手上有原版 APK，拿到处理过的 APK 后：

1. 反编译两份 → 逐文件 diff
2. 被抽的类特征明显（方法体空 + native 声明），或者被改的类差异明显
3. 定位到那一个类 → 从原版粘回去 → 破解完成

本质问题：改动是"稀疏的、可定位的"。

1.3 目标

让攻击者 diff 两个 APK 时：

· 看不到语义差异，只看到"结构/顺序/编号"的变化
· 像"同一个 App 的两个不同编译版本"，而不是"被人动过手"
· 找不到我们真正修改的那个类

---

2. 项目目标（做什么）

2.1 核心目标

在现有流水线里新增一个 anti-diff（防对比混淆） 模块：

目标 指标
防对比 反编译后 diff 工具报出的"变化文件"占比 > 90%
保语义 App 功能逐项对比，100% 一致
保性能 启动耗时、关键路径耗时劣化 ≤ 5%
保稳定 冷启动 100 次不崩，覆盖后台恢复等场景
可集成 与 dcc、stringenc 同时跑，产物正常回编、正常安装
幂等 同一输入跑两次，产物逐字节一致

2.2 明确不做（红线）

不做 理由
❌ 不改类名、方法名、字段名 改名一眼假，暴露"被处理过"
❌ 不改方法签名、字段类型 结构变化最容易被抓
❌ 不改字符串内容 内容变化是"真改动"，不是"噪声"
❌ 不注入死代码/死方法 ART 验证器风险 + 启动解析开销
❌ 不做 nop 填充 真实执行，热路径会掉性能
❌ 不做控制流平坦化 引入分发器，一看就是"被混淆过"

3. 技术路线（分阶段）

阶段划分总览

```
阶段 0：可行性验证（半天）
  └─ 手工做一次变换，确认方向对

阶段 1：MVP（1~2 天）
  └─ 三类白嫖变换，零风险，先跑通

阶段 2：增强（3~5 天）
  └─ 寄存器置换 + 条件反转（需控制流分析）

阶段 3：完整版（可选，5~10 天）
  └─ 基本块重排（需数据流分析）

阶段 4：与现有模块整合（1~2 天）
  └─ 接入 protect.sh，与 dcc/stringenc 联动测试
```

---

4. 阶段 0：可行性验证（半天）

4.1 目的

不做代码，先手工验证"改了之后会不会崩"。

4.2 任务

1. 拿一个最小 APK（比如一个 Hello World，或你自己项目的一个简单版本）
2. 反编译成 smali
3. 手工挑 3~5 个方法，做以下操作：
   · 把 :goto_0 改成 :goto_abc
   · 把类里两个 .method 块对调位置
   · 在方法入口插 2 条 const v0, 0x0 + move v0, v0
4. 回编 → 安装 → 启动 → 看崩不崩

4.3 验收

☐ App 能正常启动
☐ 反编译后对比，能看出变化
☐ 手工验证 3 种变换各自是否安全

4.4 失败处理

如果手工改都崩，说明方向有问题，立即停止，回头审视需求。

---

5. 阶段 1：MVP（1~2 天）

5.1 目的

用 Python 脚本自动完成阶段 0 的手工操作，跑通"自动变换 → 回编 → 安装"整个流程。

5.2 范围（只做 3 件事）

变换 A：跳转标签重命名

· 方法内所有 :label_name 换成随机名（如 :a3f9）
· 跳过：<init>、<clinit> 内部（执行顺序敏感）

变换 B：类内 .method / .field 块重排

· 把一个类里的多个 .method 块随机打乱顺序
· 多个 .field 块同理
· 跳过：<init>、<clinit> 的位置（它们必须紧跟 .class 声明之后，不能挪）
· 跳过：.annotation 块（可能有顺序依赖）

变换 C：方法入口插垃圾寄存器（谨慎版）

· 只在满足全部下列条件的方法里插：
  · 不是 <init> / <clinit>
  · 不是 native 方法（dcc 抽走的）
  · 方法内没有任何 try-catch
  · .registers 数量 ≥ 5（有余量）
  · 方法第一条指令是 const / move 类（不是 invoke / 跳转）
· 插 1~3 条：const v0, 0x0、move v0, v0、const/4 v1, 0x1
· 插在最开头，不动原有指令

5.3 覆盖预期

· 变换 A：约 80% 的方法
· 变换 B：约 100% 的类
· 变换 C：约 30~40% 的方法（条件严格）

覆盖率低没关系，先保命。 diff 全红的目标靠 A + B 就能达到。

5.4 验收标准

☐ 脚本能自动跑完变换
☐ 变换后的 smali 能通过 apktool 回编（不报错）
☐ 装到真机，冷启动 20 次不崩
☐ 反编译对比：diff 工具报出"变化文件"占比 > 80%
☐ 性能测试：启动耗时对比原版，劣化 ≤ 5%
☐ 跑两次脚本，产物一致（幂等）

5.5 失败处理

· 回编报错：说明 smali 变换有语法错误，逐个方法 debug
· 启动崩：说明某类变换不安全，逐步回退（先去掉 C，再去掉 B，看是哪个问题）
· 性能掉太多：大概率是 C 插得太多，减少插入数量或收紧条件

---

6. 阶段 2：增强（3~5 天，MVP 通过后做）

6.1 目的

增加扰动强度，让攻击者即使做"语义归一化"也难以对齐。

6.2 新增变换

变换 D：寄存器重编号

· 方法内 v0..vN 做随机置换
· 约束：
  · 跳过有 try-catch 的方法
  · 跳过有 long/double 跨寄存器的方法（占 2 个连续寄存器）
  · 跳过用 .locals 的方法（参数编号隐含，置换困难）
· 只对 .registers 且无 try-catch 的方法做

变换 E：条件反转 + 跳转链

· if-eqz v0, :L → if-nez v0, :L2 + goto :L + :L2:
· 约束：
  · 只对循环外的条件做（循环内会掉性能）
  · 每个方法最多 2~3 处
  · 不破坏 try-catch 边界

6.3 验收标准

☐ 在 MVP 的基础上，diff 变化率提升到 > 90%
☐ 性能劣化仍 ≤ 5%
☐ 冷启动 50 次不崩
☐ 幂等性保持

---

7. 阶段 3：完整版（可选，5~10 天）

仅在阶段 2 通过、且有更高对抗需求时才做。

7.1 新增变换

变换 F：基本块重排

· 方法内独立基本块通过 goto 重排
· 约束：
  · 跳过有 try-catch 的方法
  · 只动冷路径（热路径保持不变）
  · 用拓扑排序内随机，不做完全随机

变换 G：字符串池顺序位移

· 通过打乱方法/块的顺序，间接影响 string_ids 顺序
· 本质上是 A + B 的副产品，不需要单独实现

7.2 验收标准

☐ diff 变化率 > 95%
☐ 性能劣化仍 ≤ 5%
☐ 对抗"语义归一化脚本"测试通过

---

8. 阶段 4：与现有模块整合（1~2 天）

8.1 接入点

在 protect.sh 里插入新阶段：

```
mark-native.py → encrypt-strings.py → 【anti-diff.py】→ repack_build
```

8.2 接口约束

1. 必须跳过 native 方法（dcc 抽走的，无方法体）
2. 必须跳过 <clinit> / <init> 内部（sigcheck 和 dcc 依赖它们）
3. 必须幂等（重跑产物一致）
4. 可选开关：--anti-diff，不勾选则完全不影响现有流程

8.3 验收标准

☐ 单独跑 anti-diff：正常
☐ dcc + anti-diff：正常
☐ stringenc + anti-diff：正常
☐ 三者全跑：正常
☐ 不勾选 anti-diff 时，产物与原来一致

9. 工程约定（所有阶段通用）

9.1 文件结构

```
scripts/anti-diff/
  ├── anti-diff.py          # 主脚本
  ├── tests/
  │   ├── test-smoke.sh     # 冒烟测试
  │   └── test-idempotent.sh # 幂等测试
  └── README.md             # 模块说明
```

9.2 CLI 契约

```
anti-diff.py <解包目录> [--seed-hex HEX] [--target CLASS_DESC] [--level 1|2|3]

  --level 1  = MVP（A+B+C）
  --level 2  = 增强（+D+E）
  --level 3  = 完整（+F）
  --target   = 额外加强保护的目标类（可选）
  --seed-hex = 固定随机种子（测试/复现用）
```

9.3 随机种子策略

建议：用输入 APK 的 SHA-256 当种子。

· 内容一样 → 种子一样 → 幂等
· 内容变了 → 种子自动变 → "新版本"

9.4 幂等保证

· 每个变换必须可重入：跑两次结果一致
· 用标记注释（如 # anti-diff-applied）防止重复处理
· 重跑时先清理上一轮的变换（如果需要）

10. 风险与对策

风险 概率 对策
变换破坏 smali 语法 高 AST 级操作，不用文本 replace
ART 验证器拒绝加载 中 严格白名单，宁可不做也不冒险
性能劣化超 5% 中 热路径不改，插桩数量受限
与 dcc/stringenc 冲突 中 跳过 native 方法 / <clinit> / 解密桩
幂等性破坏 中 固定种子 + 标记注释
反编译工具不兼容 低 用 apktool 3.0.3 做基准，其他工具可能兼容

12. 一句话给下一任 AI

先做 MVP（标签 + 块顺序 + 少量垃圾寄存器），验证"不崩、不慢、diff 全红"三个指标；通过了再考虑复杂变换。别一上来就搞寄存器置换和块重排，那是坑。
