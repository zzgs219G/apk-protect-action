# 简盒 字符串加密 + StrDec 类 dcc 真机测试报告

- **测试日期**：2026-10-14
- **设备**：Xiaomi 2602BRT18C（同 2026-10-12《简盒-加壳对比测试报告》设备）/ Android 16 / SDK 36
- **测试对象（精确定义，勿混淆）**：`简盒_字符串加密类被dcc.apk` ——
  **字符串加密（类名规则 `**` 全量）+ dcc 抽取 StrDec 解密桩类**的包。
  即：dex 层全包字符串常量加密，且**解密桩本身**（`Lcom/nc/strdec/StrDec;`）
  被 dex2c 转译进 `libnc.so`、dex 内方法变 native 壳。
  **不是**「dcc 抽业务类」的常规联合方案（那是一直在用的老路径）。
- **对照组**：原生正式版 `简盒-正式版-v2.1.1_211-20261011-2048-18f9281_sign.apk`，
  **同日同时段先后测量**（见下文「对照组设计」）
- **方法**（与 2026-10-12 报告同一套）：
  冷启动 = `am force-stop` 后 `am start -W` 取 `TotalTime`，5 轮取稳态中位数；
  启动 CPU = 进程启动后 6s `/proc/<pid>/stat` utime+stime jiffies（HZ=100），3 轮；
  PSS = 启动后 7s `dumpsys meminfo`。
- **包名 / 主 Activity**：`com.xixin.box` / `.MainActivity`（卸载后全新安装，非覆盖）

## 一、结论摘要

| 维度 | 结论 |
|---|---|
| 兼容性 | **全过**：无崩溃、`<clinit>` 字段回填链正常、JNI 反调 L1 缓存正常、界面全部字符串正确解密（截图验证） |
| 冷启动 | **无劣化**：稳态 ~173ms vs 原生同日对照 ~181ms（差异在噪声内） |
| 启动 CPU | 持平略优：稳态 ~180 jiffies vs 原生 ~210 |
| PSS | 151MB vs 298MB —— **两数字均不可用于对比**（网络内容加载状态不同，见 2.3） |
| 意义 | 「StrDec 类 dcc」的真机可行性三关（兼容/性能/功能）落地，方案 E（桩注入前置 + 规则自动填入）立项条件具备 |

## 二、性能对比

### 2.1 冷启动（`am force-stop` → `am start -W` TotalTime）

| 轮次 | 原生（同日对照） | 字符串加密 + StrDec 类 dcc |
|---|---|---|
| 1 | 378ms | 177ms |
| 2 | 223ms | 172ms |
| 3 | 197ms | 184ms |
| 4 | 176ms | 163ms |
| 5 | 181ms | 173ms |
| **稳态中位数** | **~181ms** | **~173ms** |

> 测试包甚至略快于原生，但 8ms 在测量噪声内，正确结论是「**无劣化**」而非「更快」。

**对照组设计（为什么必须同日测原生）**：本次首测 173ms 时的历史参照是
10-12 报告的原生 195ms / dpt-shell 全模块加壳 427ms —— 但同日实测原生已变为
~181ms，且 10-12 的 427ms 属 **dpt-shell 体系**（隐藏 dex、无 AOT），
与本包的 apk-protect-action 体系（dex 在 APK 根、装包期 AOT 完整）**不可混比**。
跨日、跨体系的数字直接对比会得出错误结论，故补测同时段原生对照。

### 2.2 启动 CPU（启动后 6s jiffies，HZ=100）

| 轮次 | 原生 | 测试包 |
|---|---|---|
| 1 | 262 | 117 |
| 2 | 208 | 183 |
| 3 | 211 | 180 |
| **稳态** | **~210（2.1s）** | **~180（1.8s）** |

> 轮 1 两版都受采集起点（启动后第 1s 才取 J0）影响，稳态看后两轮。

### 2.3 PSS（启动后 7s，dumpsys meminfo）

| 指标 | 原生 | 测试包 |
|---|---|---|
| TOTAL PSS | 298 MB | 151 MB |
| Native Heap | 31.3 MB | 23.4 MB |

**这组数字不可用于性能结论**：两次测量时首页网络内容加载状态不同
（测试包测量时截图显示卡片图标仍在拉取，设备当时 ~124KB/s），PSS 主要差在
内容缓存而非保护机制；且截图验证界面全部字符串正确渲染，排除了
「解密失败静默降级 → 少加载 → 内存低」的功能性疑点。

### 2.4 崩溃与功能

- 连续 10+ 次启动无 FATAL / SIGSEGV / SIGILL（logcat 中的 signal 9 为系统
  LMK 杀其他进程，与本包无关）
- **截图验证**：控制台页全部 UI 字符串（标题/Tab/卡片标题与副标/底部导航、
  中英文混排）均正确解密显示，无乱码、无空缺、无裸密文

## 三、兼容性：dcc 转译 StrDec 的三个风险点落地结果

立项前预判的三个未知坑，本次真机全部落地：

| 风险点 | 预判 | 实测 |
|---|---|---|
| `<clinit>` 与 native 化 | `<clinit>` 不能是 native（dex 校验），dcc 应跳过它 → 桩成「回填 Java + 解密 native」混合形态 | **正常**：字段常量回填链（F 字段）工作，无类初始化失败（报错二十四式秒闪退未出现） |
| L1 缓存反向 JNI | 桩内 `ConcurrentHashMap` 在 native 侧需 JNI 反调 Java 集合，可能有性能/语义问题 | **正常**：缓存命中/miss 两路均正确（界面字符串正确 = 全链对） |
| 随机名/种子恢复与 native 壳兼容 | mark-native 后桩 smali 变 native 壳，续跑恢复正则可能失配 | 本次包构建链路自洽（构建成功 + 产物正确），续跑恢复场景待专门验证 |

## 四、性能归因讨论：「解密在 C 层更快」假说

**机制上成立，本次数据无法区分**。桩的解密分两条路径，C 化影响相反：

| 路径 | Java 桩 | StrDec 类 dcc 后 |
|---|---|---|
| 缓存命中（稳态） | 零分配查表 ~50-100ns | 多 2 次 JNI 往返，**变慢** |
| 缓存未命中（冷启动 1-2 万次全走此路） | 每条分配 byte[]/String，Base64 走 Java 实现 | 栈 buffer、无边界检查、零对象分配，**变快** |

冷启动全走 miss 路径，C 化省掉上万次对象分配 —— 这是「测试包与原生打平
甚至略优」的合理解释之一。但对照组是**原生包（无解密可言）**，
173 vs 181ms 的差距在噪声内，无法归因。要坐实该假说需要第三组对照：
**同流水线、规则同样 `**`、桩不 dcc（纯 Java 桩）**的包。
在那之前，结论止步于：**StrDec 类 dcc 无性能代价，可能有小赚**。
