一、任务背景与目标

1.1 现状问题

1. 签名校验相关资产散落三处：
   · sigcheck/src/：C 源码（sig_check.c / env_check.c / sig_hash.h）
   · scripts/sig-hash/：指纹提取（make-sig-hash.sh + extract-cert-fp.py）
   · scripts/sig-log/：中文日志文案生成（make-sig-log.py）
   这三者逻辑上是一个整体（都属于签名校验/环境检测的构建产物生成），却分散在 scripts/ 和 sigcheck/ 两个顶层目录下。阅读者无法一眼看出它们的归属关系。
2. 流程文档过大：docs/流程文档.md 约 117KB，其中 §0–§8 是使用手册（约 40KB），§9 是报错历史档案（约 80KB）。使用手册被历史档案淹没，阅读者难以快速定位当前流程。

1.2 目标

1. 整合签名校验资产：把 scripts/sig-hash/ 和 scripts/sig-log/ 合并进 sigcheck/ 下，让签名校验相关代码"一个目录说清楚"。
2. 拆分流程文档：§9 独立为 docs/变更历史.md，流程文档回归"使用手册"定位。

1.3 非目标（明确不做）

· ❌ 不移动 sigcheck/src/*.c（sig_check.c / env_check.c 是冻结模块，位置和内容都不动）。
· ❌ 不修改 inject-loadlib.py（它是公共模块，被 mark-native.py 和签名校验共用，不属于签名校验专属）。
· ❌ 不修改任何 C 源码内容（sig_check.c / env_check.c / sig_hash.h）。
· ❌ 不修改 extract-cert-fp.py 的逻辑（它是冻结模块，只搬家不改内容）。
· ❌ 不新增软链（见 §四评估）。

三、目标结构（方向性，细节你定）

3.1 推荐的签名校验新结构

```
sigcheck/
├── src/                      # C 源码（位置和内容都不动）
│   ├── sig_check.c
│   ├── env_check.c
│   └── sig_hash.h
└── tools/                    # 构建期脚本（从 scripts/ 搬入）
    ├── make-sig-hash.sh
    ├── extract-cert-fp.py
    └── make-sig-log.py
```

理由：

· sigcheck/ 前缀已经说明归属，内层再叫 sig-hash / sig-log 重复。
· 内部分两类：C 源码（src/）和构建脚本（tools/）。
· 与项目其他位置的命名风格一致（tools/dcc.zip、scripts/lib/）。

3.2 目标文档结构

```
docs/
├── 流程文档.md       # §0–§8（使用手册）
└── 变更历史.md       # §9（报错档案 + 教训）
```

理由：

· 使用手册与历史档案的读者、阅读时机完全不同：前者是"开工前必读"，后者是"出问题时查阅"。
· 拆分后，流程文档从 117KB 降到约 40KB，便于快速浏览。
· docs/别人的加密算法.md、docs/字符串优化文档.md 保持不变（它们是独立专题）。

3.3 可选方案（你评估后决定）

· 方案 A（推荐）：sigcheck/tools/（原名合并）
· 方案 B（保守）：sigcheck/hash/ + sigcheck/log/（保留原名，只换父目录）
· 方案 C（激进）：把所有 C 源码和脚本都摊平在 sigcheck/ 下（不推荐，混合类型）
