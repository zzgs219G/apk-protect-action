## 0. 系统总览

### 0.1 流水线与模块(共用一套工具,不要混淆)

**唯一总控:`scripts/pipelines/protect.sh`**(2025-09 起取代旧三个总控
`protect-sigcheck.sh` / `protect-dcc.sh` / `protect-sigcheck-only.sh`
与编排器 `run-modules.sh`。旧三个 yml 已删除,唯一入口是
`protect-modules.yml` schema 驱动式 workflow:App 拉 `configs/v1/config-schema.json`
生成勾选 UI → 提交 `protect_config` JSON → `scripts/actions/resolve-config.py`
按 schema 解释成 protect.sh 参数。加新模块只改 schema 一份文件)。

| | 只勾 sigcheck | 只勾 dex2c | sigcheck + dex2c 都勾 |
|---|---|---|---|
| 类名来源 | 无需类名(只插主 Activity) | 手动:用户输入规则 | 自动:Manifest 解析 LAUNCHER |
| dex2c 转译 | **无** | 有 | 有 |
| 额外注入 | `sig_check.c` + `sig_hash.h` | 无 | `sig_check.c` + `sig_hash.h`(并入 dex2c 工程) |
| smali 处理 | `inject-loadlib.py` 双保险插桩 | `mark-native.py` 壳替换 | `mark-native.py` 壳替换(不插双保险) |
| 解包/回编次数 | 1 次 | 1 次 | **1 次**(旧联合方案 2 次,合并后收益) |
| 用途 | 单独测试签名校验模块 | 只做指令抽取 | 完整加固 |
| 产物 | 未签名 APK | 未签名 APK | 未签名 APK |

> **字符串加密(`--stringenc`)是与之正交的第四个模块**:dex 层,不碰 so,任意组合。
> 详见 §3.7。勾选 `--dex2c-stub` 联动时例外——桩内核会进 so,执行顺序也变为
> 「stringenc 前置 → dex2c」,详见 §3.7.4.1。

执行顺序固定:sigcheck → dex2c → stringenc → anti-diff → envcheck → packer,
与勾选顺序无关。**注意 envcheck 的实际落点在 NDK 组装阶段**(检测代码并入
libnc.so),列表末位只是展示顺序。

其中 packer(基础加壳)**必须最后执行**:它改写 dex/so/Manifest,
一旦之后再动 smali 或再回编一次,壳与保护层就对不上(详见 §3.10)。

> **模块化路线**:以上三种勾选组合覆盖全部场景,共用一次解包/回编。已为此
> 打下的基础:
> - `scripts/inject/inject-loadlib.py`:loadLibrary 插桩的**可复用基础模块**
>   (幂等,多模块共存安全)
> - **so 名统一约定为 `nc`**:两模块都勾选时共享同一个 libnc.so
>   (dex2c 的 native 壳 + sig_check.c 的 constructor 并入同一 jni 工程,
>   constructor 先于 JNI_OnLoad 执行,天然兼容)
> - 单独签名校验的 NDK 工程用自包含 Android.mk(wildcard 收 `*.c` + `*.cpp`;
>   dex2c 模板默认只收 `*.cpp`)

### 0.3 核心事实速查(AI 审查前必须背下,历史上 3 个 bug 全栽在这里)

1. **dex2c 的 `full_name` 没有 `->`**。
   `dcc.py` 用 `''.join(method_triple)` 拼接,结果是
   `Lcom/demo/app/MainActivity;onCreate(Landroid/os/Bundle;)V`
   ——分号后**直接跟方法名**,没有箭头。filter 里写 `->onCreate` 永远匹配不上。
2. **full_name 的类名是 smali 斜杠格式**。
   dex 描述符原样返回:`Lcom/demo/app/Main;`,**不是** `Lcom.demo.app.Main;`。
   用户输入和 Manifest 都是点号 → 写 filter 前必须 `点号 → 斜杠`。
3. **dex2c 原版 native 化不完整**。
   `dcc.py` 只在自带重打包路径(不带 `--project-archive`)里替换 native 壳,
   且**从不插入** `System.loadLibrary`。我们用 `--no-build --project-archive`
   只取工程包,所以 native 化必须由 `mark-native.py` 自己做,否则必闪退
   (UnsatisfiedLinkError: 方法已声明 native 但 so 没加载 / 或方法体丢失)。

## 2. 联合方案流程(protect-modules.yml 勾选 sigcheck+dex2c → protect.sh)

> 输入:`workflow_dispatch.apk_url`(开发者 keystore 已签名的 APK)
> 输出:`protected_unsigned.apk`(未签名,用户需自行重签)

### 步骤 1:下载 APK

- 【输入】`apk_url`
- 【操作】`curl -fL --retry 3 -o app.apk "$apk_url"`,`ls -la` 确认落盘
- 【产出】工作目录 `app.apk`
- 【审查点】文件大小 > 0;`ls` 输出必须 `tee -a build.log`(否则失败无法排查)

### 步骤 2:提取证书指纹(make-sig-hash.sh → sig_hash.h)

- 【输入】`app.apk`
- 【操作】调 `extract-cert-fp.py`:纯 stdlib 解析 APK Signing Block
  (v3 `0xF05368C0` 优先,退 v2 `0x7109871A`),取第一张证书 DER → SHA-256
- 【产出】`sig_hash.h`,内容形如 `#define SIG_HASH ...`(64 hex 拆字节)
- 【审查点】
  - 指纹必须与 **最终发布重签** 的 keystore 一致(加固包重签后指纹会变!
    流程产出的包未签名,开发者重签后指纹才生效——若重签用不同 keystore,
    校验必然失败,这是设计约定不是 bug)
  - 指纹全零 = 调试模式,sig_check.c 会跳过校验(仅本地测试允许)

### 步骤 3:动态解析 Manifest → 自动 filter(联合方案核心)

- 【输入】`app.apk`
- 【操作】依次执行:
  1. `make-filter-from-apk.py app.apk $WORK/auto_filter.txt \
      --classes $WORK/activity_classes.txt --on-fail error`
     - 用 dcc 内置 androguard(载体)读 AndroidManifest.xml
     - 取带 `android.intent.action.MAIN` **且** `android.intent.category.LAUNCHER`
       的 activity(enabled=false 的跳过)
     - 相对类名补全:`.MainActivity` → `com.pkg.MainActivity`;
       无点短名 `MainActivity` → `com.pkg.MainActivity`
     - **点号 → 斜杠**后写入 filter:`Lcom/pkg/MainActivity;.*`
     - `--classes` 同时导出全部 Activity 列表(供 activity* 展开)
     - 失败策略:解析不到 LAUNCHER → exit 2,流水线终止
       (报错信息提示用户改用规则文件手动指定类名)
- 【产出】`$WORK/auto_filter.txt`(已是 dex2c filter 正则格式,直接使用)
- 【审查点】
  - filter 行必须是**斜杠**格式,出现点号即 bug
  - 出现 `->` 即 bug(见 0.3 第 1 条)
  - 多个 LAUNCHER 时全部纳入(日志会打印数量)
  - **禁止把 auto_filter.txt 再喂给 rules-to-filter.py 做二次转换**:
    该脚本输入是点号格式用户规则,二次转换会产生畸形正则导致
    `no compiled methods`(历史上真实发生过的 bug)

### 步骤 4:转译(2026-12 起 dex2c 为唯一引擎,旧引擎 dcc 已下线)

- 【输入】`app.apk` + `auto_filter.txt`
- 【操作】dex2c 转译(唯一引擎,`tools/dex2c.zip`):
  ```bash
  cd $DEX2C_DIR
  python3 dcc.py -i "$IN_APK" -o <哑值> \
    --project-archive "$WORK/dcc-project.zip" \
    --no-build --disable-signing --allow-global \
    --filter "$WORK/auto_filter.txt"
  ```
- 【产出】`$WORK/dcc-project.zip`(jni 工程,内含生成的 .cpp 与
  `jni/nc/compiled_methods.txt`)
- 【审查点】
  - **`IN_APK` 必须是绝对路径**。`protect.sh` 开头已做
    `cd dirname && pwd` 规范化——因为本步骤 `cd $DEX2C_DIR` 后相对路径
    `app.apk` 会失效,这正是历史"报错二"的根因
  - `dcc.py` 出错时只 `logger.error` **不返回非零退出码**,所以必须紧跟
    `[[ -f "$WORK/dcc-project.zip" ]] || exit 1`,不能省
  - `compiled_methods.txt` 每行格式:
    `Lcom/pkg/Class;methodName(args)ret`(无箭头,斜杠类名)

### 步骤 5:合入签名校验代码

- 【操作】
  1. `unzip dcc-project.zip -d $WORK/project`
  2. `cp scripts/sigcheck/src/sig_check.c $WORK/project/jni/nc/`
  3. `cp $WORK/sig_hash.h $WORK/project/jni/nc/`
  4. 覆写 `jni/Application.mk`:`APP_ABI := armeabi-v7a arm64-v8a`
     (dex2c 模板默认只有 v7a,必须双 ABI)
- 【审查点】
  - `sig_check.c` 用 `__attribute__((constructor))` 做入口,与 dex2c 模板
    `Dex2C.cpp` 里的 `JNI_OnLoad` **不冲突**(dlopen 时 constructor 先于
    JNI_OnLoad 执行)。审查时若有人把 sig_check 改成 JNI_OnLoad 会链接冲突
  - Android.mk 用 wildcard 收 `jni/nc/*.cpp`,新加的 .cpp 自动进编译,无需改 mk

### 步骤 6:NDK 编译

- 【操作】`ndk-build -j$(nproc) -C $WORK/project`
  (PATH 前置 `$ANDROID_NDK_HOME`)
- 【产出】`$WORK/project/libs/armeabi-v7a/libnc.so`、
  `$WORK/project/libs/arm64-v8a/libnc.so`
- 【审查点】两个 ABI 目录都要有 so,缺一个说明 Application.mk 未生效

### 步骤 7:apktool 解包

- 【操作】`java -jar apktool.jar d -r -f -o $WORK/decompiled app.apk`
  (`-r` 不反编译资源,保持资源二进制一致;**`--force-manifest` 必须不带**,
  原因见下方"报错五":带上时顶层 Manifest 被解码成文本 XML,
  `apktool b` 在 `-r` 模式下会把文本 Manifest **原样拷回** APK、不重编成
  AXML,产物是系统/文件管理器都不认的"灰包"。
  历史"报错四"曾要求带 `--force-manifest`,那是文本 Manifest 消费方案的
  遗留约定;现 `inject-loadlib.py` 已走 androguard AXMLPrinter 解析二进制,
  `extractNativeLibs` 走 `patch-extractnativelibs.py` 原位补丁,不再依赖文本)
- 【审查点】解包目录下应有 `smali/`、`smali_classes2/`…(多 dex 时);
  顶层 `AndroidManifest.xml` 必须是**二进制**(头 4 字节 `03 00 08 00`),
  若是文本 XML 立即终止排查

### 步骤 8:smali native 化(mark-native.py,不可跳过)

- 【输入】`$WORK/project/jni/nc/compiled_methods.txt` + `$WORK/decompiled`
- 【操作】对 compiled_methods.txt 中每个 (类,方法,原型):
  1. 在对应 .smali 里找到 `.method ... name(proto)`,把整个方法体替换为
     `.method native ... name(proto)`(native 方法不能有方法体)
  2. 每个被改的类插入 so 加载:
     - 已有 `<clinit>` → 在其开头插
       `const-string v0, "nc"` +
       `invoke-static {v0}, Ljava/lang/System;->loadLibrary(Ljava/lang/String;)V`
     - 没有 `<clinit>` → 在 `.class` 行后新建一个
  3. 类里已有 loadLibrary 则跳过(幂等)
- 【产出】修改后的 smali;stdout 打印每个文件的替换数
- 【审查点】
  - **退出码 3 = 有方法没在 smali 里找到** → 流水线会直接失败(set -e),
    必须排查(可能是混淆重命名/多 dex 路径问题),不许静默忽略
  - 幂等性:重复运行会再次匹配 native 头并原样重写,输出不变,安全

### 步骤 9:放 so

- 【操作】把 `$WORK/project/libs/*/libnc.so` 复制到
  `$WORK/decompiled/lib/<abi>/libnc.so`
- 【审查点】abi 目录名必须是 `armeabi-v7a` / `arm64-v8a` 原名

### 步骤 10:extractNativeLibs 强制 true

- 【操作】`python3 scripts/repack/patch-extractnativelibs.py $WORK/decompiled/AndroidManifest.xml`
  —— 直接解析**二进制 AXML**,把 `<application>` 的 BOOLEAN 属性
  `extractNativeLibs` 在原位从 false(0x12/data=0)改写为
  true(0x12/data=0xFFFFFFFF),等尺寸、大小与偏移全不变。
  (报错五之前用 sed 改文本 Manifest;现在 Manifest 全程保持二进制,无法 sed)
- 【审查点】这是**唯一允许的 Manifest 修改**,其他一律不许动
  (方案红线:不改 Application 类名、不加组件);
  脚本幂等(已是 true 跳过);属性不存在或非 AXML 时**报错退出**而非静默

### 3.1 类名规则文件格式(`workflow_dispatch.class_rules`,一行一个类)

| 规则 | 语义 | 生成 filter(斜杠格式) |
|---|---|---|
| `com.test.**` | test 包所有类,含子包 | `Lcom/test/.*;.*` |
| `com.test.*` | test 包所有类,不含子包 | `Lcom/test/[^.]*(/.+)?;.*` |
| `com.test**` | 等价 `com.test.**` | 同上第一行 |
| `com.test*` | com 下 test 开头的所有类(testx、test 均命中,可带子包) | `Lcom/test[^.]*(/.+)?;.*` |
| `com.app.MainActivity` | 精确类名 | `Lcom/app/MainActivity;.*` |
| `activity*` | 所有 Activity 子类(从 Manifest 提取) | 逐类展开为具体行 |
| `!com.test.libs.**` | 排除(优先) | `!Lcom/test/libs/.*;.*` |
| `# 注释` / 空行 | 跳过 | — |

- 【审查点】
  - `activity*` 检测用的是 `grep '^[[:space:]]*activity\*[[:space:]]*$'`,
    **不要改回 `\s`**(grep BRE 不认,历史 bug)
  - `activity*` 展开依赖 `--classes` 类列表;类列表兼容点号
    (`com.a.B # activity`)与 smali(`Lcom/a/B;`)两种格式
  - 精确类名不会误伤 `MainActivityHelper`(有分号锚定)

### 3.2 执行顺序细节

`protect.sh` 步骤 2 **先**跑 `rules-to-filter.py`,**再**检测是否含
`activity*`,含则补跑 `make-filter-from-apk.py --on-fail skip` 生成类列表。
注意:若规则含 `activity*` 但解析失败(skip),filter 里 `activity*` 会展开为
空 → dex2c 抽不到方法 → 工程包不存在检查处失败。审查时看日志里
"待 native 化方法: 0 个" 即为此场景。

## 3.5 单独签名校验流程(protect-modules.yml 只勾 sigcheck → protect.sh)

> 模块化流水线:只注入签名校验,**不跑 dex2c**。
> 用途:单独测试签名校验模块、单独定位问题。所有"模块化基础约定"见 §0.1 末尾的说明块。

与联合勾选的差异(其余步骤 6~12 完全相同,审查标准同上):

| 差异点 | 联合勾选 | 单独签名校验 |
|---|---|---|
| 步骤 3(找类) | Manifest 自动解析 → filter | **无**(不需要) |
| 步骤 4(dex2c 转译) | 有 | **无**(跳过) |
| 步骤 5(合入校验代码) | 解包 dex2c 工程后 cp 进 jni/nc/ | **组装最小 NDK 工程**:`sig_check.c` + `sig_hash.h` 放 jni/ 根;ndk_write_mk 统一模板两级 wildcard 都收(`*.c` + `*.cpp`,dex2c 模板默认只收 `*.cpp`,sig_check.c 是 .c 所以必须收 .c) |

- 【审查点】
  - so 名必须是 `nc`(模块化约定,与 dex2c 共享 so 的前提)
  - loadLibrary 插桩必须走 `inject-loadlib.py`(幂等按方法体独立检查)
  - **双保险插桩(单独方案专属)**:`<clinit>` + `onCreate` 各一份,
    攻击者要删两处才能绕过校验。联合方案(dex2c)**不要**用:
    onCreate 已抽进 so 成 native 壳,删 `<clinit>` 的 loadLibrary 会让
    native 壳 `UnsatisfiedLinkError` 自爆,天然无双保险需求
  - **`<clinit>` 永远不能被 dex2c 抽进 so**(filter 的 `!<clinit|init>`
    排除规则):被抽进 so 的方法要先加载 so 才能执行,而 loadLibrary
    就在 `<clinit>` 里 —— 鸡生蛋。dex 必须永远保留一条 Java 层
    loadLibrary,这是防线不可删除的根本约束
  - onCreate 无法插桩的情形(类未 override / onCreate 零局部寄存器,
    后者给 `.registers` +1 会让参数寄存器编号平移、方法体引用全错位,
    宁可不插):`<clinit>` 那份仍在,校验不受影响;inject-loadlib 会
    打印状态(no-method / no-local-register),流水线日志可见
  - 校验时机:主 Activity 的 `<clinit>` 在 App 启动时执行 → loadLibrary
    → so 的 constructor 立即校验签名,早于一切业务代码;onCreate 里
    那份是 `already` 跳过(so 已加载,重复加载无害)

## 3.7 字符串加密模块(protect.sh --stringenc 规则文件)

> **定位**:dex 层的字符串常量加密,与 so 完全无关(不碰 dex2c / libnc.so / native 层),
> 属于与 dex2c 并列的**独立模块**,可单独勾选,也可与任意模块组合。
> 用途:让 `strings` / 静态特征扫描看不到源码里写死的明文(URL / API key / 日志文案等)。

### 3.7.1 加密对象与边界(审查时最容易搞错的地方)

| 对象 | 是否加密 | 说明 |
|---|---|---|
| `const-string` / `const-string/jumbo` 字面量 | ✅ | 指令级改写,见 3.7.2 |
| **字段的字符串值**(`static final String S = "x"`) | ✅ | R8 会把它折叠成 `.field ... = "x"`(**不是** `const-string` 指令!),由 field 分支单独处理 |
| `<clinit>` 里 `const-string` + `sput-object` 的字段赋值 | ✅ | 形态上就是普通 `const-string` 指令,天然覆盖 |
| 字符串数组元素 / 枚举参数 / 接口常量 | ✅ | 编译产物同样是 `const-string`(数组元素为 `aput-object` 前的字面量) |
| 字段**名** / 方法名 / 类名 / 类型描述符 | ❌ | dex 结构引用(type_ids/field_ids/method_ids→string_id),动了类加载即崩 |
| 注解值(`@Foo(value = "x")`) | ❌ | 不是 `const-string` 指令,天然不在扫描面 |
| Manifest / 资源里的字符串 | ❌ | 不在 dex 里,本模块不涉及 |

- **加密粒度 = 指令级字面量**,不做"字段值密文化"那种存储层改写(要破坏常量传播、
  改写所有已内联点、给反射读取路径补解密,收益却与指令级几乎相同)
- **安全边界(必须对用户讲明)**:这是**防静态可见性**,不是密码学安全。密钥流派生
  材料(salt)与密文同处一个 dex,懂格式者仍可解。真正的密钥材料须走服务端方案

### 3.7.2 指令改写形态(不新增寄存器)

```
改前: const-string v0, "明文"
改后: const-string v0, "<Base64 密文>"
      invoke-static/range {v0 .. v0}, Lcom/nc/strdec/StrDec;->d(Ljava/lang/String;)Ljava/lang/String;
      move-result-object v0
```

- **参数与结果都用原寄存器 `v0`** → **不需要 `.registers +1`**,
  从根上规避报错十一/十三那类寄存器错位问题(这是本模块最重要的实现约束)
- **注入的 invoke 一律用 `/range` 形态**:`invoke-*` 是 35c 格式,寄存器列表
  仅 4 位(**上限 v15**),而 `const-string`(21c)可用到 v255 → 目标寄存器
  编号 ≥16(Compose/Kotlin 大方法,或 `pN` 且换算后 ≥16)时 `{vN}` 会直接汇编
  失败(报错二十一)。单寄存器 range 恒连续、dex 中同为 3 个 code unit(无体积
  代价),且对 `vN`/`pN` 都合法 → **不需要**解析 `.registers`/`.locals` 做换算;
  幂等识别正则 `_PAYLOAD_RE` 必须同时认 `invoke-static {..}` 与
  `invoke-static/range {.. .. ..}` 两种形态(否则续跑 `max_existing_idx` 漏算
  → keystream 复用)
- 字段常量(`.field ... = "明文"`)的初值**已去除**(2026-09-12 字段去初值,
  取代报错二十四时代的"保留明文初值"):字段行只留声明
  `.field public static final X:Ljava/lang/String;`,明文不再进 dex 字符串池
  → `strings` 扫产物对字段值零命中。字段值由**回填链**唯一写入:在字段所属类
  `<clinit>` 末尾(无则新建)注入
  `const-string v0, "<密文>"` + `invoke-static/range … d()` +
  `move-result-object v0` + `invoke-virtual … intern()` + `move-result-object v0`
  + `sput-object v0, <本类>;-><字段>`
  - 【为什么不再保留明文初值】**报错二十四的非法形态是"初值指向 StrDec 字段"
    (引用型 encoded static_value,FIELD 型 0x19)——dex 规范不允许**;而"无初值"
    是 STRING 型初值 offset=0(NO_INDEX),规范明确允许(static final 由 `<clinit>`
    赋值是 javac 常规产物)。两者机制不同,不是同一条红线的松绑
  - 【intern() 必须保留】Java 字面量是同一 interned 实例,代码里 `==` 比较字符串
    可能依赖它;去初值后常量的 interned 实例只能来自回填链 → 回填链缺 `intern()`
    会让 `==` 语义静默退化(报错二十六时代 §3.7.4 就写着这条约束)
  - 【幂等与代价】初值已去掉的行不再匹配字段正则,重跑自然不重复回填;代价是
    "初值永远拆不回明文"——回明文的正路是用 git 恢复源码重跑,不是指望脚本反推
  - 【构建期断言】新增 `_FIELD_STRING_LITERAL_RE` + `_scan_illegal_field_literals`:
    加密面内(带 `# nc-strdec-encrypted` 或桩自身)的 String/String[] 字段初值若仍是
    字面量即 fail-fast(去初值漏改)。⚠️ **判定必须与字段分支同源**(逐行调
    `field_literal_is_skipped`),不能用"有标记就全文件粗扫"——字段分支有**按设计
    保留明文初值**的类别(空串、编译器调试标记串、解析失败(孤立代理项))——粗扫会把它们
    一并判成漏改而误拦整包(报错二十八,`**` 全量规则命中 okhttp3/HttpUrl 的
    `FRAGMENT_ENCODE_SET=""` 时必现;`包名+*` 命中不到这些库类故不复现);
    原 `_ILLEGAL_FIELD_INIT_RE`(FIELD 型 0x19)保留
  - 【三类设计内保留的完整口径(决策 A,2026-09-12 用户拍板)】
    ① 空串 ② 编译器调试/内联标记串 → `field_literal_is_skipped()`
    ③ 值解析失败(孤立代理项等 ValueError)→ `_scan_illegal_field_literals()` 放行。
    ③ 的合理性:加密这条路对它是**走不通**而不是**没走**(smali_unescape 确定性拒绝,
    拿不到明文就无法构造回填链),且**产物出现该类明文必定伴随
    `⚠️ 跳过无法安全解析的字段字面量(...)` 告警**,不是静默失败。
    已知实例:guava `CharMatcher$Invisible.RANGE_STARTS` 含 `\ud800`(字符区间查表用
    控制字符,非敏感数据)。真漏改(本该处理却留下明文)仍被断言精确拦截,见 变更历史.md 报错二十八
  - 【必须真汇编 + 读回验证】去初值属静态数据区改写,只有 `apktool b` 真汇编
    + androguard 读回才能证明合法(报错二十四"汇编器宽容 ≠ 产物合法"教训)。
    实测:去初值后该字段 `EncodedValue` 由 STRING 型(0x23,指向字符串池)
    变为 type=30/raw=None(NO_INDEX),产物 dex 字符串池对字段明文零命中
- 密文用 **Base64( idx_be24 || cipher )** 存成 ASCII,规避 `\u0000`/代理对/转义坑;
  代价是 dex 体积膨胀约 1.33×(仅限被加密的字符串)

### 3.7.3 算法(构建期与运行期必须逐字节一致)

```
seed      : 8 字节随机(os.urandom),构建期生成;重跑已有桩时复用桩里的 SEED
offset    : 该条明文的 UTF-8 字节在"全包虚拟密钥流"里的起始下标(3 字节大端)
            分配器保证全包各条密文的 [offset, offset+len) 区段互不重叠
密文形态  : Base64( offset_be24 || cipher ),cipher[i] = plain[i] ^ keyByte(seed, offset+i)
密钥流    : keyByte(seed, i) = (mix64(seed + (i >>> 3) * GAMMA) >>> ((i & 7) * 8)) & 0xFF
            splitmix64: z ^= z>>>30; z *= 0xBF58476D1CE4E5B9L;
                        z ^= z>>>27; z *= 0x94D049BB133111EBL; return z ^ (z>>>31)
            GAMMA = 0x9E3779B97F4A7C15L
```

- 属**轻量异或**(用户选定的强度档),但密钥流由 splitmix64 现算,优于固定短 key 轮转
- **零表**:全包只存 1 个 8 字节种子,无 `KEYS` 表、无每类 `short[]`(第三方方案的表本方案不存)
- 两侧一致性靠**对拍测试**锁定(构建期 Python 实现 == 桩的 Java 实现),
  边界用例:offset 非 8 对齐(1/7/9/65535)、块边界、UTF-8 多字节、NUL、emoji、5188B 长串
- 历史教训同型:报错十八的"两侧派生协议必须以对拍为准,不能只看注释自以为一致"
- ⚠️ **`keyByte` 的块展开易错点**(2026-09-12):一个 `mix64` 产出 8 字节密钥流,
  `d()` 按块展开可省 8 倍重算,**但块内起始位必须是 `(offset + k) & 7` 而不是 0**。
  `offset` 由分配器推进(密文长度),`offset % 8` 会遍历所有值 → j 写错会让约一半
  字符串静默解错(不崩、不报错,只是文案/URL 全烂)。优化前的正确性基线见 `d()` 注释

### 3.7.4 解密桩(纯 Java,无 so 依赖)

```
类: Lcom/nc/strdec/StrDec;   ← 生产默认每包随机(见 §3.7.4.1)
  SEED:J                全包唯一密钥材料(8 字节,构建期按结构改写 `.field` 初值,
                        同时改写 d8 内联到使用点的常量 —— 双锚点一致性注入)
  d(String) -> String   【壳】try/catch 兜底 + 转调 dn();异常表必须留在这一层
  dn(String) -> String  【内核】Base64 解码 → offset_be24 → XOR → new String(UTF-8)
                        + L1 缓存;方法体内无 try/catch,供 dex2c 转译进 so
  keyByte(JJ) -> I      密钥流第 i 字节(逐字节;被块展开后的 dn() 与对拍测试共用)
  mix64(J) -> J         splitmix64 终混合(long 溢出天然 = mod 2^64)
  <clinit>              建 L1 缓存 + 字段常量回填(`inject_clinit_backfills` 注入的 sput 链)
```

- **d() 按 8 字节块展开**(2026-09-12):每块一次 `mix64`,块内取 `(offset+k)&7` 起的
  各字节;调用次数由 `len` 降为 `ceil(len/8)`,纯 XOR 主循环不受影响
- 解密失败时 `dn()` 抛异常,由壳 `d()` 的 `catch` 捕获后返回原密文串,
  不继续上抛(避免把"解密出问题"变成闪退)
- **桩自身在硬排除名单内**,永不被加密(否则递归)
- ⚠️ **`.registers` 必须 ≤ 16**:`array-length`/`int-to-byte` 是 12x 格式,
  寄存器上限 v15(报错二十五)。块展开后 `dn()` 用到 `v15`,`build-stub.sh` 重跑
  即重算 `.locals`;**改 `dn()` 后必须重跑 build-stub.sh + A1 对拍**,不要手改 smali
- ⚠️ **形参寄存器区不得当临时槽**(报错二十二,已由构建期自检锁死):
  内层循环若用形参区(v14/v15)当异或临时值,等于改写形参本身 → 第 2 轮
  `aget-byte v14, v14, v13` 把 int 当数组引用 → ART **SIGSEGV**
  (非 null 非法引用不做检查直接解引用,Java `catch Throwable` 也拦不住)
  → 闪退且**无 FATAL 日志**(段错误不走 ART uncaught-exception 路径)。
  自检锚定 **`dn()`**(2026-10 起):真正调用系统 Base64 解码的是内核,
  壳 `d()` 已退化为三行转调,按旧锚点 `d` 会误报壳的 `move-result-object`
  并放过内核真实风险

#### 3.7.4.1 两层拆分与 dex2c 联动(2026-10)

**动机**:威胁从"引擎固定签名/一键脚本"升级到"把桩类 smali 发给 AI 即可还原"。
桩名虽每包随机,但算法/常量/密钥流整体可读。联动把内核转译进 `libnc.so`,
dex 侧只剩三行壳。

| 层 | 方法 | 联动后去向 |
|---|---|---|
| 壳 | `d()` | **进 so**（2026-12 起全抽，含 try/catch 兜底） |
| 内核 | `dn()` / `mix64()` / `keyByte()` | **进 so** |

**`d()` 也进 so**（2026-12 更正）：原结论"dex2c 不支持异常表、异常处理器被
静默丢弃"已被实测证伪——T1~T8 八个 try/catch 形态全部转译成功，
`dex2c/writer.py` 有完整的异常发射（`visit_landing_pad` →
`d2c_is_instance_of` 分发、`visit_move_exception`、`EX_UnwindBlock` 统一出口）。
`catch(Throwable)` 兜底在 C 侧完整保留（`goto` 返回原密文），降级语义等价。
详见 `docs/变更历史.md` 2026-12 条目与 `scripts/string-enc/README.md`。

**filter 必须三条齐上**:dex2c 只转译 filter 命中的方法,未命中的即使被调用
也只是留一个 JNI 反调。只写 `dn` 时 `mix64`/`keyByte` 留在 dex 被
`D2C_RESOLVE_STATIC_METHOD` 反调,splitmix64 常量仍可读 —— "算法进 so"
名不副实(端到端实测发现,`tests/test-link-dex2c.sh` 断言④⑤ 锁死)。

**顺序手术**:dex2c 从 **APK** 读 dex(`compile_dex`→`auto_vm`→androguard),
而桩在 STEP5 才注入 smali,正常顺序下 STEP2 根本看不到桩类。勾选
`--dex2c-stub` 时:

```
STEP2 前  stringenc 前置跑一轮:解包 → 加密+注桩 → 回编成 APK'
STEP2     dex2c 转译 APK'(filter 含桩规则)→ 桩被抽进 so
STEP5     解 APK'(不是原始 IN_APK!否则密文+桩全丢)
          → mark-native 把 dn/mix64/keyByte 改成 native 壳
          → 跳过 stringenc(二次加密会包两层密文 → 整包乱码)
```

代价:apktool 解包/回编 **1 次变 2 次**(+30~60s);只联 `--dex2c`(唯一引擎)。

**未验证项**:全流程 apktool 回编 + NDK 编译 + 真机启动未跑;
`dn→mix64` 在无 `--dynamic-register` 时走 JNI 往返而非本地调用,
冷启动多一次 JNI/条,性能影响未实测。

### 3.7.5 选类规则(与 dex2c 完全同一套语法)

| 规则 | 语义 |
|---|---|
| `com.test.**` / `com.test.*` / `com.test*` | 同 §3.1 全部语义 |
| `com.app.MainActivity` | 精确类名 |
| `activity*` | 需 `--classes`(protect.sh 自动从 Manifest 提取) |
| `!com.test.libs.**` | 排除(优先级最高) |
| `# 注释` / 空行 | 跳过 |

- 复用 `rules-to-filter.py` 的 `class_rule_to_filter` / `has_wildcard` /
  `expand_activity_keyword`(**同一份实现,不另写一套**)
- ⚠️ **必须把「用户规则文件」直接交给 `encrypt-strings.py`**,
  绝不可先转成 filter 再喂进去:那是二次转换,会产生畸形正则
  `LLcom/myapp//[^.]*;/[^.]*(/.+)?;.*` → 0 命中(与 §2 步骤 3 的 filter 坑同型)

### 3.7.6 硬排除名单(规则层不可突破)

即使用户写 `**` 全量,下列前缀的类一律不加密(用户明确要求):

```
android.  androidx.  android.support.  com.android.  com.google.android.
dalvik.   java.      javax.            kotlin.       kotlinx.
org.jetbrains.  org.apache.  org.json.  org.w3c.  org.xml.  sun.
```

**常用第三方依赖(2026-09-12 追加)**同列硬排除——此类库的 const-string 承载
类名/字段名/协议/序列化标记(反射与注解处理必需),加密后 `Class.forName`/
`getAnnotation`/序列化匹配、甚至网络协议(OkHttp)会失效;加固只保护自家代码
(`com.xixin.box.*`),第三方字符串本非重要资产。当前清单:

```
okhttp3.   okio.        com.google.gson.  org.jsoup.   org.commonmark.
io.ktor.   coil3.       moe.shizuku.
```

外加解密桩自身 `com.nc.strdec`。用户 `!` 排除行优先级最高。
- 【审查点】前缀判定必须带**点号**(`android.` 而非 `android`)——
  否则 `androidXcustom` 这种同前缀类会被误排除
- 【审查点】日志会打印"被硬排除跳过: N 个类",为 0 且规则写了 `**` 时排查前缀表
- 【审查点】新增依赖库豁免 = 在 `encrypt-strings.py` 的 `SYSTEM_CLASS_PREFIXES`
  追加一行带点号前缀(工具类库 / 反射注解库 / 网络协议库优先豁免);纯 UI/工具
  库且确认无反射绑定的可豁免,反之绑定库必须豁免。教科书级反面:`xcrash.`、`okhttp3.`

### 3.7.7 接入点与执行顺序

**默认路径(不勾 `--dex2c-stub`)**：`protect.sh` STEP 5 内，**必须在
`mark-native.py` 之后**：

- 被 dex2c 抽走的方法此时已是 native 壳(无方法体),字符串加密自然扫不到;
  同时用 `--exclude-methods compiled_methods.txt` 做**精确跳过**(防 dex2c 与
  mark-native 之间的时序差异导致误加密,报错十三式的布局假设错误)
- 每轮先跑 `encrypt-strings.py clean <解包目录>`:按组件标记清理上一轮残留的
  解密桩(本次 0 条命中时不能把旧桩带进产物)
- **幂等**:已加密的类插了标记注释 `# nc-strdec-encrypted`(注释不进 dex),
  重跑整类跳过,输出逐字节稳定
- **组件标记**(`<解包目录>/stringenc-components.json`):记录"描述符 + 源文件路径",
  回编会重新分派 dex 号,这是唯一稳定的定位依据(报错十八式:信息在丢失前 save)
- 【审查点】`clean` 只删标记里登记的路径且要求文件含生成标记,
  绝不越界、绝不误删用户自己的类

**联动路径(勾 `--dex2c-stub`,须同时勾 `--dex2c`)**:顺序反转为
「stringenc 前置 → dex2c 转译 → mark-native」,详见 §3.7.4.1。
此时 STEP 5 的 stringenc **整段跳过**(二次加密会包两层密文 → 整包乱码),
且 `--exclude-methods` 失效(前置轮跑时还不知道哪些方法会被抽走,
后果仅体积：被抽方法里的字符串白加密后随方法变 native 壳,正确性无碍)。

### 3.7.8 与其余模块的组合

| 组合 | 行为 |
|---|---|
| 只勾 stringenc | 只加密 + 注入桩,不碰 so/签名校验 |
| sigcheck + stringenc | so 侧校验照常;dex 侧字符串加密,两者互不影响 |
| dex2c + stringenc(不勾联动) | dex2c 抽走的类其字符串随方法进 so(被 `--exclude-methods` 跳过),未被抽走的类留在 dex 加密;**解包/回编仍为 1 次** |
| dex2c + stringenc + `--dex2c-stub` | 桩内核一并进 so,dex 只剩三行壳;**解包/回编变 2 次**(+30~60s) |
| 三者全勾(不含联动) | 共用**一次**解包/回编 |

## 3.8 防对比混淆模块(protect.sh --anti-diff)

> 新增 dex 层模块,与 stringenc 正交,**默认不勾**,勾了才在 stringenc 之后执行。
> 设计与验收标准见 `docs/archive/开发文档-anti-diff.md`(已归档;MVP 只做 A+B+C 三变换,
> 全部变换实际已落地,红线部分仍有效)。

【目的】攻击者手上有原版 APK,反编译两份做逐文件 diff 时,被 dex2c/stringenc
改动的类"稀疏、可定位"。本模块给全量 smali 加**零语义无损**的结构噪声,
让 diff 结果"整包全红、像不同编译版本",掩盖真正被保护的那一个类。

【三变换(MVP)】

| 变换 | 内容 | 跳过规则(与开发文档 §5.2 一致,见归档文档) |
|---|---|---|
| A 标签重命名 | 方法内 `:cond_0`/`:goto_0` 等 → `:ncXXXXXX` | `<init>`/`<clinit>` |
| B 类内块重排 | `.method`/`.field` 块确定性乱序 | `<init>`/`<clinit>`、含 `.annotation` 的块钉在原地 |
| C 入口垃圾指令 | 方法首插 1~3 条 `const/4`/`move` | `<init>`/`<clinit>`、native、含 try-catch、`.locals < 4`、`.registers` 模式 |
| C+ return 前插桩 | 每个 `return` 前插 1~3 条(打破"只插方法开头"的可识别模式,实际效果.md 反馈) | 同 C;ban 被 return 读取的寄存器与 return-wide 伴生寄存器 |
| E 条件反折 | `if-eqz vX, :L` → `if-nez vX, :新` + `goto :L` + `:新`,真实多 1 条 goto 落 dex | `<init>`/`<clinit>`、native、含 try-catch、fall-through 恰为目标的分支;单方法最多 `--max-cond-flip`(默认 3)处 |
| F 恒等算术重编码 | `shl-int/lit8 vA, vB, k` ⇄ `mul-int/lit8 vA, vB, 2^k`(22b 等长 4 字节,32 位补码下数学恒等,乘 2 的幂的 mul 形态 R8 强度削减从不产出,零体积零性能);**已并入模块本体固定开启**(v1.2 回退:原子复选框「恒等算术重编码」schema `antidiff.reencode` 删除,勾不勾无意义——零损耗功能随模块一起走;流水线对 anti-diff.py 无条件传 `--enable-f`) | `<init>`/`<clinit>`;移位量 k=0 与 k>6 不转(2^k 超出 8 位字面量域);`lit16`/`2addr` 相邻形态不碰(编码格式不同,互转不再等长) |

> **报错三十一(阶段 2 增强 + 真实包回编暴露的 smali 语法炸点)**:新增
> E/C+ 后真实包回编报 `no viable alternative at input 'const/4'`。最小复现
> (apktool 3.0.3 内置 SmaliBuilder)钉死根因:**标签定义行带尾冒号**
> (`:ncXXXXXX:`)且"下一非空行是指令"时解析炸(尾冒号 + 后续 `return`
> 或另一标签定义则能宽容通过,极具迷惑性);baksmali 真实产物 100% 无尾
> 冒号。修复:E 生成的标签定义行去掉尾冒号。教训:**smali 是宽容编译器,
> 但宽容与否取决于上下文 token 组合——"最小 smali 验证一次"不够,必须
> 用真实包全量回编闭环验证;探针(最小 smali + SmaliBuilder.buildFile
> 单文件汇编)是定位此类语法炸点的有效手段**。

【红线(开发文档 §2.2,审查时逐条对)】不改类名/方法名/字段名/签名/字符串;
不注死代码/死方法/nop;不做控制流平坦化。

【幂等】每个处理过的类写入 `# nc-antidiff-applied v1` 标记注释,重跑整类跳过;
种子 = SHA-256(全部 smali 相对路径+内容),同输入跑两次产物逐字节一致。

【在流水线里的位置】

```
mark-native.py → encrypt-strings.py → 【anti-diff.py】→ repack_build
```

放最后的原因:stringenc 会改 `const-string` 并插桩,若 anti-diff 先做、
stringenc 后做,stringenc 的新差异会落在 anti-diff 的"已处理"区域上,
削弱防对比效果。

【审查点】
- 变换 C 的跳过条件必须**全部满足才插**,缺一条都不许插(开发文档 §5.2)
- native 方法(dex2c 抽走的)没有任何方法体,天然跳过,不得为其生成任何指令
- 标记注释 `# nc-antidiff-applied v1` 是幂等锚,**不许改格式**(改格式 = 老包重跑会再处理一遍)
- 与 dex2c/stringenc 组合时:anti-diff 不读 compiled_methods.txt,靠"native 方法无体"
  与 `<init>/<clinit>` 跳过天然避开敏感区,这是设计约定,不是漏判

## 3.10 基础加壳模块(protect.sh --packer)

> 工具为 `tools/dpt-shell.zip` 里的 **dpt-shell**(`executable/dpt.jar` +
> `shell-files/`),版本登记见 `tools/工具包版本.md`。模块本体 `scripts/packer/packer.sh`。
> **默认不勾**;勾了则固定排在所有模块之后。

【目的】前面所有模块(dex2c / stringenc / anti-diff / sigcheck)都是**局部**保护:
攻击者拿原包一对比就能定位差异类。基础加壳把 dex 整体加密、真实方法体搬进
native 壳,静态反编译拿到的只是一层壳,和原包无法直接对比——它是**兜底层**,
不是替代前面那些模块。

【CLI 契约】`scripts/packer/packer.sh <输入.apk> <输出.apk>`
(独立脚本,不 import 仓库内其他模块内部函数;公共能力只 source `scripts/lib/common.sh`)。

【实际调用的 dpt 命令】

```bash
java -jar dpt.jar -f <对齐后的输入.apk> -o <dpt 工作目录> -x \
     -r executable/dpt-exclude-classes-template.rules
```

| 参数 | 取值 | 为什么 |
|---|---|---|
| `-r` | 包内自带的 `dpt-exclude-classes-template.rules` | 不加固系统库/三方库(`android./androidx./java./kotlin./com.google` 等),加壳后启动失败面更小 |
| `-x` | 必带 | dpt `Builder` 默认 `sign=1`,会用包内 `assets/dpt.jks` **重新签名**;本仓库契约是"产出未签名包,开发者自行重签",所以必须走 `-x` 的 `_unsign` 分支 |
| `-o` | `$WORK/dpt-out` | 工作目录,产物名由 dpt 决定 |

> **⛔ 规则语义反转(最容易静默出事的一处)**:`-r` 的规则语法是 **dpt 自己的斜杠正则**
> (`Lafzkl/development/.*`),**命中 = 不加固(保持明文)**。而 dex2c/stringenc 用的是
> 本仓库的点号通配符(`com.test.**`),`!` 开头 = **排除处理**。两者语义**相反**且
> 书写形式不同,所以 `packer` 在 schema 里做成 **leaf(无子选项)**:不共用规则面,
> 零规则面 = 零风险。谁要在加壳时排除类,只能改包内那份模板 rules,不许从 UI 传。

【在流水线里的位置(与 §0.1 执行顺序对应)】

```
…各模块 → repack_build → finish_apk(zipalign) → aligned.apk → 【packer.sh】→ 产物
```

两条铁律:
1. **吃的是"已对齐的包"**:`protect.sh` 先 `finish_apk "$WORK/unsigned.apk" "$WORK/aligned.apk"`
   再交给 packer。不对齐的包喂进去,dex 偏移不合法,dpt 直接抛异常。
2. **产物不再走 `finish_apk`**:加壳已经重写了 dex/so/Manifest,packer 产物**直接作为
   最终输出**。二次 zipalign 属于对已加壳包的二次改写,可能破坏壳的对齐假设。

【产物取用】dpt 的输出文件名带自己的命名规则(`_*_unsign.apk` 形态),脚本用
`find "$DPT_OUT" -maxdepth 1 -name '*_unsign.apk'` 扫描,**不硬编码文件名**;
命中 0 个或多个都 fail-fast,不瞎猜——避免 dpt 换版后静默拿错文件或拿空。

【解压布局(不可改)】dpt 的 `getExecutablePath()` = **jar 所在目录**,所以
`shell-files/` 与 `build-key` 必须和 `dpt.jar` **同级**。`dpt-shell.zip` 内顶层即
`executable/`,解压目标固定为 `tools/`,得到单层 `tools/executable/`(与 `dcc.zip`
形态一致;报错十五:unzip 不自建多级父目录)。解压幂等:`$DPT_EXE_DIR/dpt.jar`
存在则跳过。解压后额外校验 `shell-files/` 是否同级存在——布局错位(多套一层
`executable/`)时提前人话报错,而不是让 dpt 抛一句难懂的缺文件错误。

【文件权限】`scripts/packer/packer.sh` 必须是 **100755**:`protect.sh` 是**无
`bash` 前缀直接调用**它的(`"$ROOT/scripts/packer/packer.sh" "$ALIGNED" ...`),
本地 umask 产生 0700 时 GH runner 以非 owner 身份执行会 `Permission denied`。

【审查点】
- [ ] `-x` 必须还在——去掉就会静默重签(违反"未签名产物"契约)
- [ ] `-r` 指向的 rules 存在且非空(`require_nonempty_file` fail-fast,不许静默降级成"全量加固")
- [ ] packer 拿到的是 `aligned.apk`,不是 `unsigned.apk`
- [ ] packer 产物没有再被 `finish_apk` 二次处理
- [ ] 产物扫描用 `find` 而非硬编码文件名;0 个/多个都要报错
- [ ] 解压目标仍是 `tools/`(单层),`shell-files/` 与 `dpt.jar` 同级
- [ ] `scripts/packer/packer.sh` 是 100755(protect.sh 无 `bash` 前缀直接调用,0700 会让 runner Permission denied)
- [ ] 规则语义:命中 = 不加固(与 dex2c/stringenc 相反),schema 里 packer 不得挂子选项

## 3.11 Java 层判决式签名联动(protect.sh 随 --sigcheck 自动生效,无独立勾选)

> 模块位置:`scripts/sigcheck/javalink/`(注入器)+ `scripts/sigcheck/src/nc_link.c`
> (so 侧判决)。2026-XX 用户需求:修复"sigcheck-only 模式下删 loadLibrary 即
> 静默绕过"的最大缺口,并让 Java 层从 0 防御变为真实联动,同时【不削弱】so 层。

【架构:判决式,用户拍板】Java 只"量"并执行杀,标准值与比对全在 so:

```
Java(Guard/自适应命名)                    so(nc_link.c,标准值不出 so)
  ①量 PackageManager → fp=SHA256(证书DER)
  ②t1 = SHA256(fp)  ──JNI ncVerify──►  ③还原:out[i]=t1[i]^SIG_SALT[i%16]^(i*0x9E&0xFF)
  ④收:过/不过 ◄──────────────────────    恒定时间比对 out == SIG_HASH_STORED
  ⑤不过/so缺失 → killProcess            (复用 sig_hash.h,零新增头文件字段)
另有一套:sig_check.c 独立直读 APK 文件校验(一字未动,权威兜底,延时暗杀)
```

- **为什么不"答案下发 + Java 比对"**:指纹本身不是秘密(原包公开可算),
  但把标准值放进 dex = 攻击者可原地改值/读形;判决式下 Java 层无标准值、
  无经典比对形状(用户"前缀对比"直觉的更强形态:答案根本不过境)
- **三条分支**:判定不过 → 杀(快死/可见);`UnsatisfiedLinkError` → 杀
  (fail-closed,loadLibrary 由"可删开关"变"承重墙"——独木难支的病根解法);
  其他 Throwable → 静默跳过(测量环境异常不误杀,so 层仍是权威)
- **心跳喂食点**(报错四十九 修复):`ensureLoaded() → heartbeat() → startHeartbeat() →
  测量链 → ncVerify`。喂食必须与"测量是否成功"解耦——旧形态放在 ncVerify 通过之后,
  测量抛非 ULE 异常经 `:catch_skip` 静默返回 → 一次不喂 → `env_watchdog` 把"没喂"
  误判成"Java 壳被删" → 正常包冷启动 ~6s 被杀(真机实证 docs/sigcheck_log.txt)。
  前移后:删 `c()` 调用仍不喂 → 杀(核心场景不变);测量异常只损失 Java 判决
  (so 层 constructor 照跑,与上方"三条分支"自洽)
- **结构性依赖的边界**(诚实口径):单删 loadLibrary → Java 侧当场杀;
  攻击者把全部调用点+Java 校验删净 → 回到"so 单独裁决"(=现状,不弱于现状);

## 3.12 so 静态加固(.ncguard 段自解密,随 --sigcheck 自动生效,无独立勾选)

> 模块位置:`scripts/lib/so-section-lock.py`(构建期锁箱)+ `scripts/sigcheck/src/nc_guard_*.c`
> (运行期开箱)。2026-12 用户终极需求:**让 AI 静态分析 `libnc.so` 的 token 消耗上去**。
> 机制抄自 XopProtector 的 `.bitcode` 自解密( Android so 上唯一成熟实现),
> **抄机制不抄代码**(它的 Java 侧 packer 无法复用,Python 侧重写)。

【架构:磁盘密文 / 内存明文】

```
构建期(so-section-lock.py)                运行期(nc_guard_unlock.c)
  读 libnc.so 段表                          dladdr 定位自身 so 基址
  ↓                                         ↓
  .ncguard ← RC4 加密写回(等长)             open(so) + pread 读密钥槽
  .nckey   ← wrapped 密钥(32 字节)           recover_key → mprotect(RWX)
  ↓                                         ↓
  cert/pkg 从 APK 提(HKDF)                 RC4 解密到 .ncguard 原地
                                           clear_cache + mprotect(RX)
  磁盘上 IDA/strings 读到:密文             此刻才可执行该段代码
```

【密钥派生(证书绑定,Xop 原设计)】

```
k_so = HKDF-SHA256(ikm=master, salt=SHA256(certDER), info="nc-so-v1"+pkg, 16)
       certDER = APK 第一签名者证书(锁箱脚本定点读 EOCD/CD/Signing Block)
换 key 重打包 → certDER 变 → salt 变 → k_so 变 → 密文解不开(fail-closed)
```

- **与 Xop 的刻意偏离**:Xop 在**运行期**读 APK 提证书,我们把派生放在**构建期**、
  slot 只存 wrapped → C 侧零 I/O、不拖冷启动(交替测量 8 轮无可测劣化)
- **为什么必须证书绑定**:密钥若是公开脚本算出的常量,攻击者自己跑一遍即可解密,
  4012 字节密文秒变明文 —— 等于没锁

【位置与触发】

- **锁箱点**:STEP5 解包后(`repack_unpack` 之后、`repack_install_so` 之前)——
  so 已编译完但还没进 APK,锁的是即将打包的产物
- **首次解锁**:`selftest()`(Java 侧 `NcLink.selftest()`)与 `env_check_entry`
  的 constructor 各一次,**进程内 static 标志保证只解一次**
- **Java 观测入口**:`NcLink.selftest()` 返回 `59`(完整链路通过)/
  `-100`(原子守门挡重入)/ 负数(解锁失败,码表见 `nc_guard_unlock.c` 注释)
- **回执判读**:`adb logcat -s ncguard` 无输出 = rc==59;有 `selftest rc!=NN` = 未达标

【体积与内容】

| ABI | 密文大小 | 内容 |
|---|---|---|
| arm64-v8a | 4012 B | 12 个 `env_check` 探针 + 1 个 `ncguard_probe`(共 13 处 `section(".ncguard")` 标记) |
| armeabi-v7a | 2750 B | 同上 |

【审查点(改 nc_guard_*.c / so-section-lock.py 前必读)】

- [ ] `retain` 不可省:`lib-ndk.sh` 的 `LOC_LDFLAGS` 含 `-Wl,--gc-sections`,
      漏 `retain` → 两段被静默回收 → 锁箱报"段不存在"
- [ ] **HMAC 三处 80 字节契约必须同步**:`nc_guard_probe.c` 的 `ncg_key_slot[80]`
      (它就是 `.nckey` 段的全部内容)、`nc_guard_unlock.c` 的 `NCG_SLOT_SIZE 80`、
      `so-section-lock.py` 的 `assert len(blob)==80`。长度不一致在**构建期**就
      AssertionError fail-fast(好事),但改动时漏同步会让 CI 白跑一轮
- [ ] **k_mac 与 k_so 必须用不同 label**(`nc-so-mac-v1` vs `nc-so-v1`):复用同一把
      钥匙 = 攻击者知道 RC4 密钥即可伪造 MAC,校验形同虚设。改 label 必须同时改
      Python 的 `derive_app_keys()` 与 C 的 `ncg_derive_k_mac()`
- [ ] MAC 必须对【密文】算(不是明文),且校验必须在 `mprotect`/RC4 **之前**:
      放解密后就等于"篡改的明文已生效"才报错,晚一步
- [ ] `have_mac` 必须同时判 `pread` 返回值与 `slot.sh_size`:只判前者会把
      `.nckey` 之后 48 字节(别的段数据)当期望 MAC → 畸形 so 误判 `-11` 自锁

### 3.12.1 三层设施与消费者（2026-10-18 设施化重构）

这套东西**不是某个模块的加密器**,是全项目共用的 so 段加密服务:

```
第1层 段加密服务（设施本体,改一次全项目受益）
   nc_guard_unlock.c    运行期开箱:RC4 + HMAC + mprotect + clear_cache
   so-section-lock.py   构建期锁箱:HKDF 派生 + 等长加密写回
   nc_guard_key.c       SHA-256/HMAC/HKDF/证书 DER（契约可执行证明）
   nc_guard_probe.c     .ncguard/.nckey 两段的唯一定义处 + 样例消费者
        ⚠️ 它的头部曾写"试探性文件,验证通过后可整体删除"——【错】,
        ncg_key_slot[80] 就是 .nckey 段全部内容,删它 = 段消失 = 起不来

第2层 通用标记器（规则引擎,零模块逻辑）
   scripts/lib/so_section_mark.py
     --rule dex2c-jni    匹配 JNIEXPORT/JNICALL 函数头（dex2c 产物）
     --pattern REGEX     自定义（未来模块自己写一条即可）
     --exclude NAME      排除不能被锁的文件（典型:nc_guard_jni.c）
   特性:幂等(重复跑 md5 恒定) / 只标定义不标声明 / --check 预检 exit 3

第3层 消费者（各自零侵入,不需要知道加密怎么实现的）
   sigcheck/envcheck 探针  env_check.c 手写 __attribute__（冻结,只追加）
   dex2c 转译产物          经标记器 --rule dex2c-jni
   未来新模块              加一条规则,不动第1层
```

**为什么必须分层**:如果不做第2层,dex2c 要后处理注入、stringenc 又要另想一套,
就是"每个模块单独写防御"。分层后加消费者 = 加一条规则。

**新消费者的接入清单（照此走,缺一不可）**:
- [ ] 标记器规则能命中它的函数头（用 `--check -v` 确认,不许只看正则可编译)
- [ ] **它有 unlock 触发点,否则必炸**:unlock 的三个触发源是
      ① `ncg_auto_unlock` constructor(兜底,so 加载即跑,`unlock.c` 尾部)
      ② Java 侧 `NcLink.selftest()`(随 `--sigcheck`)
      ③ `env_check_entry` constructor(随 `--sigcheck`/`--envcheck`)
      只勾 dex2c 时只有 ① —— 这正是当初"接入即必炸"的坑:
      `protect.sh` 无条件拷 `nc_guard_unlock.c`,但没人调它,
      锁了永不解 → 调第一个转译方法即 SIGILL
- [ ] **unlock 的调用方本身不能被锁**:`nc_guard_jni.c` 必须进 `--exclude`,
      否则"开锁器被锁进箱子"→ 死锁
- [ ] 端到端:锁箱后 dlopen → 自动解锁 → 函数返回正确值（不是只验符号存在）

### 3.12.2 自解谜（2026-10-18）：把开锁器也锁进箱子

针对外部逆向报告（`docs/so层防御/简盒-06` §6.2）实测结论——「解锁逻辑本身是明文，
读函数反汇编就知道怎么解」——本轮把 unlock 本体也锁进密文段。这是唯一能把攻击者
从静态逼到动态的改动（其余加固都作用在已运行的进程上）。

```
.text 明文 stub（ncguard_unlock/ncg_stub_recover，约 200 行反汇编）
   读 .nckey_stub → 验 magic → 恢复 k_stub → mprotect RWX → 简单 XOR
   ↓ 解出
.nckey_stub（32B）magic(8)+wrapped_k_stub(16)+head_size(4)+entry_delta(4)
.nckey_head 密文段 = .ncguard_head（1500B，unlock 本体）
   ↓ 由 constructor(50) 调 ncg_head_unlock
.nckey 密文段 = .ncguard（业务：dex2c 产物 + 12 探针）
```

**审查点（改 nc_guard_boot.c / lock_head() 前必读）**：

- [ ] **`ncg_head_unlock` 绝不能被标记进 `.ncguard`**：它得先被 stub 解出来，
      标进去 = 死锁。标记器对 `.ncguard_head` 段内容不生效（段名不同），
      但手工加 `__attribute__((section(".ncguard")))` 到 head 段任何函数上
      都会造成此问题
- [ ] **stub 与 `lock_head()` 必须同算法**：stub 是简单循环 XOR
      （`start[i] ^= k[i & 15]`），锁箱侧也必须是简单 XOR。
      ⚠️ 2026-10-18 实测踩过：lock_head 抄了 `rc4()`，两边不一致 →
      解出乱 C → dlopen 即 SIGILL（exit 132）。刻意不用 RC4 的理由：
      stub 里不能出现 256 字节 S 盒初始化循环（那是"这是 RC4"的活招牌）
- [ ] **`k_stub` 与 `k_so` 必须是两把钥匙**：复用 = 解开 head 就等于拿到
      业务段钥匙，分级失去意义
- [ ] **二级锁箱必须 fail-fast**：stub 见 slot 无 magic 会静默放行 → head
      保持明文 → 自解谜没发生 → 静态攻击者照旧读 unlock 本体。
      `protect.sh` 的 `--lock-head` 失败即 exit 1，不许降级
- [ ] **`.symtab` 不能被 strip**：`lock_head()` 靠它算 `entry_delta`
      （入口符号地址 − 段起始）。符号缺失会 fail-fast 报错，
      而不是拿错地址去锁（错地址 = stub 找不到入口 = 起不来）
- [ ] stub **不依赖 libc / 不读盘**：`memcmp`/`memcpy` 手写，段地址由
      `&符号`（PC 相对）取得。用了 dladdr 就等于多一个明文依赖
- [ ] 零冻结路线：`nc_guard_unlock.c` 保留在仓库但**不再进 NDK 工程**
      （protect.sh 改拷 boot.c）。unlock.c 自此是历史存档，不再维护

### 3.12.3 head 段 MAC 与密钥分离（2026-10-18 P0-a / P0-b）

针对强度报告（`docs/so层防御/简盒-07` §2.2/§5）指出的两个缺口。

**P0-a：三把钥匙不再共用一串字节**

此前 `XOR_KEY` 同时护三处——`.ncguard` 的 wrapped_k_so/wrapped_k_mac、
`.ncguard_head` 的 wrapped_k_stub、以及 `make-sig-log.py` 的中文日志 XOR 密文。
而 LSGS 侧自己的注释就写着"不抗人工逆向"，共用的后果是**破掉最脆的那套，
强的一起破**。现在：

| 用途 | 密钥 |
|---|---|
| nc_guard（`.ncguard`/head 段 wrapped） | `7e31a50dc8924bf6`（`NCG_XOR_KEY`） |
| LSGS 中文日志密文 | `5ac3119ef037b26d`（`make-sig-log.py` 的 `key`，未动） |

**P0-b：head 段也有 HMAC 了**

在此之前 head 段只有简单 XOR。攻击者可改 head 密文中对应"unlock 本体的 MAC
校验函数"那几位 → 解密后 unlock 本体还在，但它对 `.ncguard` 的校验被改成恒真
→ `.ncguard` 的 HMAC 保护被绕过。这是具体路径，不是理论风险。

`.nckey_stub` slot 从 40 → **88 字节**，新增两段：

```
[40:56) wrapped k_mac_head   k_mac_head ^ XOR_KEY
[56:88) expect_mac_head      HMAC-SHA256(k_mac_head, head 密文)
```

stub 在 `mprotect`/XOR **之前**校验，不符即拒解（不解密、不动权限、head 保持
密文），与 `.ncguard` 的 `-11` 语义完全对等。`k_mac_head` 是第三把独立钥匙
（与 `k_stub`/`k_so` 都不同）——复用任何一把都意味着"解开 head 就等于拿到
业务段的钥匙"或"知道解密钥匙即可伪造 MAC"。

**审查点**：

- [ ] **三处 88 字节契约必须同步**：`nc_guard_boot.c` 的 `NCG_STUB_SIZE`、
      `ncg_stub_slot[NCG_STUB_SIZE]` 数组、`so-section-lock.py` 的
      `assert len(blob) == 88`。不一致在构建期即 AssertionError
- [ ] **`k_mac_head` 必须独立于 `k_stub`/`k_so`**（同理 stub 与 so 域也须独立）
- [ ] MAC 必须对【密文】算，且校验在 `mprotect`/解密**之前**——放解密后
      等于"篡改的明文已生效"才报错
- [ ] **拒解必须是"不解密"而非"解密后放弃"**：只改 slot 里的 expect_mac
      （密文本是好的）也必须拒解，否则说明校验没真的生效
- [ ] `NCG_XOR_KEY` 与 LSGS 的 `key` 必须是两套值；改一侧不得牵动另一侧
      （`make-sig-log.py` 的 key 保持 `5ac3119ef037b26d` 不动）

### 3.12.4 熵值安检（2026-10-18）：防"加密悄悄失效了却没人知道"

so 加密是**自动捆绑**层——用户没有勾选框可取消，勾了 sigcheck/dex2c/envcheck
任一就自动跑。一旦锁箱静默失效（段缺失却返回成功码、某次改动把明文写回），
流水线全绿、app 正常，用户完全感知不到。这类"静默失效"比漏洞本身更危险。

`so-section-lock.py` 的 `check_entropy_or_fail()` 在**写盘前**自动抽检：

```
锁箱 → 算目标段香农熵 → 低于 7.0 即 fail-fast → 坏包不落盘
```

**阈值依据**：RC4 输出是伪随机流，熵必然接近 8.0（实测 `.ncguard_head`
1500B 锁后 7.400）；普通机器码只有 6.3~6.9。中间有明显间隙，7.0 是安全线。

**必须记住的局限（强度分级不同）**：

| 段 | 加密方式 | 校验强度 |
|---|---|---|
| `.ncguard` | RC4 | **强**：RC4 保证拉高熵，明文 6.3 → 密文 7.9+ |
| `.ncguard_head` | 简单 XOR | **弱**：XOR 不保证改变熵（实测合成样本 7.997 经 XOR 反降到 7.029） |

head 段这道安检真正有效，靠的是**真实机器码熵稳定在 6.3 左右**、与锁后
7.400 之间那 1.068 的间隙。若 head 段内容本身是高熵数据，安检可能漏放——
所以别把它当 head 段的完整性保障，那由 HMAC 负责（见 §3.12.3 P0-b）。

**审查点**：

- [ ] 熵值检查必须在**写盘之前**：放到写盘后，fail-fast 时坏包已落盘，
      会被后续步骤当成有效产物
- [ ] **样本量门槛 256 字节**：N 字节的段熵理论上限是 `min(8, log2(N))`，
      24B 的上限仅 4.59——不设门槛会把小段密文误判为明文（2026-10-18
      实测踩过这个假阳性：24B 的 `.ncguard` 熵 4.502 被判失败，而那其实
      是接近满值的随机数据）
- [ ] 跳过判断时打印的是"样本不足跳过"而非"熵 0.000 ✅"——后者看着像
      "熵为 0 却通过"，会误导人（也踩过）
- [ ] **绝不在运行时 `pwrite` 修改磁盘 so**:`.text` 是 `MAP_PRIVATE` 文件映射,
      pwrite 会使同页映射失效;而 `.ncguard` 与 `.text` 尾部**同属一页**
      (真机 0x95f4 vs 页首 0x9000)→ 连带写坏 104 字节代码 → SIGILL(报错五十)
- [ ] `mprotect` 必须给 `PROT_READ|PROT_WRITE|PROT_EXEC` 三者:漏 `PROT_EXEC`
      → 重入 RW 页 SIGSEGV(真机实测)
- [ ] ELF32 与 ELF64 三处差异必须照顾:`e_shoff` 0x28/0x20、`e_shnum` 0x3C/0x30、
      `e_shstrndx` 0x3E/0x32(报错:armeabi-v7a 曾报 `only ELF64 supported`)
- [ ] python 改段内容必须**等长覆盖**:`bytearray[a:a+16] = blob` 是插入不是覆盖,
      32 字节 blob 塞进 16 字节切片会损坏段表
- [ ] selftest 必须挂 `NcLink`(与 `ncVerify`/`heartbeat` 同源):另造独立类则
      dex 里没这个类 → `UnsatisfiedLinkError` → catch 吞掉 → **连带跳过心跳**
      → watchdog 误杀(报错四十九复现)

### 3.12.5 密钥碎片化与符号名暴露面(2026-10-18)

**密钥碎片化(w_step01,已落地)**:`XOR_KEY` 不再以整串 8 字节出现在 `.rodata`,
改为 4 个 `volatile uint16_t` 碎片(落在 `.data`)+ `NCG_XOR_FRAG[8]` 查表 +
「i<4 取低位、i>=4 取高位」重组规则,运行期由 `ncg_xor_key()` 拼回,调用方用完
`memset` 擦除。所有恢复点(k_so / k_mac / k_stub / k_mac_head)一律经该函数取
钥匙,**不许再直接引用整串 `NCG_XOR_KEY`**。

- [ ] **必须用 `volatile`,不能只是拆成常量/函数**:第一版把 4 个 uint16 常量放
      4 个 `noinline` static 函数,实测 LLVM 函数间常量传播把完整密钥折回
      `.rodata`(boot.o 0x5b0/0x5b8 仍各一份连续 8 字节)。
      **只有 volatile 这类标准级屏障才真阻断折叠**——`noinline` 不算
- [ ] 验证方式:对最终产物搜连续 8 字节密钥 hex,**命中数必须为 0**;同时按
      小端 uint16 从 `.data` 段读 4 个碎片,值必须与源一致(证明碎片没被
      优化器抹掉,只是换了位置)
- [ ] 碎片不得合并回单一 `uint8_t[8]` 全局量——那等于没拆
- [ ] `ncg_xor_key()` 每次调用重算、**不缓存**:缓存就是又把密钥写进内存
      某处;调用方用完必须 `memset` 擦除临时副本

**符号名暴露面(w_step02,结论是"无需改动")**:真实 NDK 构建带
`-fvisibility=hidden`(lib-ndk.sh:26-27)且 strip `.symtab`,CI 真产物 `.dynsym`

## 4. 关键格式规范(审查任何改动时先对表)
### 4.1 dex2c full_name(方法指纹的唯一真相)

```
<class_name><method_name><proto_with_return_type>
例: Lcom/demo/app/MainActivity;onCreate(Landroid/os/Bundle;)V
     ^^^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^
     smali 斜杠类名(含 L 与 ;)   方法名   参数原型含返回类型
```

- 拼接代码:`dcc.py compile_dex()` 中 `''.join(method_triple)`
- class_name 来源:dex 描述符(androguard 原样返回,斜杠)

### 4.2 compiled_methods.txt

- 位置:`dcc-project.zip → jni/nc/compiled_methods.txt`
- 每行一个 full_name(格式同 4.1),由 `write_compiled_methods()` 写入
- `mark-native.py` 用正则 `^(L[^;]+;)([^(]+)(\(.*\)\S+)$` 解析

### 4.3 JNI 函数名(生成 cpp 的函数头)

- `Java_<pkg斜杠转下划线>_<Class>_<method>__<proto参数mangle>`
- `.` 和 `/` → `_`;`_` → `_1`;`;` → `_2`;`[` → `_3`
- 函数靠 JNI 命名规范自动绑定,**不需要 RegisterNatives**
- 改类名/方法名会断绑定,审查时警惕

### 4.4 filter 文件语法

```
!<正则>   排除:命中则强制不转译(优先级最高)
=<全名>   精确匹配转译
<正则>    search 命中即转译
# 注释、空行跳过;首部固定加 !<clinit|init>
```

   真正按继承链识别需要解析 dex,目前未做。
2. **dex2c 的 `dcc.py` 静默吞错**:`dcc()` 异常只 log 不退出,所有"转译失败"都要靠
   工程包存在性检查兜底。给 dcc.py 本身加退出码属于改动第三方,暂不做。
3. **sig_check.c 的校验时机**:constructor 在 so 加载时执行,而 so 由
   `<clinit>` 的 loadLibrary 触发——即校验发生在**首个被抽取方法所在类
   初始化时**,早于该方法执行,满足方案要求;但不早于 App 其它未抽取代码
   (这是设计内的取舍,联合方案靠"抽取的是 LAUNCHER activity"保证足够早)。
4. ~~单独 dex2c 的 Application.mk 还是 v7a 单 ABI~~:已统一——
   protect.sh 步骤 3 现与联合勾选一样覆写为
   `APP_ABI := armeabi-v7a arm64-v8a`(APP_PLATFORM 同为 android-21)。
5. **重签名指纹**:`sig_hash.h` 在流水线提取的是**上传时** APK 的指纹;
   开发者重签必须用同一 keystore。若 SaaS 场景要求用户上传 keystore,
   属于新需求,当前流程不支持。
6. **字符串加密 != 密码学安全**:salt 与密文同处一个 dex,懂格式者可依样解密。
   防的是 `strings` 一眼可见与静态特征扫描,不是有心人的定向逆向;
   真正的密钥材料必须走服务端/白盒方案,不要依赖本模块。
7. **字符串加密的覆盖边界**:注解值、Manifest/资源字符串、字段名/方法名/类名
   一律不加密(见 §3.7.1)。若用户期望"注解里的明文也消失",属新需求。
8. **字符串加密未做 dex 直改**:走 smali 改写 + apktool 回编,因此继承回编的
   全部保真风险(`--no-debug-info` 与 dex 版本 save/restore 已覆盖,见报错八/十八)。
   极端情况下若回编本身不可用,本模块也无法工作。
