## 1. 讨论过程（用户原话按时间序 + 我们的理解）

### 1.1 起点：随机桩防不住「发给 AI」

> **用户**：「增加了随机桩只防得住一键脚本，那现在还有什么防御加强手段吗StrDec目前对方进入这个类发给ai就能轻松破解」

**我们的理解**：威胁从「引擎固定签名/一键脚本」升级到「针对性 AI 分析」。
对手只要把桩类 smali 发给 AI 就能破解，因为三个铁证：①算法标准（splitmix64
的 `0x9E3779B97F4A7C15` 常量一眼可认）②全包调用点单点汇聚（随机名不改变
「唯一汇聚点」结构）③种子静态编在指令流里。目标 = **把解密器移出 dex 或
使其不可读**。

### 1.2 第一反应：把 StrDec 类也 dcc 了 + 联动自动填入

> **用户**：「走dcc的话会不会有性能影响因为整个项目都要进过解密不是吗？，
> 还有我们是随机桩，怎么在联动的时候直接把字符串加密的类dcc了
> （这个得做联动自动填入而不是填自己手动类名了）（你分析先）」

**我们的理解（请核对）**：「字符串加密的类」= **随机桩类本身**，不是被加密
的业务类。理由：「我们是随机桩」是因果前提 —— 桩名每包构建期才知道，
手动填 dcc 规则走不通，所以必须联动自动填入。
——**若用户本意是「把被加密的业务类 dcc」，我们整段分析对象就错了，请指出**。

**我们的分析与行动**：
- 性能：桩 dcc 后每次解密 = **2 次 JNI 往返**（进 native + native 反调桩内
  Java `ConcurrentHashMap`）；「整个项目都经过解密」量级不大（L1 缓存后
  冷启动全链仅 10-20ms，非性能大头，启动大头是 VerifyClass + 解释执行）
- 机制阻塞：dcc 跑 STEP2、桩是 STEP5 才注入，且 dcc 要求类文件**已存在**。
  自动联动 ≠ 规则文件拼接，而是流水线顺序手术：桩注入前置 + dcc 规则
  自动追加随机桩名（当时称「方案 E」）
- **真机验证**（用户提供测试包 `简盒_字符串加密类被dcc.apk`）：无崩溃、
  界面全部字符串正确解密（截图验证）、冷启动 ~173ms vs 原生同日对照
  ~181ms —— 三关全过、无劣化。详见 `docs/简盒-字符串加密与StrDec类dcc测试报告.md`

### 1.3 性能观察：差不多，且可能 C 层更快

> **用户**：「其实差不多你发现没有」
> **用户**：「会不会是因为dcc的原因让解密在C层速度更快了」

**我们的回应**：机制上成立 —— 冷启动 1-2 万次解密全走缓存 miss 路径，
C 层解密省掉等量 byte[]/String 对象分配、无边界检查；缓存命中路径反而
C 更慢（多一次 JNI）。但本次对照组是**原生包（无解密可比）**，
173 vs 181ms 在噪声内，**数据无法区分该假说**；坐实需要第三组对照包：
同流水线、同样 `**` 全量加密、**桩不 dcc（纯 Java 桩）**。

### 1.4 关键转折：为什么不直接写 C 层加解密（**本节是审核重中之重**）

> **用户**：「然后你在去把字符串加密和dcc联动写出来（比如json里面字符串加密
> 加一个子复选框dcc解密类），然后我有一个问题那我们dcc的话为什么不直接写一个
> C层字符串加解密呢这样字段也不会出现在java层（我这是开智了吗？）」

**我们的理解（请逐句核对）**：

| 用户原句 | 我们的理解 | 需核对 |
|---|---|---|
| 「把字符串加密和dcc联动写出来（json 里字符串加密加一个子复选框 dcc 解密类）」 | 明确指令：落地方案 E 的联动 —— workflow 配置里 stringenc 模块下加子勾选项，勾上则桩类自动进 dcc。**此指令尚未执行** | 该指令是否仍有效？ |
| 「为什么不直接写一个C层字符串加解密」 | 不走 dcc **转译** Java 桩，而是**直接手写 C 实现解密桩**（JNI native 方法），dex 里只有 native 方法声明 | 是否误解？ |
| 「这样字段也不会出现在java层」 | 种子/密钥流/缓存全部在 so 的 C 全局变量里，dex 层零算法痕迹 | 是否误解？ |

**我们的回应**：「开智了」确认 —— 我们给了三条路线对比（Java 桩现状 /
dcc 转译桩 / C 手写桩），结论 **C 手写桩优于 dcc 转译桩**，理由：
一次 JNI 往返（vs 转译桩的两次，转译桩 native 侧反调 Java 集合）、
无流水线顺序手术（native 声明无方法体，「抽不抽得到」问题不存在）、
so 内无 dex2c runtime 特征、代码自己写的可控可维护。

**未拍板处**：1.4 的两个指令（①json 子复选框联动 ②C 手写桩）关系如何？
我们的判断：若 ② 立项，① 是重复建设（② 使 ① 要解决的顺序/联动问题整体
消失），建议 ① 不做 —— **但用户尚未拍板，且 ① 是用户明确说过的指令，
此处必须由用户（或审核者建议后由用户）重新确认**。

## 2. 方案轮廓：C 手写桩（若拍板立项）

```
dex 侧（stringenc 注入，替换现有 Java 桩 smali）:
    .method public static native d(Ljava/lang/String;)Ljava/lang/String;   ← 一行声明
    <clinit> 里 System.loadLibrary

so 侧（并入 libnc.so，蹭 sig_check/env_check 的加固编译参数）:
    C 实现：splitmix64 密钥流 + XOR + Base64 解码 + C 层 L1 缓存（hash map）
    构建期生成 strdec_config.h（种子 + 随机桩名）编译进 so；
    protect.sh 前置生成一次，STEP5 的 stringenc 读同一份配置
```

相对 dcc 转译桩的优势（我们的判断，见 1.4）：性能路径优 / dex 痕迹更少 /
无顺序手术 / 无转译黑盒 / so 内更隐蔽（无 dex2c 特征）。

**代价（诚实列出）**：
1. 新写 ~170 行 C（解密 + Base64 + hash 缓存 + JNI 桥）
2. 种子/名生成前置，跨步骤配置一致性要设计
3. Java 桩的 `intern()` 语义（保 `==`）在 C 侧无法直接复刻 —— 语义兼容风险
4. C 层缓存线程安全自己保证（Java 侧有 ConcurrentHashMap）
5. stringenc 从「纯 dex 模块」变成「依赖 so 的模块」（打破报错二十三建立的
   模块定位：stringenc-only 勾选组合将没有 so 可加载）

## 3. 疑惑与待审核点（每条附我们的初步判断，请优先攻击判断）

1. **intern() 语义**（我们判断：风险最高）—— C 桩 `NewStringUTF` 返回新
   对象，若业务代码依赖 `==` 比较解密结果会静默改变行为。判断：可在 L1
   miss 时补调一次 `String.intern()`（一次反向调用）；但业务是否真的依赖
   == 无从全量验证。问：这个风险量级如何评估？有无更稳做法？
2. **模块定位漂移** —— stringenc-only 组合没有 so → `UnsatisfiedLinkError`。
   判断：protect.sh 勾 stringenc 时强制带最小 NDK 编译或 fail-fast。问：
   有没有不破坏纯 dex 组合的第三种做法？
3. **配置前置时序** —— `strdec_config.h` 须在 NDK 编译前生成、STEP5 读同一
   份。判断：开头生成一次、写后只读（与组件标记同思想）。问：半途失败重跑
   的幂等性（旧 config.h 与新种子错位）有没有坑？
4. **C 缓存并发与多进程** —— 判断：开放寻址 + 分段锁，cap 对齐 Java 侧
   30000，多进程各自一份（与 Java 侧行为一致）。问：内存代价可忽略吗？
5. **`<clinit>` 回填链重写** —— 现有字段回填靠「桩的 Java 静态字段 F + 业务
   类 `<clinit>` sget」，C 桩无 Java 字段，须改成业务 `<clinit>` 调 native
   取值。问：类加载最早期（早于 attachBaseContext）loadLibrary 一定安全吗？
6. **so 反编译上限** —— 算法进 so 后 PC 端 Ghidra 可见。判断：对手成本从
   「10 分钟」抬到「数小时 + native 能力」，符合「抬成本不求绝对」定位。
   问：这个成本评估成立吗？需叠加 so 混淆吗？
7. **报毒维度回归** —— 初衷是防安装器报毒；C 桩同时改变 dex 与 so 侧特征
   分布，so 侧影响无数据。判断：落地后应把「新包报毒表现」列为必测项。
   问：同意吗？
8. **1.4①（json 子复选框）的存废** —— 判断：若 ② 立项则 ① 不做。
   问：是否存在 dcc 转译路线更优的场景（如无法编译 C 的纯云端流水线）？
9. **性能维度是否到此为止** —— 1.3 的假说测不出。判断：C 桩卖点是痕迹与
   可控性而非速度，不再追性能对照。问：有无我们没想到的性能敏感场景？
