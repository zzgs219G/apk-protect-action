## 1. 需求与威胁模型

### 1.1 威胁模型的演进（三阶段）

| 阶段 | 威胁 | 已做的防御 | 状态 |
|---|---|---|---|
| ① | 安装器报毒（引擎特征扫描） | 桩随机化：每包随机包名/类名/方法名，废掉固定签名 `Lcom/nc/strdec/StrDec;->d` | 已落地（`a877ae8` + 报错四十八修复 `6b52ff5`） |
| ② | 一键脚本批量提取字符串 | 桩随机化 + 加密算法本身 | 已落地 |
| ③ | **针对性人工/AI 分析**：对手把桩类 smali 发给 AI 即可秒破 | **无** —— 本文档要解决的就是这层 | 待解决 |

### 1.2 阶段③的破绽本质（为什么随机名防不住）

桩随机化只废掉「精确签名匹配」，但桩本身仍是一个**结构独特、算法标准**的类：

1. **算法指纹**：桩内含 `0x9E3779B97F4A7C15`（splitmix64 黄金比例常量），
   AI/逆向者一眼认出标准算法，直接套现成实现
2. **单点汇聚**：全包数千调用点指向同一个类的同一个方法（随机名不改变
   「唯一汇聚点」这一结构特征，静态扫 invoke 目标即可定位）
3. **种子静态可见**：8 字节 SEED 编在桩的指令流里

只要解密器与密文同处一个 APK 且 dex 层可读，「发给 AI 破解」就是必然结局
（Kerckhoffs 原则）。**能做的只有把解密器移出 dex 或使其不可读。**

### 1.3 目标（按优先级）

1. **dex 层零算法痕迹**：对手解包 APK 后，dex 内找不到任何解密逻辑/密钥字段
2. 性能不劣化（当前基线：冷启动 ≈ 原生，见第 2 节实测）
3. 流水线改动尽量小、不引入黑盒依赖

## 3. 候选路线与我们的推理

### 路线 A：dcc 转译 StrDec（=「方案 E」，已被 F2 证明可行）

**思路**：把 StrDec 类也塞进 dex2c —— 算法进 so，dex 内桩变 native 壳。

**阻塞点（F4）**：dcc 跑 STEP2 时桩还不存在。我们的解法设计（方案 E）：
桩注入拆出前置为独立步骤（生成随机名 + 注入桩类）→ dcc 规则**自动追加桩名**
（这就是「联动自动填入」——随机名构建期才知道，手动填规则走不通）→ STEP5
stringenc 复用已存在桩（F6 机制天然兼容）。

**疑虑**：
- dex2c 转译是**黑盒**（老毛病有前科：报错十三 Kotlin 类型瑕疵），冻结区不能改
- 性能路径差：两次 JNI 往返（含反调 Java 集合），单次解密纸面估 300-800ns
  vs Java 桩 50-100ns —— 但 F2 证明冷启动测不出
- 转译产物在 so 里带 **dex2c runtime 显著特征**，对手容易识别这是转译代码

### 路线 B：C 层手写 JNI 桩（本文档主推，用户提出）

**思路**：不走 dcc 转译，**直接手写 C 实现解密桩**：

```
dex 侧:  .method public static native d(Ljava/lang/String;)Ljava/lang/String;   ← 仅一行声明
         <clinit> 里 System.loadLibrary
so 侧:   C 实现：splitmix64 密钥流 + XOR + Base64 解码 + C 层 L1 缓存(hash map)
         种子/密钥流参数编译期生成 strdec_config.h 进 so
```

**相对 A 的优势（我们的分析）**：

| 维度 | A（dcc 转译） | B（C 手写） |
|---|---|---|
| 解密路径 | 2 次 JNI 往返（含反调 Java 集合） | **1 次**（缓存纯 C 层）——纸面 100-300ns |
| dex 痕迹 | native 壳 + 类名 + loadLibrary | **仅 native 方法声明**——「字段不进 Java 层」 |
| 流水线 | 顺序手术 + 规则联动 + exclude 重排 | **无顺序问题**（声明无方法体，「抽不抽得到」不存在） |
| 代码质量 | 转译器产物，冻结区 | 自己写的，可维护可再混淆 |
| so 内隐匿 | dex2c runtime 特征明显 | **无特征**——对手在 so 里认不出这是解密桩 |
| 复用 | 独立 | 并入 `libnc.so`，蹭 sig_check/env_check 的加固编译参数（-Oz/去指纹/gc-sections） |

**代价（诚实列出）**：
1. 新写 ~170 行 C（解密 + Base64 + hash map + JNI 桥）——但复杂度可控
2. 种子/随机名生成要**前置**（NDK 编译前生成 `strdec_config.h`），与 STEP5 的
   stringenc 读同一份配置 —— 跨步骤状态一致性要设计
3. Java 桩的 `intern()` 语义（保 `==`）在 C 侧无法直接复刻 —— **语义兼容风险**
4. C 层缓存的线程安全要自己保证（Java 侧有 ConcurrentHashMap 白捡）
5. **stringenc 从「纯 dex 模块」变成「依赖 so」** —— 打破报错二十三建立的
   模块定位（stringenc-only 组合没有 so）

### 路线 C（对照项，已基本被 B 挤掉）：算法变体化

纯构建期：密钥流生成器每包从变体池组合（xorshift/PCG/自定义轮函数）+ 魔数
随机化。零运行时改动、零流水线风险，但只抬高「套模板」成本，dex 内算法仍可读。
B 若成立则 C 无必要；B 若因隐藏成本搁浅，C 是低配 fallback。

### 我们的倾向（待审核）

**B 优于 A**：B 用「写 170 行 C」换掉了 A 的全部流水线手术与转译黑盒依赖，
且性能、dex 痕迹、so 隐匿三个维度都更好。F2 已证明 A 可行，但 A 的自动化
（规则联动）复杂度是结构性的；B 是釜底抽薪。

## 4. 疑惑与待审核点（核心输出，请审核者逐条把关）

> 下面每条都标注了「我们自己的初步判断」，请审核者优先攻击这些判断。

1. **intern() 语义**（我们判断：风险最高的一条）
   Java 桩解密后 `intern()` 保 `==` 引用相等。C 桩经 `NewStringUTF` 返回的
   String 每次是新对象 —— 若业务代码有 ` decrypted == CONSTANT` 或以 String
   为 key 的 IdentityHashMap 依赖，会静默改变行为。
   → 初步判断：JNI 里可先 `NewStringUTF` 再调 `String.intern()`（一次反向
   调用，只在 L1 miss 时付）；但**业务代码是否真的依赖 == 无从全量验证**。
   审核者：这个风险的实际量级如何评估？有没有比「补调 intern」更稳的做法？

2. **模块定位漂移**（我们判断：真实但可接受）
   stringenc 变依赖 so 后：stringenc-only 勾选组合将**编不出能跑的包**
   （没有 so 可 loadLibrary → `UnsatisfiedLinkError`）。
   → 初步判断：protect.sh 里 stringenc 勾选时强制带最小 NDK 编译（或
   fail-fast 提示必须同时勾 sigcheck/dcc/envcheck 任一）。
   审核者：有没有不破坏「纯 dex 组合」的第三种做法（如桩对 loadLibrary
   失败做降级——但降级回 Java 桩又把算法放回 dex，等于白做）？

3. **种子/配置前置的时序一致性**
   `strdec_config.h`（种子+随机名）须在 STEP3/4 编译前生成，STEP5 注入时
   必须读到**同一份**。
   → 初步判断：protect.sh 开头生成一次、两处消费，写文件后只读不重写
   （与 F6 组件标记同思想）。审核者：中途失败重跑（protect.sh 半途死）的
   幂等性有没有坑（旧 config.h 与新种子错位）？

4. **C 层缓存的并发与生命周期**
   → 初步判断：开放寻址 hash map + 分段 spinlock（或 racy 读 + 细粒度写锁），
   cap 对齐 Java 侧 30000；缓存是进程级、纯内存、不跨 fork 语义
   （App 多进程各自一份，与 Java 侧行为一致）。审核者：多进程场景（如
   `:push` 进程）下每进程一份 so 缓存的内存代价是否可忽略？

5. **`<clinit>` 字段回填链的重写范围**
   现有字段常量加密靠「桩的 Java 静态字段 F + 业务类 `<clinit>` sget 回填」。
   C 桩没有 Java 字段 —— 回填链必须改成「业务 `<clinit>` 调 native 方法取值」。
   → 初步判断：改动集中在 `inject_clinit_backfills()` 的调用形态，机制等价。
   审核者：native `<clinit>` 调用链在**类加载最早期**（甚至早于
   Application.attachBaseContext）是否一定安全（loadLibrary 能否成功）？

6. **so 反编译上限与对手成本**
   算法进 so 后 PC 端 Ghidra 可见（与路线 A 同上限，且 B 无 dex2c 特征反而
   更隐蔽）。我们判断：对手成本从「10 分钟」抬到「数小时人工逆向 + 需要
   native 能力」，符合「抬成本不求绝对」的定位。
   审核者：这个成本评估是否成立？是否需要叠加 so 层手段（已有 -Oz 等
   编译加固；更重的 so 混淆是否值得）？

7. **报毒维度是否需要回归验证**
   初衷是防安装器报毒。B 改变 dex 与 so 双侧特征分布 —— dex 侧减特征
   （好事），so 侧增内容（未知）。
   → 初步判断：报毒引擎对 so 内容的敏感度低于 dex，但**没有数据**。
   审核者：是否应把「新包报毒表现」列为 B 落地后的必测项？

8. **路线 A 的存废**
   F2 已证明 A 真机可行。若采纳 B，A 的流水线联动（json 子复选框
   「dcc 解密类」）是否还值得做？
   → 初步判断：不做（重复建设）；A 作为「手工场景的已知可行路径」记录在案
   即可。审核者：是否存在 A 更优的场景（如无法编译 C 的纯云端流水线）？

9. **性能数据的天花板**
   F2 显示差异已在噪声内，B 比 A 理论更快但更测不出。
   → 初步判断：性能维度到此为止，B 的卖点是**痕迹与可控性**而非速度。
   审核者：是否存在我们没想到的性能敏感场景（如字符串访问极密集的热路径）？
