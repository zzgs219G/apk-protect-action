## 4. 逆向思路复盘（含错误记录）

### 4.1 有效的步骤

1. **先定性后解剖**：MD5 比对两包 → 锁定"校验基于证书"，省掉 70% 无效探索。
2. **从入口反推**：`onCreate` 是 native → 放弃 6 dex 直扑 so。
3. **用引用密度定位，不用符号**：扫 `adrp` 落点，所有 `.ncks/.nck/.ncxr` 引用收敛于 `0x1e074` 附近 → 解密器定位。
4. **识别 CRC32 魔数**：`movk w12,0xedb8,lsl 16` + `mov w12,0x8320` = `0xEDB88320`，判定为自校验。
5. **特征定位 Java 层校验点**：同一 `code_item` 内同时引用 `ncVerify` 与 `killProcess` → 精确命中（该方法被改名为 `coroutineBoundary` 伪装）。
6. **建立可证伪对照组**：testkey 重签 → 43ms 死亡；用户签名 → 长期存活。

### 4.2 决定性对照实验（本版最有价值的证据）

只把 `.text` 里一条**正常运行中 100% 不可达**的指令改写（watchdog 中 `_exit(3)` 前的 `mov w0,3` → `mov w0,0`），重新加密 `.ncxh` 后：

| 包 | 结果 |
|---|---|
| 原版 `.text` CRC | 正常运行 |
| 只改 1 条不可达指令，CRC 变化，`.ncxh` 已正确重加密 | **SIGILL，进程死** |

**结论（硬事实）**：`.text` 内容与 `.ncx`/`.ncxh` 解密存在强耦合。
任何 `.text` 修改，即使语义完全无害、即使壳自身加密链已重新对齐，仍会导致 shell 自毁。
**这不是"我的补丁写坏了"——是对照实验排除的。**

## 6. 为什么走到这里（结构性弱点）

1. **段名自曝**：`ncks/nck/ncxr/ncx/ncxh/ncxhr` 六连发，`iS` 30 秒拿全布局。
2. **解密器与被解密数据同库、密钥材料全在文件内**：`.ncxh` 的 16 字节密钥
   = `.ncks` 明文 + `.rodata` 明文置换表 + **离线可算的** `CRC32(.text)`，
   因此 `.ncxh` 可 100% 离线复现。
3. **明文日志 = 流程说明书**：`"apk path from data/app: %s"`、`"nc: fp=%s"`、
   `"der_len=%zu"`、`"data/app scan exhausted"`、`"id=0x%llx len=%d"`。
4. **kill 路径全在明文**：`0x22698`（tgkill+raise）、`0x2264c` 全可静态定位。

**但请注意**：弱点 2 在 `.ncx` 上**不成立**——这才是防线有效的真正原因。

## 8. 缺陷清单（修订版，含新增项）

### 🔴 高危

**F-1 判定阈值明文可写**
`.ncxr[0x40..0x60)` 是放行基准，明文、无自完整性保护。
攻击者无需碰代码即可改"标准答案"。（我未打中，因定制哈希无法复现算出正确值，
但**架构上这仍是最弱点**——只要攻击者能本地执行一次正版包并 dump 结果即可。）

**F-2 `.text` 与载荷解密耦合 —— 防线强，但维护性自锁**
对照实验证明改 `.text` 必 SIGILL。安全性上这是**成功设计**，代价是：
- 无法热修/增量更新 `.text`；
- 编译器/PGO 变动需重新生成全部壳数据；
- **自己也无法 patch 校验逻辑**（这正是我遇到的困境）。
建议：密钥改由"服务端下发 + 设备指纹"派生，`.text` 完整性单独做 hash 比对。

**F-3 双判定路径不一致**
Java 侧走 `PackageManager`+双重 SHA256，native 侧走自解析 v2 block+定制哈希。
实测改 Java 侧无效 → 至少一套是死代码或未接上，维护风险与攻击面同时增加。

### 🟠 中危

**F-4 `0x210a0` 为定制哈希**（IV = `6a09e667 bb67ae85 3c6ef372 a54ff53a 510e527f 9b05688c…`）
设计上是好的（std 库不可复现），但**常量表就明文放在 `.rodata`**，
等于把"我们改了 IV"这件事写在脸上。建议改为运行时从密钥材料展开。

**F-5 v2 块 ID 解析脆弱**
ID 是 uint32（`0x7109871a`，见 `0x20288`）。若签名工具改用 v3/v4-only 或 lid-only，
解析可能直接落空且无兜底路径。

**F-6 `.ncks+0x30/0x34` 死字段**
全二进制扫描 `adr/adrp+ldr` 确认无代码引用。残留或未完成设计。

**F-7 段名自曝**、**F-8 明文日志字符串**
见第 6 节，仍成立。

**F-9 反调试强度低**：仅 `ptrace`+`prctl`，无 `TracerPid` 轮询、无时间差检测。

**F-10 双 ABI 重复实现**：32 位版本分析成本显著更低。

### 🟡 工程质量

**F-11 `debuggable=true` + `extractNativeLibs=true`**：so 落盘可直接替换。
**F-12 杀进程策略粗暴**：重签包 43ms 即死，等于告诉分析者"已被识别且是第一道判定"；
应静默降级。
**F-13 残留符号未清理**：`amimo_dcc`、libc++ demangle、`com/xixin/tc/R$layout`。
**F-14 `.ncks` 自描述**：`[0x18] = 0x125cc(self)` 写入自身地址，便于定位，无必要。

## 10. 若要继续：唯一有意义的下一步

**读 `.ncxh` 解密后的 driver，还原 `sp+0x360` 16 字节密钥的生成过程。**

已知线索：
- driver 位于解密后的 `.ncxh`（`0x43d94`+ 区），入口 `0x43d94` 是 RC4 初始化
  （`sub sp,#0x130; stp; str; add; mrs; S 盒填充; udiv/msub 密钥滚动`）；
- 调用点 `0x447c8`：`bl 0x43d94`，参数 `x0=sp+0x360`(密钥)、`x1=0x10`(长度)、`x3=malloc 缓冲`；
- driver 流程：`mprotect(RW)` → `malloc` → `RC4(sp+0x360, 0x10)` → `memcpy` 回写目标 → `icache` → `mprotect(RX)`；
- 因此唯一缺失的是**这 16 字节从何而来**，向上游追溯 `0x44700`–`0x44790` 的栈帧来源即可。

**不建议再做的事**：盲改 `.text`（对照实验已证明必自毁）、继续穷举密钥（88 个候选覆盖了静态可得的所有密钥源）。
