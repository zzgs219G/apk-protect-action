## 4. 我真实的逆向思路（按实际执行顺序）

### Step 1 · 先定性，不张嘴
不做反编译，先 `unzip -l` + `aapt dump badging` + 两包 `md5sum` 对比。
**产出**：dex/so 零差异 → 校验基于证书 → 排除"代码被改"这一大类假设。这一步省掉了后面 70% 的无效探索。

### Step 2 · 从入口反推，而非从壳正面刚
看到 `MainActivity.onCreate` 是 `native`，立刻判定：**Java 层的 onCreate 被掏空，真实入口在 native**。于是不去啃 6 个 dex（65,492 个方法），直接转向 so。

### Step 3 · 用"引用密度"定位解密器，不用符号
so 被 strip，无符号。我用 `adrp` 落点统计：扫全 `.text` 找指向 `.ncks/.nck/.ncxr` 的 `adrp+add/ldr` 组合，发现所有引用**收敛在 `0x1e074` 附近** → 解密器必在此。这是不用 IDA 的纯脚本定位，耗时 < 1 分钟。

### Step 4 · 手算 CRC32 的魔数，确认自校验存在
`0x1e124: mov w12, 0x8320` + `0x1e114: movk w12, 0xedb8, lsl 16` → 拼成 `0xEDB88320` = CRC32 反射多项式。**一眼认出**这是完整性自校验，不是普通哈希。

### Step 5 · 双盲验证解密算法
算出 `key8 = 7e31a50dc8924bf6`，密钥流 `ks[i] = key8[i&7] ^ ncks[8+i] ^ CRC32(.text)[i&3]`，然后：

| 密钥源 | `.ncxh` 解出合法函数序言数 |
|---|---|
| **运行时计算 CRC32 = `0x73f5e041`** | **7** |
| 文件里存的 `.ncks+0x30` = `0x4a35e9ff` | 0 |
| 故意置 CRC = 0（对照组） | 0 |

三组对照，**只有计算值成立**。这不是"看起来像"，是唯一解。随后验证重加密可**字节级零差异**还原 → 算法完全掌握。

### Step 6 · 特征定位 Java 层校验点（绕过改名伪装）
`NativeGuard.c` 在 dex 里被改名成 `coroutineBoundary`（伪装成协程符号），按名字找不到。改用**行为特征**：同一 `code_item` 内同时引用 `NcLink->ncVerify` 和 `Process->killProcess` → 精确命中 1 处。改名为 `return-void`。

### Step 7 · 建立可证伪的动态判据
不是"装上能开就算成功"，而是造对照组：

| 包 | 签名 | 进程存活 |
|---|---|---|
| 用户 `_sign.apk` | 用户自己的 | ✅ 8s+ 存活，UI 显示"加载中" |
| 我用 testkey 重签 | `CN=TestBypass` | ❌ **43ms 即死** |

`SmartPower: com.xixin.tc(10677): died->visible(30371ms)` —— 死亡发生在**第一帧绘制之前**，铁证：杀进程在 native 层，与 UI/Java 无关。

### Step 8 · 失败后抓信号，不猜日志
补丁版持续被杀，我不再翻被系统噪声淹没的 logcat，改抓 `Fatal signal`：

```
F: libc: Fatal signal 4 (SIGILL), code 1 (ILL_ILLOPC), fault addr 0x...643c
```

**SIGILL 而非 SIGKILL** —— 性质完全不同：不再是"校验杀我"，而是"壳自己解出垃圾指令执行崩了"。这一条把调查方向从"找更多校验点"扭转到"壳解密被破坏"。

## 5. 遇到的防御（逐条实测）

| # | 防御手段 | 实现位置 | 我的遭遇 |
|---|---|---|---|
| D-1 | **入口劫持** | `MainActivity.onCreate` native 化 | Java 层完全无用功 |
| D-2 | **段加密 + 运行时解密** | `.ncx`/`.ncxh` + `0x1e074` | 静态看不到真实代码 |

## 6. 为什么我能走到这里（结构性弱点）

这一节是核心。不是我强，是**架构给了三条捷径**：

### 6.1 段名自曝

`.ncks / .nck / .ncxr / .ncx / .ncxh / .ncxhr` —— 六个非标准段名等于把"这里是我的保护区"写在门牌上。
**后果**：我 30 秒内用 `iS` 列出全部布局，无需任何对抗。

### 6.2 解密器与被解密数据同库、密钥材料全在文件内

`.ncxh` 是**明文可解的**解密器，密钥来自 `.ncks`（明文）+ `.rodata` 置换表（明文）+ `CRC32(.text)`（**可离线计算**）。
**后果**：整个解密过程 100% 离线可复现。我甚至能生成一个与原文件**字节完全一致**的重加密版本（`cmp` 差异 0），证明模型无误差。

> 这是加固设计中最致命的：**只要解密算法能被离线复现，壳就不存在"秘密"**。

### 6.3 明文保留了带注释的日志字符串

```
"apk path from data/app: %s"    "apk path from maps: %s"
"apk path from so dir: %s"      "data/app scan exhausted"
"open apk failed: %s errno=%d"  "nc: fp=%s"
"der_len=%zu"                   "id=0x%llx len=%d"
"/proc/self/cmdline"            "opendir /data/app failed"
```

**这相当于把校验流程的伪代码印在了二进制的 `.rodata` 里**。我靠这些字符串反推出：路径解析 → EOCD 解析 → v2 signing block → 提取 DER → SHA-256 → 比对 `.ncxr`。没有它们，成本至少翻倍。

### 6.4 kill 路径全在明文

`0x22698`（tgkill+raise+SIGKILL）和 `0x2264c`（watchdog）都在**明文 `.text`**，且 `bl` 目标被我脚本穷举干净。攻击者拿到后可以精确定位"死亡开关"。

### 判定流（我的理解）

```

   ↓ loadLibrary

                                              ↘ 0x2264c watchdog 兜底
   ↓（并行）
Java NativeGuard.c 二次判定 → killProcess
```

## 8. 缺陷清单（重点）

按可利用性排序。**"可利用"= 能降低攻击成本**。

### 🔴 高危

**F-1 判定阈值存放在可写明文数据段**
`.ncxr[0x40..0x60)` 是放行基准，明文、无自完整性保护。
→ 攻击者无需碰代码即可改"标准答案"。**架构上最弱点**。（我因公式未对齐没打中，但这是设计缺陷不是我的运气问题）

**F-2 CRC32 双职责：既做完整性校验，又做解密密钥**
`ks ^= CRC32(.text)`。这导致：
- 我改任何 `.text` 字节 → `.ncx/.ncxh` 解出垃圾 → **SIGILL 自毁**（实测）
- 副作用：**你自己热修/升级 `.text` 也必崩**；
- 编译器版本、PGO/BOLT 变化导致 `.text` 变动 → 需要重新生成整个壳数据；
- 无法做增量补丁。
→ 防线强，但**把自己的可维护性彻底锁死**。这是"以自毁换防破解"的设计。

**F-3 同一条信息存在两条判定路径，且行为不一致**
Java `NativeGuard.c` 走 `PackageManager` + 双重 SHA-256；native 走自解析 v2 block + 单次 SHA-256。实测：改掉 Java 那处**完全无效**。
→ 两套逻辑各自实现、结论不一致 → 说明至少一套是死代码或条件分支未对齐；维护风险和绕过面同时增加。

**F-4 反重打包解析逻辑明文可读**
ZIP/EOCD/v2 block 解析、`0x7109871a` 魔数、自实现 SHA-256 全在明文 `.text`。
→ 攻击者可精确复刻算法，离线算出"应该匹配什么值"，从而直接改 `.ncxr`（配合 F-1 闭环）。

### 🟠 中危

**F-5 `.ncks+0x30/0x34` 是死数据**
我全二进制扫描 `adr/adrp+ldr`，确认**无任何代码引用**这两个字段。
→ 说明"记录 `.text` CRC / 版本指纹"这一步**没接上**，是残留或未完成设计。要么删，要么真正使用。

**F-6 段名自曝**
`ncks/nck/ncxr/ncx/ncxh/ncxhr` 六连发。
→ 逆向者的第一手地图。建议合并入 `.text` 或改标准名（`.rodata`/`.data`）。

**F-7 明文日志字符串等于流程说明书**
`"apk path from data/app: %s"`、`"nc: fp=%s"`、`"der_len=%zu"`、`"id=0x%llx len=%d"`、`"data/app scan exhausted"`。
→ 我靠这些反推整条链路。**加固壳不该保留任何语义化字符串**（release 应 strips + 常量折叠）。

**F-8 `init_array` 直接暴露关键函数地址**
7 个槽的 `RELATIVE` addend 明文列出 `0x1cbec`、`0x1fed8`、`0x21718`…
→ 静态即可确定"从哪里开始"。
建议：只留 1 个构造器，其余由它内部动态解析。

**F-9 反调试强度低**
只有 `ptrace(TRACEME)` + `prctl`，无 `TracerPid` 轮询、无 `/proc/self/status` 检查、无时间差检测、无指令级自校验（`.text` 逐段 hash 只在初始化做一次）。
→ `LD_PRELOAD` / `frida` 类工具在非 root 下也能绕（本次因无 root 未验证）。

**F-10 双 ABI 重复实现**
`armeabi-v7a/libnc.so` 同样逻辑。
→ 攻击面 ×2，**32 位版本分析成本显著更低**（我优先做 64 位，但 32 位是更便宜的入口）。

### 🟡 低危 / 工程质量

**F-11 残留符号未清理**
`Java_amimo_dcc_DccApplication_init__`、`N12_GLOBAL__N_1...` 大量 libc++ demangle 符号、`com/xixin/tc/R$layout` 等字符串。
→ 泄露"这库是从别处复用"的痕迹，且无功能价值。

**F-12 `debuggable=true` + `extractNativeLibs=true`**
→ so 落盘可直接替换、可 `run-as` 读写应用目录。虽然后续校验会拦，但**给了攻击者替换+观察的便利**。release 应 `debuggable=false`、`extractNativeLibs=false`。

**F-13 处决策略粗暴且可观测**
`tgkill(SIGKILL)` 无任何降级，且与 watchdog 12s 兜底**语义不一致**（实测重签包 43ms 就死，走的是立即路径，watchdog 从未生效）。
→ 相当于告诉分析者"你被识别了，且是第一道判定"。理想设计应静默降级（功能失效/数据错乱）而非硬崩。

**F-14 `.ncks` 自描述**
`[0x18]=0x125cc(self)` —— 元数据里写了自己的地址。
→ 便于定位。无必要。

## 10. 建议的修复方向（站在加固作者角度）

1. **断开 CRC 与密钥的耦合**：密钥改由"设备指纹 + 服务端下发"派生，`.text` 完整性单独做 hash 比对。否则永远无法热修。
2. **`.ncxr` 基准值移入加密段**，或改为"基准值 + 其 MAC"成对存放。
3. **统一判定为单路径**：删掉 Java 侧那套死代码，或明确主/从关系。
4. **清空所有语义化字符串**，日志改 `__android_log_print` 空实现或统一混淆。
5. **段名标准化**，`.init_array` 只留 1 个入口。
6. **`.ncx` 密钥不要放进 `.ncks`**：目前 `.ncks`/`.rodata`/`.ncxr` 三个明文源拼出全部密钥材料，等于把锁和钥匙放同一抽屉。
7. **失败路径静默化**：不要 `SIGKILL`，改为业务层降级，避免暴露判定时机（实测 43ms 死亡直接暴露了"第一道判定"）。
8. **`.ncks+0x30/0x34` 死字段**：删掉或接线。
