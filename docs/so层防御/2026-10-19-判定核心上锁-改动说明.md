## 0. 一句话

实测报告最致命的那条 ——「`.ncguard`（密文）里装的是 `ncVerify` 转发壳，
真正的判定算法 `nc_verify_t1` 和两张表 `SIG_SALT`/`SIG_HASH_STORED`

## 1. 根因：不是加密坏了，是东西放错位置

### 1.1 修复前的资产分布

| 资产 | 位置 | 可见性 | 攻击成本 |
|---|---|---|---|
| `ncVerify`（JNI 入口） | `.ncguard` 密文 | 解不开 | 8 分钟离线解密 |
| `heartbeat`（JNI 入口） | `.ncguard` 密文 | 解不开 | 同上 |
| **`nc_verify_t1`（真正的判定）** | **`.text` 明文** | **可读** | **0** |
| **`SIG_SALT`（16B 盐）** | **`.rodata` 明文** | **可读** | **`od` 一条命令** |
| **`SIG_HASH_STORED`（32B 期望值）** | **`.rodata` 明文** | **可读** | **同上** |

实测报告作者据此 **5 分钟反推出 32 字节通过凭据**（报告 §3.6）。

### 1.2 为什么会这样

三个原因叠加，缺一不可：

1. **`nc_verify_t1` 从未加段属性**。`nc_link.c` 里 `ncVerify`/`heartbeat`
   两个 JNI 入口在 `.ncguard` 加密段（这是对的），但被判定的核心函数
   `nc_verify_t1` 一行 `__attribute__` 都没写 → 落进 `.text`。

2. **表是构建期生成的 `static const`，生成器没写段属性**。
   `make-sig-hash.sh` 输出的 `sig_hash.h` 里，`SIG_SALT` /
   `SIG_HASH_STORED` 就是裸 `static const` → 必进 `.rodata`。

3. **没人问过「加密段里装的东西值不值得加密」**。
   此前所有验证都在测「密文能不能解开」（熵值、HMAC、`selftest=59`），
   没有一项测「**密文里装的是不是核心**」。解密成功 ≠ 保护住。

## 2. 改了什么

### 2.1 新增第二个加密段 `.ncguard_ro`

**为什么不能直接塞进 `.ncguard`**：

```
clang: 'nc_verify_t1' causes a section type conflict with 'SIG_SALT'
```

`.ncguard` 是 `AXR`（可执行）段，`SIG_SALT` 是 `const` 只读数据。
LLVM 拒绝让同一段既装代码又装只读数据。这是**硬约束，不是偷懒**。

所以拆成两段，**共用同一把 `k_so`、同一个 MAC**：

```
.ncguard       AXR   代码   ← nc_verify_t1
.ncguard_ro    AWR   数据   ← SIG_SALT + SIG_HASH_STORED（不可执行）
```

分两段还有个附带好处：解完权限各自最小——代码段 `RX`，数据段 `R`。
给数据段加 `X` 是没必要的权限扩大。

### 2.2 段标记条件化（三条纪律）

`nc_link.c` 里新增：

```c
#if defined(NC_GUARD_SECTIONED) && !defined(NCLINK_HOST_TEST)
#  define NC_VERIFY_SECTION __attribute__((section(".ncguard"), retain, used))
#else
#  define NC_VERIFY_SECTION
#endif
```

- **为什么是显式宏而非 `__ANDROID__` 自动判断**：宿主端任何一次「想验证段
  布局」的编译都会因为「标了段却没人解锁」而读到密文 → 假红。显式开关让
  「我要标段」成为必须说出口的事，由 `lib-ndk.sh` 统一开启。
- **`NCLINK_HOST_TEST` 必须优先排除**：`test-javacheck.sh` 用这个宏做纯逻辑
  对拍，没有解锁设施，标了段就必红。
- **`retain` 不可省**：`lib-ndk.sh` 的 `LOCAL_LDFLAGS` 含 `-Wl,--gc-sections`，
  漏掉会被连段回收（报错十一同款）。

### 2.3 增量 HMAC（MAC 覆盖两段）

两段在内存中不连续。一次性算 HMAC 得先把两段拼进临时缓冲（最多几十 KB
`malloc` + `memcpy`）。新增增量接口，零额外内存、零拷贝：

```c
khmac_init(&ctx, key, 16);
for (i = 0; i < nseg; i++) khmac_update(&ctx, base + segs[i].sh_addr, segs[i].sh_size);
khmac_final(&ctx, got_mac);
```

实现要点：

- `opad` 必须在 `init` 阶段就算好存进 ctx —— `final` 时 key 已不在手上。
- `k0` 必须先清零再 `memcpy`：`key_len < 64` 时后半段必须是 0（哈希块填充语义）。
- `.h` 里 `ksha_ctx`/`khmac_ctx` 是不透明句柄，调用方开不出栈对象。
  用 `KHMAC_CTX_SIZE` + `_Alignas` 字节缓冲，并由
  `typedef char khmac_size_check_t[(sizeof <= SIZE) ? 1 : -1]`
  在**编译期**把关——不一致直接编译失败，而不是运行期栈溢出。

### 2.4 向后兼容

老产物只有 `.ncguard`、没有 `.ncguard_ro`：

```c
Elf64_Shdr segs[2];
int nseg = 0;
segs[nseg++] = sec;                       /* .ncguard 必有 */
if (ncg_find_section(so_path, NCG_SECTION_RO, &ro) == 0 && ...) {
    segs[nseg++] = ro;                    /* 有则一并解 */
}
```

`nseg == 1` 时，MAC 输入就是该段密文本身，与历史版本**逐字节一致**。
`protect.sh` 也先探测段是否存在，不存在则退回单段并**打印明确提示**
（不静默降级——这是本机制最该避免的失败模式）。

```bash
print('SIG_HASH_STORED 命中:', d.count(bytes.fromhex('<从 sig_hash.h 抄 32 字节>')))
```


## 5. 还剩什么问题（如实）

### 5.1 本轮**没有**修的（报告 P0/P1 其余项）

| 项 | 现状 | 报告依据 |
|---|---|---|
| **kill 链走 `abort`/`_exit`/`raise` PLT** | **未修**。实测 `abort@plt` 有 **380 个调用点**，改 4 字节全废 | 实战 §12.1 |
| `master[32]` 仍是 `0x11`×32 占位符 | **未修**。构建脚本无注入机制 | 静态 §3.3 |
| `.text` 完整性校验可能不覆盖本 so | **未查明**（见 5.3） | 复核清单 G 项 |
| 失败路径 13 分支 → 1 汇聚点 | 未修 | 静态 §10 |
| `.dynsym` 导出业务符号 | 未修 | 静态 §1 |

**为什么先做这一项**：报告 §17.4 的排序里
「`0x238bc` 移进 `.ncguard`」是**成本极低、收益最大**的一项
（报告原文："一行 `__attribute__` 的事，收益大于其余所有改动之和"）。
kill 链改动动 `env_check.c`（冻结模块）且是架构级，需要单独一轮。

### 5.2 本轮修复的**边界**

判定核心上锁，挡的是「**静态读懂判定逻辑**」和「**静态反推通过凭据**」。

**挡不住的**（数学上无法靠客户端解决）：

- 攻击者 patch `nc_verify_t1` 让它恒真 —— 但它现在是密文，
  patch 密文会让 MAC 失败 → `-11` 拒解。要绕过得先破 key 链。
- 攻击者 patch `ncVerify`（JNI 入口，明文）跳过判定调用 —— **这条路仍然开着**。
  但注意：`ncVerify` 只是 Java 快线，`sig_check.c` 的独立校验（直读 APK）
  不受影响，那条线在 `sig_check_entry` 的 constructor 里。
- 运行期内存 dump —— 解密后明文必然在内存中，这是自解密机制的物理上限。

### 5.3 关于 `.text` 完整性校验（复核清单 G 项）

复核清单说「机制是磁盘 vs 内存，设计正确，但改 3 处仍报 clean，原因未查明」。

我追到一半，得到一个**阶段性发现**（不是结论）：

```
0x4e3ec: adrp x0, 0x13000 / add x0, x0, #0x197  → "libc.so"
0x4e3f8: bl 0x21e6c                              → 定位文件
0x4e40c: bl 0x21f38                              → 取大小
0x4e480: bl 0x21d58                              → 读取（含 realloc，是完整读文件实现）
0x4e4bc: crc32(缓冲A + off, len)                 → A 来自文件
0x4e4cc: crc32(运行期地址 + off, len)            → B 来自内存
0x4e4dc: 比对
```

**`0x13197` 处的字符串是 `"libc.so"`** —— 这条路径校验的是 **libc 的
`.text`**，不是本 so 的。所以「改本 so 的 `.text` 仍报 clean」很可能因为
**这项校验根本不覆盖本 so 的 `.text`**。

日志里「libc .text」和「本 so .text」是两项，第二项走哪条路径**尚未确认**。
标记为**部分查明**，不是结论。要坐实需要真机抓 `openat` 的系统调用参数。

### 5.4 未做真机验证

本轮全部在宿主端（Termux aarch64 + clang）用
`exec -a` 注入 `/proc/self/cmdline` 模拟 Android 环境完成闭环
（`selftest=59`）。**未在真机跑过**，`/proc/self/maps` 的 APK 定位路径
在真机上的实际行为仍需 CI/真机确认。

## 6. 给下一位接手者

### 6.1 三条必须先读的

1. **「解密成功」不等于「保护有效」**。本轮修复的根因不是加密算法差，
   是**加密的东西不对**。任何后续验证都必须包含一项：
   「**密文段里装的是不是核心逻辑**」，而不只是「密文能不能解开」。

2. **段类型冲突是 clang 硬约束**。`const` 数据不能进 `AXR` 段。
   要装进加密区就另开 `AWR` 段，两段共用 key 与 MAC。

3. **`retain` + `used` 缺一不可**。`--gc-sections` 会静默回收无引用段。

### 6.2 改这块之前的环境检查

```bash
# 段属性是否真的生效（不是看源码，是看产物）
readelf -SW libnc.so | grep -E 'ncguard'

# 解密后权限是否各自最小
readelf -lW libnc.so | grep LOAD

# 判定核心是否在加密段
nm libnc.so | grep nc_verify_t1     # 地址应落在 .ncguard 范围内
```

### 6.3 下一步优先级（沿用报告 §17.4，本轮已插掉第 1 项）

```
✅ 已完成  判定核心 + 两张表进加密段（本轮）
P0-1      kill 链去 abort/_exit，改走「静默垃圾数据」
P0-2      .text 完整性校验改构建期基线（先查明 5.3）
P1-1      master[32] 构建期随机 + 注入
P1-2      失败路径分散（13 → N 个独立出口）
P2        .dynsym 符号抹除、节名标准化、字符串加密
```

**仍然成立的判断**（报告 §14.3）：如果只能再改一处，改 **kill 链**。
因为判定核心上锁只防「读懂」，kill 链才防「跑起来」。
攻击者仍可 patch `ncVerify` 跳过判定，此时唯一的阻力就是 kill 链。
