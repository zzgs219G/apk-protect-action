## B. 验一次 `k_so`（验证密钥派生）

### 原理

主报告声称：

```
k_so = HKDF-SHA256(ikm = master, salt = SHA256(certDER),
                   info = "nc-so-v1" + 包名, length = 16)
master = 0x11 × 32
```

如果这个公式对，应该算出 `k_so = 81830c13771b64b8de9a2d4642e19029`。

### 命令

```bash
cd ~/jianhe_re_work
python3 probe_ncguard.py target.apk ex/lib/arm64-v8a/libnc.so
```

### 预期输出

```
signing block id = 0x7109871A
certDER len = 666
certDER sha256 = d82e48dae7ce6268ebcefd61feb8128fdf1a55f574cbbbc788db7be4491b689e
k_so = 81830c13771b64b8de9a2d4642e19029
.ncguard addr=0x46ac8 off=0x46ac8 size=0x7f1c
decrypted head: c0035fd6fd7bbaa9fc6f01a9fd030091...
```

### 关键判据

解密后首字节必须是 **`c0 03 5f d6`**（`ret`），接下来是 `fd 7b ba a9`（`stp x29,x30,[sp,#-0x60]!`）。

**这是合法 AArch64 函数序言。** 如果 `master` 是错的，RC4 解出来必然是乱码，不可能出现这种结构。

### 这条不过说明什么

- `k_so` 不对 → `master` 不是 `0x11×32`，或派生公式记错 → **主报告 §3.3 核心论断作废**
- `certDER len` 不是 666 → 证书提取逻辑有问题

## C. 验 PLT 桩改动（验证 kill 链绕过）

### 命令

```bash
cd ~/jianhe_re_work

# 原包三个桩
for a in 4f6a0 4f8e0 4f8f0; do
  echo -n "原 0x$a: "; od -A n -t x1 -j 0x$a -N 4 ex/lib/arm64-v8a/libnc.so
done

# 改后三个桩
for a in 4f6a0 4f8e0 4f8f0; do
  echo -n "改 0x$a: "; od -A n -t x1 -j 0x$a -N 4 libnc_bypass4.so
done
```

### 预期结果

```
原 0x4f6a0:  30 00 00 d0      ← adrp x16, ...
原 0x4f8e0:  30 00 00 d0
原 0x4f8f0:  30 00 00 d0

改 0x4f6a0:  c0 03 5f d6      ← ret
改 0x4f8e0:  c0 03 5f d6
改 0x4f8f0:  c0 03 5f d6
```

### 为什么这条重要

`abort@plt` 在 `.text` 和 `.ncguard` 里被 **380 处**调用。逐处 patch 会一直漏。
**改 PLT 表项一次全废。**

数一下调用点：

```bash
llvm-objdump -d libnc_bypass4.so | grep -c 'bl\s+0x4f6a0'
```

## E. 验 `master` 是占位符

### 命令

```bash
od -A x -t x1 -j 0x13e80 -N 32 ex/lib/arm64-v8a/libnc.so
```

### 预期结果

```
013e80 11 11 11 11 11 11 11 11 11 11 11 11 11 11 11 11
013e90 11 11 11 11 11 11 11 11 11 11 11 11 ...
```

**32 个 `0x11`。**

### 但这条判据要小心

**光看到 `0x11` 不等于它在运行期被当作密钥用。**

真正的证据是 B 项：如果 B 项用 `0x11×32` 算出了能解开 `.ncguard` 的 `k_so`，
那就同时证明了「它是 `0x11`」+「它真的在用于派生」。

**所以 E 项不必单独复核，跟着 B 项一起验就行。**

## F. 验 `.ncguard_head` 的 XOR key（★ 最不可靠的一条）

### 为什么单列

主报告给的 key `346c9e9fadcfcff063956de65b8b8817` **不是从代码里读出来的**，
是**统计推断**（余弦相似度）出来的。16 个字节里只有 3 个有独立验证。

**这是全报告里最容易被推翻的一条。**

### 命令

```bash
cd ~/jianhe_re_work
python3 - <<'PYEOF'
so = open('ex/lib/arm64-v8a/libnc.so','rb').read()
head = so[0x4e9e4:0x4e9e4+0xa28]
key = bytes.fromhex('346c9e9fadcfcff063956de65b8b8817')
pt = bytes(head[i]^key[i%16] for i in range(len(head)))
open('review_head.bin','wb').write(pt)
print("首 32B:", pt[:32].hex())
PYEOF

# 反汇编看有多少 <unknown>
cp ex/lib/arm64-v8a/libnc.so review_head.so
python3 -c "
d=bytearray(open('review_head.so','rb').read())
p=open('review_head.bin','rb').read()
d[0x4e9e4:0x4e9e4+len(p)]=p
open('review_head.so','wb').write(d)"
llvm-objdump -d --start-address=0x4e9e4 --stop-address=0x4e9e4+0xa28 review_head.so | grep -c '<unknown>'
```

### 预期结果

```
首 32B: ffc304d1fd7b11a9fc9300f9fd43049148d03bd5e9031faa0a1540f9aa831ff8
```

`<unknown>` 数量应该 **0**（或极少，个位数）。

首指令 `ff c3 04 d1` = `sub sp, sp, #0x130`。

### 判据

```bash
# 合法指令比例
llvm-objdump -d --start-address=0x4e9e4 --stop-address=0x4f40c review_head.so \
  | grep -c '<unknown>'
```

**如果 `<unknown>` 超过总数的 5%（约 32 条），说明 key 是错的。**

### 这条不过说明什么

XOR key 错了 → `.ncguard_head` 那段分析的推论全部作废。
但**不影响 A、C、D 的结论**——因为最终产物里的 `.ncguard_head` 是明文，
不需要 key 也能量。

## G. ★ 自我更正项：`.text` 完整性校验

### 主报告原本的说法（已被作者推翻）

原文（§13.1）写：

> `.text` 完整性校验比较的是「内存 vs 内存」，基准不可信。

**这个判断在复核过程中被推翻了。** 重新反汇编后发现实际机制是：

```
0x4e46c  → 读 /proc/self/maps，确认 [addr, addr+len) 有映射
           （字符串 0x10edf = "/proc/self/maps"，
             格式串 0x12b9a = "%lx-%lx %7s"）
0x4e480  → syscall(openat) + syscall(read) 把【文件】全读到缓冲 A
0x4e4bc  → crc32(A + off, len)
0x4e4cc  → crc32(运行期地址 + off, len)
0x4e4dc  → 比对
```

**A 来自文件，B 来自运行期内存。这是「磁盘 vs 内存」，是正确做法。**

### 那为什么我改了 `.text` 仍报 `clean`？

现有两种可能，**都未被证实**：

1. **它校验的文件不是本 APK 的 so**——日志里 `libc .text` 和 `本 so .text` 是两项分开的，
   可能第二项实际读的是别的路径
2. **我改的 `0x238bc` 不在它的校验区间内**——区间可能只覆盖部分 `.text`

### 复核方法

在真机上抓它到底 open 了什么文件：

```bash
adb logcat -c
adb shell am start -n com.xixin.box/.MainActivity
sleep 3
# 需要 root 或用 strace/frida hook openat
# 简易版：看应用自己打的日志
adb logcat -d | grep -E '\snc\s+:' | head -30
```

**如果没条件抓 openat，这条就保持「未证实」状态，不要采信主报告的原判断。**

### 主报告应该怎么改

§13.1 应改为：

> `.text` 完整性校验的**机制是「磁盘文件 vs 运行期内存」**，设计正确。
> 但实测改 3 处 `.text` 字节后仍报 `clean`，**原因未查明**。
> 可能是校验区间未覆盖、或校验对象不是本 so。**待查。**

## I-2. 已由外部复核确认的错误（感谢复核者）

| 出处 | 原结论 | 实际情况 | 处理 |
|---|---|---|---|
| 主报告 §6.2 | `reserved8` 非零，产物与源码不一致 | **误判**。`expect_mac` 是 32 字节不是 16 字节，字段整体前移 8 字节。看到的 `10d2cadff1d5accf` 位于 `0x50`，是 `pkg_sha8`；`0x58` 的 `reserved8` **确实全零** | 已在 §6.2 标注推翻，并附正确字段切分 |

**复核者的纠正方法**（供后续参考）：

```bash
python3 - <<'PYEOF'
so = open('ex/lib/arm64-v8a/libnc.so','rb').read()
slot = so[0x16694:0x16694+96]
fields = [('magic',0,16),('wrapped_k_so',16,16),('wrapped_k_mac',32,16),
          ('expect_mac',48,32),('pkg_sha8',80,8),('reserved8',88,8)]
for name,off,ln in fields:
    print(f"0x{off:02x} {name:14s} = {slot[off:off+ln].hex()}")
PYEOF
```

输出应为：

```
0x00 magic          = 3072ee4891de04b50000000000000000
0x10 wrapped_k_so   = d6054d96f1e7128525a5b6cc9b496258
0x20 wrapped_k_mac  = df137044a989ac6284cb5c97e2b7e680
0x30 expect_mac     = 4e4be1d5...9366737bf7fec1ef6fb7fa147d2dfb49
0x50 pkg_sha8       = 10d2cadff1d5accf
0x58 reserved8      = 0000000000000000    ← 全零
```

**顺带验证**：`SHA256("com.xixin.box")[:8] = 10d2cadff1d5accf`，与 `pkg_sha8` 完全一致，
说明该字段语义正确、功能正常。

**这条错误的影响范围**：仅限 §6.2 本身。该结论**未被用于任何安全判断或评分**，
因此主报告的强度和结论不受影响。
