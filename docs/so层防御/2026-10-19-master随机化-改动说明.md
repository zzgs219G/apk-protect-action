> **配套文档**：`简盒-so层静态防御实测报告.md`（攻击方报告）、

>
> **本文回答**：报告静态部分 P1-1 的 `master[32] = 0x11×32` 这个口子怎么堵的，
> 为什么"只是换成随机数"不够，还剩什么。

---

## 0. 一句话

**`master` 从「全 `0x11`、躺在 `.rodata` 的公开常量」变成「每次构建随机、藏在
`.ncguard_head_ro` 密文段」**。攻击链从 2 步变 5 步，且中间产物全不是明文常量。

报告实测的「8 分钟离线解密 `.ncguard`」这条路，**现在至少要先解开 head 段才起步**。

---

## 1. 原来怎么被破的

```
攻击者动作                          成本
─────────────────────────────────────────────────
strings/od 读 .rodata 0x13e80        1 条命令
  → master = 0x11 × 32               零
读 APK 签名块取 SHA256(certDER)      一条命令
取包名（aapt2 dump packagename）     零
k_so = HKDF(master, cert, "nc-so-v1"+pkg)
  → RC4 解 .ncguard 32,540 B         8 分钟
```

**全程不需要运行、不需要真机、不需要证书私钥。** 因为 `master` 是公开常量，
HKDF 的四个输入全都能静态拿到。

---

## 2. 为什么"只换成随机数"不够

这是一个容易踩的坑，必须写清楚：

```c
// 这样改等于没改 ↓
static const uint8_t master[32] = {0x8f, 0x3a, ...};   // 随机了，但还在 .rodata
```

随机值若仍是 `.rodata` 里的裸常量，攻击者 `od` 一样读出来，**成本完全不变**。
随机化只增加了 0 秒——它挡不住任何会读二进制的人。

**必须【同时】做两件事：值随机 + 藏在读不到的地方。**

---

## 3. 改成了什么

### 3.1 结构

```
.ncguard_head_ro   AWR（不可执行）   32 字节   ← master（密文）
         ↑ 用 k_stub 加密，与 head 段在同一阶段锁
```

新增第 5 个契约段：

| 段 | flags | 内容 | 用哪把钥匙 |
|---|---|---|---|
| `.ncguard` | AXR | 业务代码 + 判定核心 | `k_so` |
| `.ncguard_ro` | AWR | 两张签名表 | `k_so` |
| `.ncguard_head` | AXR | unlock 本体 | `k_stub` |
| **`.ncguard_head_ro`** | **AWR** | **master** | **`k_stub`** |
| `.nckey` / `.nckey_stub` | AR | 密钥槽 | — |

### 3.2 为什么用 `k_stub` 而不是 `k_so`（关键设计）

**用 `k_so` 会死循环**：`k_so` 的派生正需要 `master`。
若 `master` 又被 `k_so` 加密，就是"要用自己的产物解开自己"。

用 `k_stub` 则链路是单向的：

```
碎片(4×uint16) → XOR_KEY → wrapped_k_stub → k_stub
                                              ├─→ 解 .ncguard_head（unlock 本体）
                                              └─→ 解 .ncguard_head_ro → master
                                                                        ↓
                                            master + certDER + pkg → HKDF → k_so
                                                                        ↓
                                                           解 .ncguard / .ncguard_ro
```

### 3.3 为什么必须分两个段（`head` 与 `head_ro`）

`.ncguard_head` 是 `AXR`（可执行），clang 拒绝让数据进去：

```
error: 'ncg_rc4' causes a section type conflict with 'ncg_master'
```

本仓库已经踩过三次同一个坑（签名表→`.ncguard_ro`、代码 vs 数据）。
**规矩：加密区里的代码和数据必须分属不同段。**

### 3.4 构建顺序（不可颠倒）

```
1) lock()      生成随机 master（os.urandom(32)）
               以【明文】写进 .ncguard_head_ro
               用它派生 k_so / k_mac → 加密 .ncguard + .ncguard_ro
2) lock_head() 用 k_stub 把 master 加密（同段同期）
               k_stub 又混入 crc32(.text)（代码自绑定）
```

`lock()` 必须先生成，因为 `k_so` 要用它；`lock_head()` 只负责藏。
`lock_head()` 里检查 master 全零即报错（说明一级锁箱没跑），**不静默降级**。

明文 master 只存在于构建机临时目录的中间产物里，产物一旦过完 `lock_head` 就是密文。

---

## 4. 攻击者现在要做什么

```
碎片(4 个 uint16，在 .data)           ← od 能读到，但要懂重组规则
  → XOR_KEY
  → wrapped_k_stub（在 .nckey_stub）
  → k_stub ← 还要先算对 crc32(.text)（代码自绑定，改一位就错）
  → 解 .ncguard_head（密文）
  → 解 .ncguard_head_ro → master
  → master + certDER + pkg → HKDF → k_so
  → 解 .ncguard
```

**从 2 步变 5 步，且每一步的产物都不是明文常量。**

必须说清楚的边界：**这不是"解不开"，是"更贵"。** 五个步骤全在 so 内部可静态完成，
不需要运行。真正不可静态还原的只有"运行期从 APK 读证书"（P1-a 已做）。

## 6. 本轮踩的坑（都会再遇到）

### 6.1 `ncg_rc4` 在 head 段里，stub 不能调它

第一版 `stub` 用 `ncg_rc4()` 解 `head_ro`，**直接卡死**。

原因：`ncg_rc4` 本身标在 `.ncguard_head` 段，此刻还是密文。
调用它就是执行密文。

**规矩：stub 能碰到的函数只能是 `.text` 里的。** 循环 XOR 就地内联（32 字节）。

这是本文件第二次踩同一个坑——上一轮 `lock_head()` 抄 `rc4()` 也踩过。

### 6.2 mprotect 粒度是页，`.ncguard_head_ro` 与 `.data`/`.bss` 同页

实测 arm64 布局：

```
.data               0x13ca8 .. 0x13cc4
.ncguard_head_ro    0x13cd0 .. 0x13cf0   ← 32 字节
.bss                0x13cf0 .. 0x36bc8
       ↑ 全在页 0x13000 内
```

第一版解完 master 后 `mprotect(..., PROT_READ)` 想把数据段设成只读，
**结果把 `.bss` 也变成只读** → 后续任何 `.bss` 写入即 SIGSEGV。

修复：恢复成 `PROT_READ | PROT_WRITE`（还原原状）。
密文段的安全性不靠页权限，靠"内容是密文"。

### 6.3 slot 从 96 扩到 104

需要存 `head_ro` 的 addr + size 两个 u32。原 `[44:48)` reserved 只有 4 字节，
而 `[64:96)` 已被 `expect_mac_head` 占满，**硬塞会与 MAC 字段重叠**（静默破坏校验）。

扩到 104，放在尾部 `[96:104)`。三处契约同步：`NCG_STUB_SIZE`、Python
`assert len(blob) == 104`、`.nckey_stub` 段大小。

## 7. 还剩什么问题

### 7.1 本轮没解决的

| 项 | 现状 |
|---|---|
| `k_stub` 仍是硬编码常量 | 可读，但要配 `crc32(.text)` 才能用 |
| 证书绑定只在构建期 | 运行期 P1-a 已做（从 APK 读证书） |
| `.text` 完整性校验是否覆盖本 so | 仅部分查明（见判定核心文档 §5.3） |
| 运行期内存 dump | 物理上限，客户端无解 |

### 7.2 关于「还能不能离线解」

**能，但更贵。** 五步全在 so 内部。真正的分界线是 P1-a：
运行期从 APK 读证书 → 派生 `k_so`。攻击者若只有 so 没有 APK，到此为止。

现在这两条组合起来：

```
静态只需 so        → 走到第 4 步（master）就卡住，还要 APK 的证书
有 so + APK        → 五步走完能解（这就是"更贵"的准确含义）
```

### 7.3 未验证

- **armv7 未在真机验证**：`.ncguard_head_ro` 的 ELF32 段定位照旧走 switch，
  逻辑与 ELF64 同构，但 `ncg_find_section` 只实现了 ELF64（既有缺口，本轮未扩）。
- **未做真机验证**：全部宿主端（Termux aarch64 + clang + `exec -a` + `LD_PRELOAD`
  补 `liblog` 桩）。

## 8. 给下一位接手者

### 8.1 三条

1. **随机化不等于藏起来**。`.rodata` 里的随机常量照样是公开的。
   要让攻击者读不到，必须让它处于"要先解开另一层才能拿到"的位置。
2. **加密区的代码和数据必须分不同段**。clang 会直接报
   `causes a section type conflict`，别试图绕过。
3. **stub 只能调 `.text` 里的函数**。调 head 段里的任何函数都是执行密文。

### 8.2 验收

```bash
# master 是否已随机化
python3 -c "d=open('libnc.so','rb').read(); print(d.count(b'\x11'*32), d.count(b'\x11'*16))"
#   期望 0 0

# master 是否在密文段
readelf -SW libnc.so | grep head_ro
#   应有 .ncguard_head_ro AWR，锁定后内容为随机字节

# 功能是否完好
bash scripts/lib/tests/test-so-lock.sh     # 19/19
```
