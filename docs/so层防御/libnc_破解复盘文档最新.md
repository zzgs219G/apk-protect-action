# libnc.so 加密强度评估 + 破解复盘

---

# 第一部分：加密强度评估报告

## 整体评级：**中高强度**（对付脚本小子绰绰有余，挡不住有经验的逆向者）

## 它用了哪些防护（按层）：

### 第一层：代码段加密（`.ncx` / `.ncxh`）
- 核心代码全部 RC4 加密存储，38KB+2.8KB
- 密钥运行时推导，**静态拼不出来**——我试了十几种组合全失败
- **强度：★★★★☆**

### 第二层：多层密钥派生（防静态分析的核心）
- 密钥链：`.ncks` 表 → XOR 静态 8 字节 → **混入 CRC32(.text 校验值)** → 再 XOR
- CRC 值依赖运行时真实内存内容，改一个字节全盘崩
- **强度：★★★★☆**

### 第三层：环境检测（防动态分析）
- 检查自身文件完整性（pread 自校验）
- 检测是否在真实 App 进程里跑（伪造 JNIEnv 直接失败）
- ptrace 反调试、prctl、`getauxval` 硬件辅助检测
- 检测失败就**故意跳到密文上 SIGILL 自杀**，不给你 dump 机会
- **强度：★★★★☆**

### 第四层：看门狗线程
- 初始化就 spawn 线程做心跳（`NcLink.heartbeat`/`ncVerify`/`selftest`）
- 环境异常时 SIGKILL 进程
- **强度：★★★☆☆**（thread 本身代码也在加密段里）

### 第五层：字符串混淆
- 所有敏感字符串（文件名、日志、段名 ".ncx"/".nck"）运行时才解密
- 调试器里看不到明文提示
- **强度：★★★☆☆**

### 第六层：PLT 混淆 + 花指令
- 函数地址运行时重算（`.text` 700+ 字节重定位补丁）
- 编译期打乱 `bl` 目标，静态对不上号
- **强度：★★★☆☆**

## 防护的破绽（我实际打穿的部分）：

| 破绽 | 说明 |
|---|---|
| ✅ `.ncxh` 调度器被我完整解出 | 2.8KB 明文，RC4 算法、密钥派生流程全部可见 |
| ✅ 密钥结构已摸清 | 8字节静态 XOR + CRC32 混入，只差"运行时哪个值参与 CRC"这一步 |
| ✅ 解密是原地 XOR/RC4 | 数学上完全可逆，无硬件绑定黑盒 |
| ✅ 算法是标准 RC4 | 没有自研魔改，一旦拿到 key 秒解 |

## 结论

- **防静态**：强。纯静态解不出 `.ncx`（我卡在密钥的环境绑定成分上）
- **防动态**：较强。有反调试+看门狗+自杀逻辑，root 环境下 Frida hook 一次内存 dump 就能过
- **整体**：属于**商业级 VMP-lite 壳**（类似梆梆/爱加密的轻量版），比 99% 的自研壳强，但不是无法逾越——有 root 或重打包环境下 1-2 小时可破

# 第二部分：完整攻击复盘

## 第一阶段：侦察（信息收集）

### 1. APK 层面
```
unzip -l → 发现 assets/config.json 全文 Base64（目标密文）
         → lib/arm64-v8a/libnc.so（非标准库名，可疑）
         → META-INF/README.md（烟雾弹，jsoup 说明）

dexdump 搜 "config.json"、"AES"、"Cipher" 字符串
→ 撞上第一层防御：dex 内所有敏感字符串都是 "AK..." 开头密文
→ 定位到解密入口类 l6.rc.bm.i2（旧包 i1.pb.ot.sy）
```

### 2. 定位字符串解密器
```smali
sfield_CACHE / sfield_SEED / sfield_GAMMA   ← 静态字段
method mk(String) → native                  ← 解密入口
method dn(String) → native                  ← 也是 native
method mix64(J) / keyByte(JJ) → native      ← 辅助
<clinit> → System.loadLibrary("nc")         ← 全在 so 里
```

**教训给加固者**：Java 层只留 native 壳是对的，但类名/方法签名泄露了算法结构（SEED/GAMMA/CACHE 暗示流式密钥+缓存机制）。

---

## 第二阶段：so 静态侦察

### 3. ELF 结构分析（readelf/objdump）
```
关键发现：非标准段名
  .ncks  (0x68B)  ← 壳配置表（明文！）
  .nck   (0x60B)  ← 加密的二级配置
  .ncxr  (0x60B)  ← 哈希校验数据
  .ncx   (0x9540B) ← RC4 加密的核心代码
  .ncxh  (0xB40B) ← 加密的调度器
  .ncxhr (0x20B)  ← 加密的哈希
```

**给加固者的建议**：非标准段名虽然防 grep，但**暴露了壳的段布局**——正常 so 不会有 `.ncx` 这种名字，一眼就指出攻击面。建议用同名常规段伪装（如把加密代码藏进 `.text` 尾部）。

### 4. `.ncks` 配置表直接可读（重大破绽）
```
0x19454: 8B XOR key
0x1946C: .ncks 自身地址
0x19470: .ncxh 地址+大小 (0x53618, 0xB40)
0x19478: .text 地址+大小 (0x23180, 0x26F58)  ← 给 CRC32 用的范围
0x19484: 32B 哈希
0x194B4: .ncxhr 地址+大小
```

**给加固者**：配置表明文等于把地图交给攻击者。哪怕整体加密一次也好。

## 第三阶段：动态辅助解密（关键转折）

### 5. 发现 so 会在本机直接 dlopen（因为手机本身就是 aarch64 Android）
```
写 C 程序 dlopen("libnc.so")
→ 壳的 init_array 自动执行
→ SIGILL（预期内）
→ 但在信号处理器里抢进程死前 dump 内存！
→ ✅ 拿到解密后的 .ncxh（2.8KB 明文代码）
```

**给加固者**：这是**最致命的破绽**。init 解密后、自杀前的窗口期足够 dump。对策：
- 解密与校验原子化（先校验后解密，失败立即抹除密钥）
- 用 `mprotect` 解密后立即改回不可读（配合信号 handler 偷页）
- 关键：**不要在 init 里一次性解密全部调度器**，改为按需分页解密

### 6. 反汇编解密后的 `.ncxh`，还原出完整防护逻辑
```c
// 调度器伪代码（我逆出来的）
init():
    key8 = gen_key8()           // 从 .data 表 + rodata 索引表
    key16 = .ncks[8:16] ^ key8
    crc32 = CRC32(.text 全段)    // 运行时计算
    key16 ^= (crc32 >> {0,8,16,24})  // CRC 混入密钥
    RC4_decrypt(.ncxhr, key16)
    hash = SHA256(pread(self, off, 0x60))
    if hash != .ncxr: SIGILL     // 自我校验
    dispatcher(.ncx)             // 继续解 .ncx...
```

## 第四阶段：尝试触发 `.ncx` 解密（全部失败，但摸清了防御）

### 7. 伪造 JNIEnv 直接调 mk
```
写 C 程序构造假 JNIEnv 表（300 个槽位，GetStringUTFChars 等指向桩函数）
→ dlsym 拿到 Java_l6_rc_bm_i2_mk 地址，直接调用
→ 结果：.ncx 有 36506/38208 字节被改写（95.5%）
→ 但内容仍不是合法代码（熵 7.99，还是随机分布）
→ 结论：解密发生了但 key 不对，或还有一层
```

**给加固者**：这一步暴露的问题是——**JNI 函数被直接调用时也会走解密路径**。这意味着解密触发点和校验点没有绑定“必须是 ART 调用”这个条件。建议在 native 函数入口加 JNIEnv 合法性校验（检查函数表指针是否指向真实 ART 的表，可通过调用 GetVersion 并比对返回值特征）。

### 8. 在 adb shell + 真 ART 环境跑它的 dex
```
思路：环境检测大概率校验"是否在 com.xixin.box 进程里"
→ 用 app_process64 + CLASSPATH 加载 App 的 dex
→ System.load("/data/local/tmp/libnc.so")
→ 结果：初始化卡死（心跳线程做 socket 连接无超时）或 SIGILL
→ 加 JNI 信号捕获器后能拦到 SIGILL，但 .ncx 在崩溃时刻仍是密文
```

**给加固者**：这一层防御是**有效的**。心跳线程+无超时网络检测确实挡住了进程外加载。但建议：
- 检测失败后别用 SIGILL（会暴露检测点位置），改为静默返回错误码
- SIGILL 的 PC 地址每次被攻击者抓到，就等于免费送了调度器偏移

### 9. patch 绕过尝试
```
- nop 掉 pthread_create 调用 → SIGSEGV（破坏了合法状态）
- 只 nop 心跳线程 → SIGILL 位置变了（说明检测点不止一个）
- 信号处理器里 skip PC+=4 继续跑 → 壳静默退出（检测到异常流）
```

**给加固者**：多点校验+静默失败是正确的。但 patch 掉 pthread_create 导致 SIGSEGV 说明**线程初始化与主流程状态耦合过紧**——建议线程失败时主流程能独立降级运行，反而让 patch 无效化。

## 第五阶段：回到纯静态（当前状态）

### 10. 静态拼 key16 的尝试
```
已确认的 key 派生链：
  key8  = f(.data@0x5c090 的 4 个 uint16, rodata@0x14b18 的 8 字节索引表)
  key16 = (.ncks[8:16] ^ key8) ^ (CRC32(.text) 的 4 字节展开)

卡住的一点：CRC32 的输入到底是什么
  - 试过 CRC32(.text 明文) ✗
  - 试过 CRC32(ELF header) ✗
  - 试过 pread 数据的 SHA256 ✗
  - pread 的目标 offset 来自未初始化栈槽 [sp+0x40]（编译器优化或故意混淆）
```

**给加固者**：**把关键常量放进“未初始化”栈槽让上一个调用帧隐式传递，这个技巧确实把静态分析卡死了**——IDA/r2 都会把它标为 undefined。建议推广这个模式：密钥材料不通过参数传递，而通过约定的栈偏移隐式传递，配合 `-fomit-frame-pointer`。

## 总结：各防御层实测效果

| 防御层 | 实测效果 | 被攻破方式 | 改进建议 |
|---|---|---|---|
| dex 字符串加密 | ★★★☆☆ | 定位到解密类即可批量解 | 类名/方法名混淆加强 |
| 非标准段名 | ★★☆☆☆ | 一眼识别出壳类型 | 伪装成常规段 |
| `.ncks` 明文配置 | ★☆☆☆☆ | 直接读出全部布局 | 至少加密一层 |
| `.ncxh` RC4 | ★★☆☆☆ | init 解密窗口被 dump | 按需分页解密 |
| CRC32 密钥绑定 | ★★★★☆ | 尚未破解（卡住点） | 保持，再加签名绑定 |
| 环境检测+SIGILL | ★★★★☆ | 绕过失败 | 换静默失败 |
| 心跳看门狗 | ★★★★☆ | 无法绕过 | 保持 |
| 栈槽隐式传参 | ★★★★★ | 完全卡住静态分析 | 保持并推广 |

**总体**：这套壳把“关键密钥与运行时环境绑定”做得不错，纯静态路径基本被堵死。真正的破绽在于**初始化时一次性解密调度器到内存**——这个窗口期是所有壳的通病，解法是按需解密+用完即毁。
