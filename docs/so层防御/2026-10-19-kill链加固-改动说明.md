## 0. 一句话

**改 `abort@plt` / `_exit@plt` / `raise@plt` 三个桩（各 4 字节）废掉 380 个调用点**
这条路已经不通了：四个软目标（含 `syscall@plt`）**全部从产物的 PLT 表里消失**，
kill 逻辑本身还进了加密段。

但要说清楚：**这是提高了成本，不是不可绕过。** 见 §5。

## 1. 为什么不是「静默污染」

报告 §14.3 推荐的是「改成静默垃圾数据」——检测失败不杀进程，让业务输出垃圾。
**这个方案没法对任意 APK 通用**，所以没有采用。三个硬障碍：

| 障碍 | 说明 |
|---|---|
| **不知道什么叫「功能全废」** | 计算器算错、播放器花屏是可见的；但工具类 App 里某个方法可能三年不被调用。没有业务语义知识就无法判断污染得对不对 |
| **污染点选不出来** | `.ncguard` 里是 dex2c 转译产物，函数数量随 APK 变化，转译器不知道哪个是「核心业务」 |
| **无法自动验证** | 方案 2 能断言「PLT 里还有没有 abort」；污染方案的验收是「这个 App 的核心功能全部不可用」，需要逐个人工测试。**对流水线来说，没法自动验证的防御等于没有防御** |

报告作者是在「已知这是简盒」的前提下提的——他知道壳加载是核心。流水线接的是任意 APK，
没有这个知识。

**采用的两条不依赖业务语义的路**：

- **方案 4**：kill 逻辑进加密段 → 攻击者**找不到**它
- **方案 2**：内联 `svc` 去掉 PLT 软目标 → 找到了也**不能一击全废**

## 2. 方案 4：kill 逻辑进加密段

### 2.1 改了什么

| 文件 | 函数 | 处理 |
|---|---|---|
| `env_check.c` | `env_delayed_kill` | 标进 `.ncguard` |
| `sig_check.c` | `delayed_kill` | 标进 `.ncguard` |

段标记宏：

```c
#if defined(NC_GUARD_SECTIONED) && !defined(HOST_TEST)
#  define ENV_KILL_SECTION __attribute__((section(".ncguard"), retain, used, noinline))
#else
#  define ENV_KILL_SECTION
#endif
```

### 2.2 三条纪律（违反即死锁或误红）

- [ ] **调用方不能标段**：`env_fail` / `sig_verify` / `env_check_entry` 保持明文。
      它们是 unlock 的使用者，标进去 = 「解锁前就要调用密文」= 死锁。
      只标**被调用**的 kill 函数本身。
- [ ] **必须条件化**：宿主测试没有解锁设施，标了段就读到密文 → 假红。
- [ ] **时序必须安全**：`ncg_auto_unlock` 是 `constructor(50)`，早于
      `env_check_entry` / `sig_check_entry` 的默认 constructor（65535）。
      所以线程真正执行到 kill 函数时，段必已是明文。**已实测 `selftest=59` 通过。**

### 2.3 效果

| | 修复前 | 修复后 |
|---|---|---|
| `env_delayed_kill` 位置 | `.text` 明文 | **`.ncguard` 密文** |
| 反汇编 | 可读 | 大量 `<unknown>` |
| 静态搜 kill 逻辑 | `abort@plt` 引用一目了然 | 只看到「某处 `bl` 进了一段解不开的东西」 |

## 3. 方案 2：内联 `svc`，去掉 PLT 软目标

### 3.1 为什么 `syscall()` 也是软目标

此前代码已经「syscall 直调绕过 libc」——但那是调用 **libc 的 `syscall()`**，
它**本身也是一个 PLT 表项**（`syscall@plt`）。

所以当时的真实绕过成本只是「改 4 个桩而不是 3 个」，不是报告以为的 3 个。

### 3.2 改法

```c
#if defined(__aarch64__)
    register long x8 __asm__("x8") = n;      /* arm64: 调用号在 x8 */
    ...
    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), ... : "memory");
#elif defined(__arm__)
    register long r7 __asm__("r7") = n;      /* armv7: 调用号在 r7 */
    ...
    __asm__ volatile("svc #0" : "+r"(r0) : "r"(r7), ... : "memory");
#endif
```

用 GNU 内联汇编的具名寄存器变量绑定，让编译器自己安排其余寄存器——
写死物理寄存器分配会与编译器分配的实参冲突。

终止路径（`env_raw_die` / `sig_raw_die`）：

```
svc 直投 tgkill(SIGABRT)  ← 不经任何 libc
  └─ 信号被拦？→ __builtin_trap() 生成 brk #1  ← 仍不经 libc，SIGILL 也留 tombstone
```

`tid` 也用 `__NR_gettid` 直调（`gettid()` 在部分老 bionic 上是 API 21+ 符号）。

### 3.3 为什么两个文件各写一份

**`sigcheck-only` 组合下 `env_check.c` 不参与编译**（`protect.sh` 的拷贝清单里
只有勾 envcheck 时才拷它）。跨文件依赖会让「只勾签名校验」直接链接失败。

用 `static`：两文件同时编译时各有一份副本，互不冲突，也不导出符号扩大攻击面。
多约 100 字节代码，换「任何组合都能编过」。

### 3.4 效果（实测）

```
$ nm -D -u libnc.so | grep -wE "abort|syscall|_exit|raise"
（无输出）

$ objdump -d --section=.plt libnc.so | grep -oE "<[a-z_]+@plt>" | sort -u
__android_log_print@plt __clear_cache@plt ... （共 66 个，均与 kill 无关）

$ objdump -d libnc.so | grep -c svc
17        ← 内联系统调用
```

**四个软目标全部消失。** PLT 表里再没有任何一个「改 4 字节废掉 kill 链」的入口。

### 3.5 终止能力实测

```bash
$ ./killtest
before die, pid=7538
Aborted
$ echo $?
134        # 128 + 6 = SIGABRT，正确
```

## 5. 还剩什么问题（如实）

### 5.1 本轮**不改变**的根本问题

**`master[32]` 仍是 `0x11`×32 占位符。** 这在报告里排 P1-1，本轮没动。

后果直接削弱本轮收益：

> 攻击者若离线解开 `.ncguard`（报告实测 **8 分钟**），就又能看到 kill 逻辑在哪。

也就是说：**方案 4 提高的是「发现成本」，不是「patch 成本」。** 它把
「30 秒静态搜索」变成「先花 8 分钟离线解密」——是纵深的一层，不是终点。

要真正断绝，必须做 `master` 构建期随机化 + 注入。**这是下一轮的 P0。**

### 5.2 本轮仍未解决的攻击路径

| 路径 | 现状 |
|---|---|
| patch `ncVerify`（JNI 入口，明文）跳过判定调用 | **仍开着**。但 `sig_check.c` 的独立校验（直读 APK）不受影响 |
| 逐个 patch kill 调用点 | 仍可行，但调用点现在分散在密文段内，必须先解密才找得到 |
| 运行期内存 dump | 解密后明文必在内存，这是自解密机制的物理上限 |
| `.text` 完整性校验是否真覆盖本 so | 仅部分查明（见上一轮文档 §5.3） |

### 5.3 未验证项

- **armv7 未在真机验证**：内联汇编已用 `--target=armv7-linux-androideabi` 交叉编译
  验证语法与指令生成（`mov r7, r0` / `svc #0`），但未在 armv7 设备运行。
- **未做真机验证**：本轮全部在宿主端（Termux aarch64 + clang）完成，
  用 `exec -a` 注入 `/proc/self/cmdline` 模拟 Android 环境 + `LD_PRELOAD` 补
  `liblog` 桩。
- **kill 链真实触发未端到端测**：只单独验证了 `sig_raw_die` 的终止能力
  （退出码 134 = SIGABRT），没有构造「签名校验失败 → 走完整条 kill 链」的场景。

## 6. 给下一位接手者

### 6.1 三条必须知道的

1. **`syscall()` 也是 PLT 表项**。说「syscall 直调绕过 libc hook」时，
   先确认二进制里还有没有 `syscall@plt`——有的话攻击者改一处即可。
2. **kill 函数标段，调用方不标段**。探针/判定核心是「被调用方」可以锁；
   `env_fail`/`sig_verify` 是 unlock 的使用者，锁了就是死锁。
3. **`sigcheck-only` 组合下 `env_check.c` 不参与编译**。任何跨文件依赖都要
   先确认编译组合。

### 6.2 验收命令

```bash
# kill 链软目标是否清零
nm -D -u libnc.so | grep -wE "abort|syscall|_exit|raise"     # 应为空
objdump -d --section=.plt libnc.so | grep -E "abort|_exit|raise|syscall"  # 应为空

# kill 逻辑是否在加密段
nm libnc.so | grep env_delayed_kill    # 地址应落在 .ncguard 范围内
readelf -SW libnc.so | grep .ncguard
```

### 6.3 下一步优先级

```
✅ 已完成  判定核心 + 两张表进加密段（2026-10-19 上一轮）
✅ 已完成  kill 链进加密段 + 去掉 PLT 软目标（本轮）
P0        master[32] 构建期随机化 + 注入   ← 不做这个，前两项的收益都被 8 分钟解密吃掉
P0-2      .text 完整性校验改构建期基线（先查明是否覆盖本 so）
P1        失败路径分散（13 → N 个独立出口）
P2        .dynsym 符号抹除、节名标准化、字符串加密
```

**为什么 `master` 现在是第一优先**：本轮与上一轮的收益都建立在
「攻击者解不开 `.ncguard`」上。而 `master` 是公开常量，解开的成本是 8 分钟。
**把这个口子堵上，前两项才有意义。**
